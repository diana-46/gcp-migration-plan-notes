# 7. dbt 테이블 아웃풋: 어디에 어떻게 저장할지

> dbt 모델의 SELECT 결과가 실제로 어떤 형태/위치에 적재되는지, 모델 레이어별로 어떤 저장 전략을 골라야 비용·성능이 맞는지 정리.
> 관련: [[1_materialization]], [[애슬론/5_Neptune SQL 변환의 dbt-BigQuery 대체 검토]]

---

## 0. 출발 질문

dbt 모델 출력은 중간 테이블일 수도, 최종 마트일 수도 있다. 그리고 보통 **쓰기 1회 << 읽기 N회**.
→ 그러면 모델마다 "이거 누가/얼마나 자주 읽나" 를 먼저 정하고, 그에 맞춰 저장 위치·포맷·인덱싱 정책을 골라야 한다.

이 노트는 그 결정 프레임을 정리한다.

## 1. dbt 모델 출력이 갈 수 있는 3가지 위치 (BQ 어댑터)

본 노트는 **BigLake non-Iceberg** 를 기준으로 정리. Neptune POC 처럼 스냅샷·append-only 배치 패턴이면 non-Iceberg 가 자연스러운 fit (UPDATE/DELETE/시간여행 요구사항 없음). Iceberg 는 mutable 배치·CDC 가 필요할 때만 검토.

|                  | Native                                  | GCS External                                      | BigLake (non-Iceberg)         |
| ---------------- | --------------------------------------- | ------------------------------------------------- | --------------------------- |
| 실제 데이터 위치        | BQ 내부 Capacitor                         | GCS 파일 (Parquet/CSV/...)                          | GCS 파일 + BQ 메타              |
| 사용자 권한           | BQ 권한만                                  | BQ + **GCS 직접 권한**                                | BQ 권한만 (Connection 위임)      |
| 파티션              | 컬럼 1개 + granularity                     | **Hive 다단 폴더** (key 여러개)                         | Hive 다단 폴더                  |
| 클러스터링            | ✅ 최대 4개 (블록 프루닝)                       | ❌                                                 | ❌                           |
| INSERT/MERGE     | ✅                                       | ❌ (읽기 전용)                                         | ❌ (읽기 전용)                   |
| 적재 방법            | dbt 가 직접                                | 외부 적재 후 메타 등록 / EXPORT DATA                      | EXPORT DATA → CREATE EXTERNAL |
| 컬럼/행 보안          | ✅ Policy tag, RLS                       | ❌                                                 | ✅ Policy tag, RLS, 마스킹      |
| 멀티 엔진 공유 (Spark) | ❌ (BQ 만)                                | ✅                                                 | ✅ (거버넌스 일관)                 |
| 메타 캐싱            | (자동 결과 캐시)                              | ❌ 매 쿼리 GCS 리스팅                                   | ✅ 파일 리스트 캐싱                 |
| MV / Search Idx  | ✅                                       | ❌                                                 | ❌                           |
| dbt 표현           | `materialized='table' / 'incremental'`  | `materialized='external_table'` / `dbt-external-tables` | post_hook(EXPORT+EXTERNAL)  |

핵심: **Native = BQ 내부, External/BigLake = GCS 파일.**
`parquet` 태그가 붙어 있어도 Native 면 GCS 에 파일이 안 생긴다 (그냥 라벨일 뿐).
**External vs BigLake** 는 같은 GCS 기반인데 **거버넌스(권한 위임 + 보안) + 메타 캐싱** 유무 차이. BigLake = "거버넌스 붙은 External" 의 업그레이드 버전.

## 2. 비용 구조 — 어디서 새는가

### 2-1. 스토리지

| 클래스 | 단가 | 설명 |
|---|---|---|
| BQ Native Active | $0.020 / GB / 월 | 최근 90일 내 수정 |
| BQ Native Long-term | $0.010 / GB / 월 | 90일 미수정 시 자동 |
| GCS Standard | $0.020 / GB / 월 | External/BigLake 기본 |
| GCS Nearline | $0.010 / GB / 월 | 월 1회 미만 접근 |
| GCS Coldline | $0.004 / GB / 월 | 분기 1회 미만 |
| GCS Archive | $0.0012 / GB / 월 | 연 1회 미만 |

### 2-2. 컴퓨트 (on-demand)

- $6.25 / TB 스캔 — **쿼리당 읽은 바이트** 기준
- 같은 SQL 이어도 Native(클러스터링+통계) vs External(매번 GCS 리스팅) 의 스캔 효율이 다름
- `SELECT *` 는 컬럼 저장 이점을 다 날림. 필요한 컬럼만 SELECT 가 곧 비용

### 2-3. 부수 비용

- GCS class A operations (write/list): $0.005 / 1000
  - External 은 매 쿼리마다 list → BigLake metadata cache 가 이걸 줄임
- Egress (multi-region 이동) — 의외로 큼
- 적재 자체는 BQ load job 무료, EXPORT DATA 는 슬롯 사용

## 3. 모델 레이어별 운영 전략

dbt 표준 컨벤션(staging → intermediate → marts) 기준.

| 레이어                      | 누가 읽나          | 빈도                | 권장 materialization                                          | 실제 저장                           |
| ------------------------ | -------------- | ----------------- | ----------------------------------------------------------- | ------------------------------- |
| staging (`stg_*`)        | 다음 dbt 모델만     | run 당 1회          | `view` / `ephemeral`                                        | 저장 0 (메타만 / CTE 인라인)            |
| intermediate (`int_*`)   | 다음 dbt 모델만     | run 당 1~N         | `view` or `ephemeral` 디폴트, 재사용 무거우면 `table`                 | 보통 저장 0. `table` 선택 시 BQ Native |
| marts (`fct_*`, `dim_*`) | BI, 분석가, 서비스   | 하루 수백~수만          | `incremental` (+ partition + cluster) / `materialized_view` | BQ Native                       |
| snapshots (시계열 적재)       | 마트 빌드 + 가끔 분석  | 적재만 자주, SELECT 적음 | `incremental`                                               | BQ Native (핫) → GCS (콜드 티어링)    |
| archive                  | 거의 안 봄 (보존 의무) | 월 N회 이하           | `external_table`                                            | GCS Coldline/Archive            |

규칙: **읽힘이 적을수록 저장 최소화, 읽힘이 많을수록 스캔 최소화**.

> **intermediate 가 BQ Native 인 이유 (GCS/BigLake 가 아닌 이유):**
> 다운스트림이 dbt 모델 하나 뿐이라 BigLake/External 이 주는 장점(멀티 엔진 공유, 권한 거버넌스, Hive 다단 파티션, 콜드 아카이브)이 전부 불필요.
> 반면 GCS 로 가면 EXPORT→CREATE EXTERNAL 2단계 오버헤드 + 클러스터링 불가 + 다음 모델 GCS 리스팅 비용까지 떠안음.
> 그래서 intermediate 는 "저장 안 하는 게 디폴트(view/ephemeral)" 이고, 무거운 계산을 N번 재사용해야 할 때만 `table` 로 물리화 — 그때 자연스럽게 BQ Native.

## 4. materialization 선택 = 비용 정책 선택

[[1_materialization]] 에 정리된 5종을 비용 관점으로 재배열:

```text
저장 0 / 매 SELECT 재계산  ─────────────  view, ephemeral
                                          ↓ (자주 읽힘)
저장 O / SELECT 빠름        ─────────────  table
                                          ↓ (대용량 + 증분)
저장 O / 증분 처리          ─────────────  incremental
                                          ↓ (집계 패턴 고정)
저장 O / 집계 미리 계산     ─────────────  materialized_view
                                          ↓ (외부 공유 / 콜드)
저장 GCS / 파일             ─────────────  external_table (+ BigLake)
```

선택 기준: **이 모델 다운스트림이 누구인가, 얼마나 자주 SELECT 하나, 데이터 규모는 어느 정도인가**.

## 5. ephemeral 의 함정과 임시 테이블 lifecycle

ephemeral 은 "BQ 한테는 한 쿼리, 개발자한테는 N개 파일" 컴파일 트릭. 가독성·lineage·테스트성을 챙기면서 런타임 비용은 한 쿼리와 동일. 다만 **만능이 아님** — BQ 의 CTE 동작 때문에 의외의 비용 함정이 있다.

### 5-1. 검증: ephemeral 은 정말 인라인되는가

`dbt compile` 후:

```text
target/compiled/.../case3_first_open/   ← 7개 (lineage·docs용)
  tmp_open.sql, tmp_click.sql, ..., stat_first_open_detail_daily.sql

target/run/.../case3_first_open/        ← 1개 (실제 BQ 실행)
  stat_first_open_detail_daily.sql
```

실제 BQ 로 가는 SQL 모양:

```sql
create or replace table dataset.stat_first_open_detail_daily
partition by create_date as (
  with __dbt__cte__tmp_open as ( SELECT ... ),
       __dbt__cte__tmp_click as ( SELECT ... ),
       __dbt__cte__tmp_imp   as ( SELECT ... ),
       ...
  SELECT ... FROM __dbt__cte__tmp_stat_result
);
```

→ ephemeral N개가 `__dbt__cte__<이름>` 으로 풀려서 **한 거대한 쿼리**로 합쳐짐. BQ 입장에선 한 파일에 WITH 절로 다 쓴 것과 동일. Airflow task 도 마트 1개만 생김.

### 5-2. BQ CTE 의 함정: 자동 물리화 안 됨

```sql
WITH tmp_huge AS (
  SELECT ... FROM source_100gb        -- 100GB 스캔하는 쿼리
)
SELECT a.*, b.parent
FROM tmp_huge a
JOIN tmp_huge b ON a.id = b.parent_id  -- ← tmp_huge 가 2번 평가될 수 있음
```

같은 CTE 를 여러 번 참조하면 BQ 가 N번 재계산할 수 있다. 옵티마이저가 fuse 해주는 경우도 있지만 **보장 없음**. 쿼리가 복잡할수록 풀려서 같은 source 를 여러 번 읽음.

ephemeral 모델이 다운스트림에서 5번 ref 된다면, BQ 가 받는 한 쿼리에서도 동일하게 "5번 참조되는 CTE" 가 되어 같은 위험에 노출.

### 5-3. ephemeral 이 나쁜 케이스

- 같은 ephemeral 모델이 다운스트림에서 **여러 번 ref**
- 중간 단계가 데이터를 **크게 축소** (filter/aggregate 효과)
- 원본 source 가 **거대**해서 다중 스캔 비용이 큼
- 전체 실패 시 **재실행 단위가 큼** (디버깅·retry 부담)
- 쿼리가 너무 복잡해 옵티마이저가 못 따라옴

→ Neptune 의 temp table 패턴(각 단계가 작은 중간 테이블로 떨어져 다음 단계는 작은 테이블만 스캔하던 구조)은 위 사항을 자연히 회피하던 구조였다. dbt-BQ 로 옮기면서 **다 ephemeral 로 바꾸면 이 이점을 잃음**.

### 5-4. 해결: 참조 횟수 ≥ 2 + 데이터 축소 효과 있는 단계만 `table`

```python
# 5번 참조되는 무거운 중간 단계 → 진짜 table
{{ config(materialized='table', hours_to_expiration=2) }}

# 1번만 참조되는 가벼운 중간 → ephemeral 유지 (인라인이 더 쌈)
{{ config(materialized='ephemeral') }}
```

case3 적용 예:

| 모델 | 참조 횟수 | 권장 |
|---|---|---|
| `tmp_open` | **5번** | `table` + run-scoped alias + expiration |
| `tmp_click`, `tmp_imp`, `tmp_pv`, `tmp_open_web` | 각 1번 | ephemeral 유지 |
| `tmp_stat_result` | 1번 | ephemeral 유지 |
| `stat_first_open_detail_daily` | — | 마트 (incremental) |

### 5-5. 임시 테이블 lifecycle — "영구 보관" 걱정 해소

"`table` 로 떨어뜨리면 영구히 남는 거 아냐?" → BQ 의 `expiration_time` 으로 해결.

**(a) `hours_to_expiration` — 모델 단위 (가장 깔끔)**
```python
{{ config(
    materialized='table',
    hours_to_expiration=2,    -- BQ 가 2시간 뒤 자동 DROP
) }}
```
Neptune 의 "ETL 끝나면 사라지는 temp" 시맨틱과 매칭.

**(b) 데이터셋 디폴트 만료 — 조직 정책**
```bash
bq mk --default_table_expiration=86400 dbt_test_tmp    # 24시간
```
```yaml
# dbt_project.yml
models:
  dbt_test:
    case3:
      +schema: tmp                # → dbt_test_tmp 데이터셋으로 자동 격리
```
intermediate 데이터셋 자체에 만료 강제. 모델마다 설정 안 해도 됨.

**(c) post_hook DROP — 즉시 정리**
```python
post_hook=[
    "DROP TABLE IF EXISTS {{ ref('tmp_open') }}",
]
```
명시적·즉시. 모델 N개면 반복.

**(d) BQ TEMP TABLE (세션 스코프) — 비추**
`CREATE TEMP TABLE` 은 진짜 세션 임시지만 dbt 모델 추상화와 안 맞아 매크로 hack 필요.

### 5-6. hourly / 백필 충돌 — run-scoped 네이밍

순차 hourly 라면 `CREATE OR REPLACE` 가 매번 덮어쓰니 충돌 없음.
**하지만 백필을 N시간 병렬로 돌리는 순간** 같은 이름의 tmp 가 서로를 덮어써서 데이터 오염:

```text
백필 03시 run ─ CREATE OR REPLACE tmp_open (03시 데이터)
백필 04시 run ─ CREATE OR REPLACE tmp_open (04시 데이터)
                                ↑
        병렬 진행 시 서로 덮어씀 → 마트가 잘못된 tmp 참조
```

**해결: `alias` 에 run 시각을 박아 물리적으로 분리.**

```python
{{ config(
    materialized='table',
    alias='tmp_open_' ~ (var('run_date') | replace('-','')) ~ '_' ~ var('run_hour'),
    hours_to_expiration=2,
) }}
```

→ 각 run 이 자기만의 테이블:
```text
tmp_open_20260615_03   ← 03시 run
tmp_open_20260615_04   ← 04시 run
tmp_open_20260615_05   ← 05시 run
```

`{{ ref('tmp_open') }}` 는 dbt 가 alias 까지 자동으로 풀어주므로 **다른 모델 SQL 은 안 바꿔도 됨** (같은 run 안에선 var 가 공유되어 alias 일치).

이 패턴에선 `hours_to_expiration` 이 단순 안전망이 아니라 **누적 방지 필수 메커니즘**. 안 걸면 백필 100시간 = 600개 tmp 가 영원히 남음.

### 5-7. lifecycle 패턴 비교

| 패턴                        | 동시 실행 안전 | 백필 안전 | 정리                  | 적합한 케이스             |
| ------------------------- | -------- | ----- | ------------------- | ------------------- |
| `CREATE OR REPLACE` 단순    | 안전 X    | 안전 X | hours_to_expiration | 순차 hourly 만 돌리면 OK  |
| `alias` 에 run 시각 박기       | 안전       | 안전    | hours_to_expiration | 백필 병렬 / retry 가능성   |
| run 별 schema 분리           | 안전       | 안전    | 데이터셋 디폴트 만료         | 격리 강하게, 콘솔 정리 깔끔    |
| BQ TEMP TABLE (스크립트)      | 안전       | 안전    | 세션 종료 시             | dbt 추상화 깨짐, 비추      |

**실무 가이드**: 백필 병렬 가능성이 있으면 처음부터 **alias 패턴**으로. 백필은 거의 항상 병렬로 돌려야 시간이 맞으므로 사실상 **표준 답**.

## 6. 읽기 비용 최적화 (마트 레이어)

저장 위치별로 사용 가능한 최적화 도구가 다르다. **6-1 ~ 6-4 는 Native 전용**, **6-5 는 External / BigLake non-Iceberg 용**.

### 6-1. 파티션·클러스터링 (Native) — WHERE 절 예측

```python
# 대시보드가 "최근 7일 + 국가별" 로 매일 조회
partition_by={'field':'event_date','data_type':'date','granularity':'day'}
cluster_by=['country_code', 'partner_id']
```

풀스캔 $6.25/TB → 파티션 1주치 + 블록 프루닝 → 수십 배 절감.

원칙: **쿼리하는 사람의 WHERE 를 예측해서 파티션/클러스터 키를 잡는다.**
모르겠으면 `INFORMATION_SCHEMA.JOBS` 로 실제 쿼리 패턴 보고 결정 (아래 7-2 참고).

### 6-2. Materialized View (Native, BQ MV)

dbt `materialized='materialized_view'`. 자주 쓰는 집계 미리 계산:

```sql
-- 원본 1TB → MV 가 10GB 만 미리 계산해서 갱신
-- BI 가 MV 만 보면 매 쿼리 100배 쌈
```

### 6-3. BI Engine (Native)

Looker Studio / Tableau 가 핫한 마트를 인메모리 캐싱. dbt 와 별개지만 마트 설계시 같이 고려.

### 6-4. Search Index (Native)

"특정 user_id 1건 찾기" 같은 needle-in-haystack 패턴이면 search index 가 풀스캔 막아줌.

### 6-5. GCS External / BigLake non-Iceberg 의 최적화는 결이 다름

핵심: **클러스터링 / MV / Search Index / BI Engine 다 못 씀**. 대신 **파일 레이아웃**과 **메타 캐싱**이 최적화 포인트.

#### (a) Hive 다단 파티션 폴더 — 파일 단위 프루닝
```text
gs://bucket/snap_date=2026-06-15/snap_hour=03/data.parquet
                              ↑                   ↑
                        파티션 키 1          파티션 키 2
```
```sql
WHERE snap_date = DATE '2026-06-15' AND snap_hour = 3
```
→ BQ 가 해당 폴더 안의 파일만 읽음. Native 의 `partition_by 1키 + granularity` 와 달리 **임의 키 조합**으로 다단 가능. case6 의 강점이 이거.

#### (b) `require_hive_partition_filter=true` — 풀스캔 안전장치
```sql
OPTIONS ( require_hive_partition_filter = true )
```
파티션 필터 없는 쿼리는 **에러로 막음** → 실수로 풀스캔하는 사고 방지. Native 엔 없는 BigLake 만의 안전장치. **운영 마트라면 무조건 켜기**.

#### (c) Parquet row group 통계 — 자동 미니 프루닝
Parquet 파일 내부 row group (보통 128MB) 단위로 min/max 통계가 박혀 있음. WHERE 범위 밖이면 row group 스킵. **Native 클러스터링의 약한 버전**.
→ EXPORT 시 파일이 정렬돼 있을수록 효과 ↑. 자주 필터되는 컬럼으로 ORDER BY 해서 EXPORT 하면 클러스터링 흉내.

#### (d) BigLake metadata cache
```sql
OPTIONS (
  max_staleness = INTERVAL 1 HOUR,
  metadata_cache_mode = 'AUTOMATIC'
)
```
**데이터 캐시 아님, 파일 리스트 캐시**. 매 쿼리마다 GCS `LIST` 호출 비용·지연 절감. 파일 수 많은 데이터 레이크일수록 효과 큼.

#### (e) 파일 크기·개수 튜닝
- 너무 작은 파일 多 → 리스팅·열기 비용 폭증
- 너무 큰 파일 1개 → 병렬 처리 못함
- **권장: 100MB ~ 1GB / 파일, Snappy 압축**
- EXPORT DATA 의 `*.parquet` 와일드카드는 BQ 가 적당히 쪼개주지만, 너무 잘게 쪼개지면 compaction 잡 별도 검토

#### (f) 마트가 무거우면 → BQ Native 로 한번 더 마트화
External/BigLake 가 분석가에게 자주 쿼리되는 패턴이면, 그 결과를 **Native 마트로 또 떨궈서** 클러스터링/MV 다 활용하는 게 답. BigLake 는 "공유·거버넌스" 레이어, Native 는 "성능 마트" 레이어로 분리.

## 7. 결정 방법

### 7-1. 의사결정 트리

```text
이 데이터를 자주(주 1회 이상) 쿼리하나?
│
├─ YES → 다른 엔진(Spark/Trino)도 같이 쓰나? 거버넌스(PII/컬럼 보안) 필요?
│        ├─ YES → BigLake
│        └─ NO  → Native (제일 싸고 빠름)
│
└─ NO  → 보존 의무로 들고만 있나?
         ├─ YES → GCS External + Coldline/Archive 클래스
         └─ NO  → 애초에 왜 들고 있는지 재검토
```

### 7-2. 데이터로 결정하기

추측 말고 실제 쿼리 로그 보고 결정:

```sql
-- 최근 30일 가장 비싸게 스캔된 테이블 = 클러스터링/파티셔닝 후보
SELECT
  referenced_tables,
  SUM(total_bytes_billed) / POW(1024, 4) AS tb_scanned,
  COUNT(*)                                AS query_count
FROM `region-us`.INFORMATION_SCHEMA.JOBS_BY_PROJECT
WHERE creation_time > TIMESTAMP_SUB(CURRENT_TIMESTAMP(), INTERVAL 30 DAY)
  AND job_type = 'QUERY'
GROUP BY referenced_tables
ORDER BY tb_scanned DESC
LIMIT 20;
```

→ "이 마트가 매일 5TB 풀스캔되네 → cluster_by 추가" 같은 결정이 숫자로 나온다.

## 8. Neptune POC 적용 — case5/case6

| | case5 (Native) | case6 (BigLake) |
|---|---|---|
| 저장 | BQ 내부 Capacitor | GCS Parquet |
| 파티션 | 1키 (`snap_at` DATETIME, hour granularity) | 2키 Hive (`snap_date`, `snap_hour`) — Neptune 원본 그대로 |
| 적재 방식 | `incremental` + `insert_overwrite` | `table` 스테이징 → post_hook(EXPORT + EXTERNAL + DROP) |
| 적정 사용처 | 핫 데이터, 분석가/BI 직접 쿼리 | 멀티 엔진 공유, 거버넌스 필요, 콜드 보존 |

실무 패턴 (하이브리드 티어링):

```text
최근 7~30일   →  Native (case5)         자주 쿼리, 빠르고 쌈
N일 이후      →  GCS Parquet 로 EXPORT  Native 파티션 삭제
보존 의무 구간 →  GCS lifecycle 자동 이동 (Standard → Coldline → Archive)
```

한 가지로 통일하는 것보다 **레이어별 + 시간별 티어링**이 진짜 비용 절약 포인트.

case3 에는 5장의 intermediate lifecycle 패턴이 그대로 적용됨 — `tmp_open` 만 `table` + run-scoped alias + `hours_to_expiration=2` 로, 나머지 tmp 는 ephemeral 유지.

## 10. 한 줄 요약

> dbt 의 강점은 **모델 단위로 저장·운영 정책을 코드로 표현**할 수 있다는 점.
> 모델마다 "다운스트림 누구·얼마나 자주" 를 먼저 정하고, materialization 과 저장 위치(Native / GCS External / BigLake)를 매칭한다.
> intermediate 는 ephemeral 디폴트지만 **여러 번 ref 되는 무거운 단계는 `table` + `hours_to_expiration` + (백필 병렬 시) run-scoped `alias`** 패턴으로.
> 데이터 한 종류도 시간이 지나면 핫 → 콜드로 변하므로, **티어링과 lifecycle 정책**까지 묶어서 설계하는 게 진짜 비용 최적화.
