# 애슬론 — 플랫폼 재구현 의사결정

## 🍽️ 한 줄 요약 (식당 비유)

> **athlon은 "주방 일과표 관리"에서 "메뉴판 관리"로 진화한다.**
> dbt + BigQuery + Airflow + DataHub 시대에 athlon이 통합 관리하는 단위를 **"task(작업)"에서 "asset(데이터 자산)"으로 옮긴다.**

## 🎯 풀어야 할 문제 (다시 정리)

GCP 이관 + dbt 도입이 확정된 상태에서, **athlon 플랫폼을 어떻게 재구현할까?**

해결해야 할 것:

1. **dbt를 지원** — SQL 변환의 대부분이 dbt로 감
2. **UI에서 잘 셋팅** — DE가 GUI 또는 git workflow로 데이터 정의·편집
3. **UI 셋팅 → DBT Sync + Git** — 정의가 git에 형상관리되고 dbt가 받음
4. **DataHub 리니지 관리** — 수집부터 소비까지 통합 lineage
5. **수집 → ETL 연결** — dbt 만으론 "수집(extract) → 변환(transform)" 의 lineage edge 가 끊김. athlon이 이걸 메워야 함

상세: [[3_dbt 능력 경계와 영역 분담]]

## 🔀 두 갈래 결정 (메인 선택)

이게 팀 논의의 핵심:

### 안 1. **현 모델 진화** (workflow / actions / action_dependencies 유지 + 확장)

기존 데이터 모델 그대로 두고 새 기능만 더함:

- `actions_meta` 에 `DBT_MODEL` type 추가
- `actions_meta` 에 1:N 매핑 지원 (dbt 모델 N개 묶기)
- ActionGroup 신설 (action_dependencies 와 공존)
- 기존 `airflow.py` factory 패턴 그대로

**장점**:
- 기존 자산 활용, 점진 확장
- DE 학습 곡선 낮음
- 짧은 구현 기간

**단점**:
- workflow / actions 의 경직성이 그대로 (operator_class enum, flat dependency)
- 수집-ETL lineage 통합이 우격다짐
- dbt 정도의 자유도 못 줌
- 장기적으로 또 재설계 필요할 가능성

### 안 2. **Asset-Centric 신설계** ⭐

워크플로/액션 모델 폐기하고 데이터 자산 중심으로 재설계:

- 4개 엔티티: **Asset / Producer / AssetGroup / Profile**
- Producer 5 종류: `DBT_MODEL` / `EXTRACT` / `EXPORT` / `SENSOR` / `CUSTOM`
- UI는 YAML 편집 → CI에서 Python DAG 자동 생성
- Airflow 3 Asset 개념과 native 매핑

상세: [[4_Asset-Centric 아키텍처 안]]

**장점**:
- dbt / Airflow 3 / DataHub 와 자연스럽게 정합
- 수집-ETL lineage 자동 (Airflow Asset URI 그대로 DataHub)
- 새 producer 추가가 단순 (plugin)
- 환경 분리 (Profile) native
- 미래 정합성 (업계 방향)

**단점**:
- 백엔드 + UI 새로 작성 (1년 ~ 1.5년 추정)
- DE 사고 전환 (task → asset)
- 마이그레이션 부담 (manual actions ~3,952개)
- 인력 부담

### 안 3. (참고) 하이브리드

workflow 유지하면서 일부 Asset abstraction 도입. 보수적 절충안이지만 두 모델 동시 운영 부담 큼. 일반적으로 권장 안 함.

## 💡 추천 (Claudian 관점)

**안 2 (Asset-Centric) 권장.** 이유:

1. **dbt + Airflow 3 + DataHub 모두 같은 방향으로 진화 중** — 우리가 거기 맞추는 게 자연스러움
2. **본인이 짚은 "workflow/actions 경직성"** 의 근본 해결책은 이 방향
3. **수집-ETL lineage 부재** (dbt 만으론 안 됨) 는 Asset URN 일관성으로 해결
4. 기존 모델 진화로 가도 결국 비슷한 곳에 도달할 가능성 높음 — 시간 손해

다만 **사람 비용** 이 큼. 이게 팀 논의의 진짜 쟁점.

| Airflow 3 Asset 활용 | 부분적 | 완전 |
| DataHub 통합 | 별도 push 로직 | 자동 stitching |

## 🍴 4가지 개념 (Asset-Centric 채택 시)

| 개념 | 식당 비유 | 진짜 의미 |
|---|---|---|
| **Asset** | 음식 | 데이터 한 덩어리 (`bigquery://...`, `gs://...`) |
| **Producer** | 레시피 | Asset 만드는 방법 (5종류) |
| **AssetGroup** | 한 끼 메뉴 묶음 | 같이 만들고 백필하는 단위 |
| **Profile** | 본점/분점 환경 | dev / prod 환경 변수 |

## 🔄 흐름 (Asset-Centric 시)

```
[UI 또는 git] YAML 작성·편집
        ↓
[CI] athlon-compiler 실행
   ├─ YAML → 의존성 그래프
   ├─ Profile 변수 치환
   ├─ dbt manifest 흡수
   └─ Python DAG 생성
        ↓
[GCS] Composer DAG 버킷 push
        ↓
[Composer / Airflow 3] DAG 실행
   ├─ inlets/outlets 로 lineage 자동
   └─ schedule=[Asset] 으로 inter-DAG 트리거
        ↓
[BQ / GCS / 외부 시스템] 실제 데이터 생성
        ↓
[DataHub] lineage 자동 형성 (Airflow + dbt plugin 자동 push)
```
