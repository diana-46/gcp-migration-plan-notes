## 1. 저장소 간 push 순서 ⚠

### 원칙

**dbt 저장소 (storydata-dbt) 를 먼저 push 하고, 그 다음 DAG 저장소 (storydata-airflow-dags) 를 push.**

### 왜

cosmos 는 `LoadMode.DBT_MANIFEST` 로 Composer 워커에 배포된
`/home/airflow/gcs/data/dbt/target/manifest.json` 을 읽어 dbt 모델 그래프를 Airflow task 로
렌더한다. **DAG 파일 안 `select=["+new_model"]` 이 참조하는 모델이 manifest 에 존재해야
파싱 성공**.

역순 (airflow-dags 먼저 push) 이면:

1. Airflow-dags CI 가 새 DAG 을 Composer 로 sync
2. 스케줄러가 파싱 시도
3. cosmos 가 manifest 에서 `new_model` 못 찾음 → "model not found" 에러
4. **DAG import error 배지** 가 UI 에 뜸 (dbt push 완료 전까지 지속)

역순 자체는 자동 복구되지만 (dbt push 시점에 manifest 갱신되면서 parse 성공), UI 노이즈와
잠재적 스케줄러 리셋 이슈를 피하려면 순서 지키는 게 안전.

### 표준 순서

```
1. storydata-dbt 에서 새/변경 모델 커밋 → PR merge
2. GitHub Actions 실행 대기:
   - dbt parse → target/manifest.json 재생성
   - gsutil rsync → Composer 의 gs://<bucket>/data/dbt/ 로 배포 (~1-2분)
3. storydata-airflow-dags 에서 DAG 변경 커밋 (cosmos select 에 새 모델 포함) → PR merge
4. Actions 로 DAG sync → Airflow 스케줄러 pickup → cosmos 가 갱신된 manifest 로 렌더
```

### 예외 케이스

- **모델 코드만 변경 (신규 없음)**: dbt push 만 하면 됨. DAG 변경 없으니 airflow-dags 안
  건드림.
- **DAG 코드만 변경 (모델 참조 그대로)**: airflow-dags 만 push. Manifest 는 그대로.
- **모델 rename**: dbt 에서 새 이름으로 만들고 옛 이름 지운 뒤 push. 그 다음 DAG 에서
  참조 갱신하고 push. **역순은 심각한 실패 발생** — 옛 이름 참조하는 DAG 이 새 manifest
  에서 안 보임.

## 2. Composer PyPI 패키지 관리 함정

### 2-1. `--update-pypi-package` vs `--update-pypi-packages-from-file`

두 명령의 세만틱이 다름:

- `--update-pypi-package X==Y` : **개별 upsert**. 기존 목록에 X 추가/갱신, 나머지 유지.
- `--update-pypi-packages-from-file <file>` : **전체 replace**. 파일에 없는 기존 패키지 제거됨.

`from-file` 쓸 땐 유지해야 할 모든 pin (프로젝트팀 provider 등) 을 파일에 함께 넣어야 함.

### 2-2. `apache-beam` backtracking 지옥

Composer 3 의 `apache-airflow-core==3.1.7+composer` variant 가 `providers-apache-beam` 을
hard dep 로 갖고 있어, 새 패키지 install 시 pip resolver 가 apache-beam (transitive deps
수십 개) 을 재검증. 30분 timeout 이 흔함.

**해결책**: raw pin 을 requirements 파일에 넣어 resolver 를 짧게 만든다.

```
apache-beam==2.74.0
asyncssh==2.20.0
astronomer-cosmos==1.10.1
dbt-core==1.11.12
dbt-bigquery==1.11.3
```

Composer 는 `--update-pypi-packages-from-file` 에서 `--constraint`, `--extra-index-url`
같은 pip directive 는 **CLI validation 에서 거부**한다. 순수 `pkg==ver` 라인만 사용
가능.

### 2-3. `PIP_NO_DEPS` 는 함정

Backtracking 회피용으로 `PIP_NO_DEPS=1` env var 를 세팅하면 pip 이 신규 패키지의 deps 를
resolve 하지 않음. 결과:
- 새로 install 한 `dbt-bigquery` 는 있는데, 필수 dep `dbt-core` 는 옛 버전 그대로
- click 등 transitive 호환성 깨짐
- dbt 실행 시 `ImportError: cannot import name '_OptionParser' from 'click.parser'` 등
  런타임 크래시

**교훈**: `PIP_NO_DEPS` 는 install 은 빠르게 하지만 환경을 망침. Raw pin + 정상 dep
resolve 조합이 정답.

### 2-4. 버전 지정 스타일: `>=` vs `==`

Composer 의 pypi 목록은 declared 상태와 실제 install 상태가 다를 수 있음.

`>=X` 로 declare 하면 pip 이 "이미 만족" 판단해 upgrade 안 하는 경우 발생. 특히 base
image 에 미리 들어있던 옛 버전이 그대로 유지됨. **exact pin (`==X.Y.Z`) 이 안전**.

```
✅ dbt-core==1.11.12
❌ dbt-core>=1.11    # 옛 dbt-core 그대로일 수 있음
```

### 2-5. Composer 업데이트 중 DAG 실행 금지

Composer 가 `UPDATING` 상태일 때 워커가 재빌드되면서 python env 가 불안정. 그 사이 실행
되는 태스크는 transitional state (일부 파일 옛것, 일부 새것) 를 볼 수 있음.

**규칙**: `gcloud composer environments describe --format="value(state)"` 로 `RUNNING`
확인 후 DAG trigger.

## 3. Provider 릴리즈와 DAG 배포 관계

### 3-1. Provider (kakaoent-dataplatform) 버전 bump 흐름

Provider 는 별도 저장소 (`dp-airflow-provider`) 로 관리하며 GAR
(`asia-northeast3-python.pkg.dev/dev-dp-project-354904/dev-dp-python-registry`) 에
publish. 소비 팀 (`storydata-airflow-dags`) 은 `requirements.txt` 로 특정 버전 pin.

새 버전이 나왔을 때:
1. `dp-airflow-provider` 에서 tag 생성 → GitHub Release publish
2. Actions 가 wheel build + GAR upload
3. `storydata-airflow-dags` 에서 `requirements.txt` 의 provider 버전 bump → PR merge
4. **Composer 환경에 `--update-pypi-package` 로 provider 설치** ⚠ 수동

현재 CI 에는 `requirements.txt` 변경 → Composer pypi update 자동화가 없음. 이관 초기엔
수동 관리로 유지 (실수 여지 방지).

### 3-2. Provider install 자체는 backtracking 안 함

우리 provider (`apache-airflow-providers-kakaoent-dataplatform`) 는 `dependencies=[]`
(runtime deps 없음). 그래서 install 시 resolver 부담 zero. Composer 업데이트에서
provider 만 갱신하는 건 몇 분 안에 끝남.

Airflow 표준 provider 컨벤션은 `apache-airflow>=X.Y` 를 명시하지만, 사내 provider 는
Composer 만 target 이라 이 명시조차 뺐다 (backtracking 방지).

## 4. DataHub emit CI 제약

### 4-1. GitHub-hosted runner 는 사내 DataHub GMS 접근 불가

`https://datahub-gms-gcp-dev.kakaodev.io` 는 사내 네트워크. GitHub Actions 의 hosted
runner (Microsoft Azure) 에서 접근 불가. `dbt parse` 후 `datahub ingest` 스텝은 CI 에서
network fail.

### 4-2. 현재 대응

`storydata-dbt/.github/workflows/deploy.yml` 의 datahub emit 스텝은 **주석 처리**.
데이터플랫폼팀이 로컬에서 수동 emit:

```bash
cd ~/PycharmProjects/storydata-dbt
source .venv/bin/activate
export DATAHUB_TOKEN=<PAT>
datahub ingest -c /tmp/datahub-recipe.yml
```

Recipe (요약):
```yaml
source:
  type: dbt
  config:
    manifest_path: ./target/manifest.json
    target_platform: bigquery
    target_platform_instance: dev-dp-project-354904
sink:
  type: datahub-rest
  config:
    server: https://datahub-gms-gcp-dev.kakaodev.io
    token: ${DATAHUB_TOKEN}
```

### 4-3. Self-hosted runner 세팅 완료 시 활성화

Self-hosted runner 가 사내망에서 실행되면 DataHub GMS 접근 가능. 그때:
1. GH Secret `DATAHUB_TOKEN` 유효한지 확인
2. `deploy.yml` 의 datahub emit 스텝 주석 해제
3. Job 의 `runs-on:` 을 `[self-hosted, <label>]` 로 변경

## 5. DataHub emit 은 CI 에서 하고 DAG task 로 안 넣는다

초기 설계에선 hourly DAG 의 마지막 task 로 `datahub_emit` 을 넣었었지만 아래 이유로 CI
로 이관:

- dbt 모델 정의는 **배포 시점에만** 변경됨
- Runtime (hourly DAG run) 마다 identical metadata 를 반복 emit 하는 건 낭비
- Composer 워커에 `acryl-datahub` 를 install 할 필요 없어짐 (deps 부담 감소)
- 관심사 분리: dbt CI 는 dbt lineage 갱신 담당, Airflow DAG 는 데이터 파이프라인 담당

DAG 문서화에도 이 결정을 명시해두면 팀원 혼란 방지.

## 6. 시크릿 / 인증 관리

### 6-1. GitHub Secret 명명 규칙

- `GCP_SA_KEY_DEV` : dev 환경 SA JSON (Composer 배포 / GAR upload 용)
- `GCP_SA_KEY_PROD` : prod 환경 SA JSON (예정, prod 환경 구축 후)
- `DATAHUB_TOKEN` : DataHub PAT (dbt lineage emit 용)

### 6-2. 로컬 gcloud 인증 만료

`gcloud auth application-default login` 은 만료됨. Composer update 명령이 조용히 실패하고
"If you have already logged in with a different account..." 안내만 출력하는 경우가 있어
헷갈리기 쉽다. Update 명령 전:

```bash
gcloud auth application-default print-access-token > /dev/null && echo "ADC OK" || echo "ADC 재로그인 필요"
```

## 7. 요약 체크리스트

배포 전 확인:

- [ ] Composer state 가 `RUNNING` (`UPDATING` 아님)
- [ ] `gcloud auth` 및 `application-default` 토큰 유효
- [ ] dbt 모델 신규/변경이면 storydata-dbt 를 먼저 push
- [ ] PyPI 업데이트 시 raw pin (`==X.Y.Z`) 사용, apache-beam/asyncssh 등 무거운 dep 도 pin
- [ ] `PIP_NO_DEPS`, `PIP_USE_DEPRECATED` env var 남아있지 않은지 확인
- [ ] Provider 버전 bump 후 Composer pypi 갱신은 별도 수동 (`--update-pypi-package`)
- [ ] DataHub emit 은 시연 후 self-hosted runner 세팅 완료 시 CI 로 이관

배포 후 확인:

- [ ] Airflow UI 에 DAG import error 없음
- [ ] cosmos 가 렌더한 dbt task 목록이 예상과 일치
- [ ] BQ 결과 데이터셋에 실제 데이터 write 되는지 (수동 trigger 로 확인)
- [ ] DataHub 에서 새 모델 lineage 검색 가능
