# 5. 계층 분리 원칙 — Cosmos 는 물리 lineage, Stamp 는 비즈니스 readiness

> [[4_해결_패턴]] 의 stamp task 를 왜 **Cosmos 안에 넣지 않고 뒤에 붙이는지** 의 아키텍처적 근거.

## 핵심 명제

> **Cosmos 자동 outlet 과 stamp task outlet 은 서로 다른 층위의 사실을 표현하는 별개의 이벤트 스트림이다.** 하나를 다른 하나로 대체하는 게 아니라 **공존시키고 소비자를 분리**한다.

## 두 층위의 이벤트

### Cosmos 자동 outlet 이 의미하는 것

> "이 dbt 모델이 정상적으로 SQL 을 실행해서 target relation 에 write 했다"

- **사실의 종류**: 물리적 fact
- **시점**: dbt run 성공 직후
- **조건**: 무조건 (성공 = emit)
- **URI**: 물리 테이블 좌표 (`bigquery://project.dataset.table`)
- **소유권**: Cosmos 라이브러리

### Stamp task outlet 이 의미하는 것

> "이 mart 의 논리적 readiness — dbt + Kafka export + signal + QC 까지 통과했고, 지금 KST 23시라서 EOD downstream 을 깨워야 하는 파티션이다"

- **사실의 종류**: 논리적 / 비즈니스 fact
- **시점**: 전체 파이프라인 chain 완료 후
- **조건**: 비즈니스 조건 (KST 시간대, run_type, QC 결과 등)
- **URI**: 팀이 명시한 논리 좌표 (`story://berriz/bizberry/summary_ready`) 또는 AssetAlias
- **소유권**: 팀

## 비교

| 축 | Cosmos outlet | Stamp task outlet |
|---|---|---|
| 발신자 | Cosmos 가 dbt run 후 자동 | 팀 코드가 명시적으로 |
| 발신 조건 | 무조건 (task 성공) | 비즈니스 조건 |
| Payload | 대체로 빈 dict | 팀이 명시한 필드 |
| URI | 물리 테이블 좌표 | 논리적 좌표 / alias |
| 시점 | dbt SQL 완료 시점 | 파이프라인 전체 완료 시점 |
| 목적 | Lineage (누가 이 테이블 생성?) | Downstream 트리거 (누가 준비됐음을 알림?) |
| 주 소비자 | 카탈로그 / lineage 툴 (DataHub 등) | Downstream DAG |
| 소유권 | Cosmos 라이브러리 | 팀 |

## 왜 분리해야 하나

### 1. dbt 는 이벤트 브로커가 아니다

dbt 의 관심사는 "SQL 을 실행해 테이블을 만든다". "언제 다른 DAG 을 깨워야 하는가" 같은 판단은 dbt 의 도메인이 아니다.

Cosmos 가 outlet 을 자동 붙여준 건 **lineage 편의** 목적이지, **downstream 트리거 로직** 을 담는 자리가 아니다. 여기에 조건부 emit / partition 정보 / alias 를 얹으려 하면 **관심사가 뒤섞임**.

### 2. Cosmos 의 outlet 은 팀이 수정할 자리가 아니다

Cosmos 의 outlet emission 은 dbt run operator 안에 baked in 되어 있다. 수정 방법:

- Subclass → 침습적, cosmos 마이너 업그레이드마다 깨질 위험
- Monkey-patch → 논의 대상 아님
- Callback → 있어도 outlet 조작 시점 지남

즉 **팀 코드 레벨에서 clean 하게 조작할 수 없음**. 억지로 하려면 라이브러리를 뜯게 됨.

### 3. "물리 완료" 와 "논리 준비" 는 다를 수 있다

**예시**:
- dbt run 은 성공했지만 뒤이은 QC 검증 실패 → 물리적으로는 테이블에 write 됐지만 downstream 이 그 위에 돌면 잘못된 결과
- Cosmos outlet 은 이미 emit 됨 → downstream 트리거됨 → 사고

Stamp task 를 QC 뒤에 두면 **QC 통과 시점에만 논리적 readiness 를 알림**. 두 사건을 시간·조건으로 분리.

### 4. 팀이 소유권을 가져야 계약 진화 가능

Downstream 이 요구하는 payload 스키마는 시간이 지나며 바뀔 수 있다:
- 처음: `partition_kst` 만
- 나중: `partition_kst`, `data_freshness_check`, `row_count` 추가
- 더 나중: 팀별 커스텀 필드

이 진화가 **팀 코드 안에서** 이뤄져야 함. Cosmos 라이브러리 업데이트에 묶이면 진화 불가능.

## Factory helper 로 배선 편의성 회복

계층 분리를 원칙으로 두되, 매 mart 마다 손으로 배선하기 귀찮으니 helper 로 pack:

```python
# dags/storydata/lib/mart_pipeline.py

def dbt_mart_with_stamp(
    *,
    group_id: str,
    dbt_model: str,
    stamp_task_id: str,
    aliases: list[AssetAlias],
    payload_builder: Callable[[dict], dict],
    emit_conditions: dict[AssetAlias, Callable[[dict], bool]] | None = None,
    skip_on_run_type: list[str] | None = None,
):
    """dbt task group + stamp task 를 함께 배선."""
    dbt = make_dbt_task_group(group_id=group_id, model_name=dbt_model)
    
    @task(task_id=stamp_task_id, outlets=list(aliases))
    def _stamp(**ctx):
        if skip_on_run_type and ctx["dag_run"].run_type in skip_on_run_type:
            raise AirflowSkipException(f"run_type={ctx['dag_run'].run_type} → skip")
        
        extra = payload_builder(ctx)
        partition_key = extra.get("partition_kst", "")
        concrete = Asset(f"story://berriz/bizberry/{group_id}/{partition_key}")
        
        for alias in aliases:
            cond = (emit_conditions or {}).get(alias)
            if cond is None or cond(ctx):
                ctx["outlet_events"][alias].add(concrete, extra=extra)
    
    return dbt, _stamp()
```

DAG 안에서:

```python
dbt_summary, stamp_summary = dbt_mart_with_stamp(
    group_id="dbt_contents_summary",
    dbt_model="bizberry_community_contents_summary",
    stamp_task_id="stamp_summary_ready",
    aliases=[SUMMARY_HOURLY, SUMMARY_EOD],
    payload_builder=bizberry_payload,
    emit_conditions={
        SUMMARY_EOD: lambda c: c["data_interval_start"].in_timezone("Asia/Seoul").hour == 23,
    },
    skip_on_run_type=["backfill"],
)

dbt_summary >> export_to_kafka >> signal >> stamp_summary
```

**얻는 것**:
- Cosmos 는 자기 outlet 을 계속 emit (lineage 유지)
- Stamp 는 별도 outlet 으로 비즈니스 이벤트 emit
- 두 emission 의 소비자가 자연스럽게 분리됨
- Factory 가 배선 반복 흡수 → DAG 파일은 config 만 남음

## Cosmos 자동 outlet 을 꺼야 할까?

### 켜둘 이유

- **Data lineage tool 이 의존** (Marquez, DataHub, Airflow UI lineage)
- **팀 밖에서 우리 mart 를 참조** 할 stable identity
- **DataHub URN 과의 자동 stitching** — [[../스케줄러/9_Airflow Asset과 Dataset]] 에서 언급된 표준 URI 스키마 활용

### 끌 이유

- Downstream 이 실수로 cosmos URI 를 subscribe 하는 걸 원천 차단
- Metadata DB 크기 감소

### 팀 컨벤션 제안

**켜두되, 팀 내부적으로 "Cosmos URI 는 lineage 전용, subscription 은 stamp/alias 만" 이라는 규약 정하기**.

- Cosmos URI = 물리 자산 좌표. DataHub 카탈로그에서 조회
- Stamp URI = 비즈니스 이벤트. Downstream DAG 이 subscribe
- 문서에 명시, 코드 리뷰에서 체크

## 안티패턴

### AP-1. Cosmos outlet 을 downstream 스케줄에 직접 사용

```python
# 안티패턴
with DAG(
    ...,
    schedule=[Asset("bigquery://project.dataset.table_integration")],  # Cosmos URI
) as dag:
    ...
```

**왜 나쁜가**:
- Payload 없음 (Cosmos 는 stamp 안 함)
- 조건부 emit 불가 (Cosmos 는 무조건 emit)
- 물리 좌표 변경 시 downstream 도 함께 수정 필요
- 환경별 (dev/prod) 접미사 처리가 URI 하드코딩

**대신**: Stamp task 의 논리 URI 나 alias 를 subscribe.

### AP-2. Cosmos operator 를 subclass 해서 stamp 로직 삽입

```python
# 안티패턴
class MyDbtRunOperator(DbtRunOperator):
    def execute(self, context):
        result = super().execute(context)
        # 여기에 stamp 로직 삽입
        ...
```

**왜 나쁜가**:
- Cosmos internal API 의존 → 마이너 버전 업그레이드에서 깨짐
- 관심사 뒤섞임 (dbt 실행 + 이벤트 발신)
- 테스트 어려움
- 재사용성 낮음

**대신**: Cosmos 는 그대로, stamp 는 별도 task 로.

### AP-3. Stamp task 없이 downstream 에서 매번 run_id 파싱

```python
# 안티패턴
@task
def process(**context):
    for ev in context["triggering_asset_events"]...:
        run_id = ev.source_run_id
        if run_id.startswith("scheduled__"):
            iso = run_id.split("__", 1)[1]
            logical_date = datetime.fromisoformat(iso)
        # backfill/manual 케이스 handling...
```

**왜 나쁜가**:
- Airflow 마이너 버전 format 변경 시 깨짐
- Backfill/manual/scheduled 별 분기 필요
- Consumer 마다 이 로직 반복
- Producer 가 뭘 담아 보내는지 계약이 코드에 없음

**대신**: Producer 에 stamp task 를 두고 `extra` 로 명시적 전달.

## 원칙 요약

1. **Cosmos 는 dbt 만 한다.** 이벤트 계약은 팀 소유.
2. **두 outlet 을 공존시킨다.** 물리 lineage 와 비즈니스 readiness 는 다른 소비자를 가진 다른 이벤트.
3. **Factory 로 배선 편의성 회복.** 두 outlet 을 매번 손으로 붙이는 부담은 helper 로 흡수.
4. **팀 컨벤션으로 URI 역할 분리 명시.** Cosmos URI 는 lineage, stamp URI 는 subscription.
