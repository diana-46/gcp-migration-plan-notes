## 0. 핵심 발견 (TL;DR)

### 한달간 운영 숫자

### 🔑 가장 중요한 인사이트 — "정기 스케줄 잡이 주류"

**190개 코호트가 평균 36회씩 실행** = 대부분이 **정기 배치 스케줄**.
- ad-hoc / 마케터 트리거가 아니라 자동 스케줄러가 시간대 균일하게 호출
- → idle timeout 절약 절대 불가능
- → 24h 상주 + 다운사이즈가 답

### 이전 가정 3개 폐기

1. ❌ "userlake-worker 는 업무 시간에 집중" → ✅ **시간대별 거의 균일** (정기 스케줄 때문)
2. ❌ "batch 모드도 옵션" → ✅ **Gate/Sync 평균 4~10초 < cold start 30~60초, Interactive Session 만**
3. ❌ "DCU 126 적정 사이즈" → ✅ **75% 코호트가 10만 행 이하, 다운사이즈 가능 (DCU 21~30)**

### 추가 발견

- 이벤트/캠페인 burst 시 평소의 **2~3배** (6/8~6/13 burst week)
- 재시도 거의 없음 (FAILED 0.05%, max attempt 5)
- STOPPED 8~10% (timeout / cancel — 추가 분석 필요)
- 코호트 1개 빌드 = 평균 ~7 stage, Spark 처리 시간 ~28초
- ⚠ **Queue Wait 병목 발견** (§ 3-1) — 평균 큐 대기 **2시간** vs 실행 **7.25초** = 1000:1. 병목이 executor 가 아닌 상위 스케줄링 (Pub/Sub 이관 시 개선 여지)

### Over-spec 실측 → 다운사이즈 결정

Pod uptime **409일** + Grafana 30일 실측 + Executor JSON 409일 누적 데이터 기반으로 **72 vCPU → 24 vCPU (-67%)** 다운사이즈 결정.

→ 실측 근거 · Spark 설정 변경안 · 노드 구성 · PoC 계획 상세: [[13_Spark Connect 다운사이즈 결정 (실측 기반)]]

## 3-1. Queue Wait 병목 발견 (2026-07-02)

`updated_dt - created_dt` (전체 lifetime) vs `result.executionSeconds` (실 실행 시간) 비교로 **큐 대기 시간** 계산.

**대상**: GATE + SYNC COMPLETED, 30일, 27,641개

| 지표 | 값 |
|---|---|
| **평균 큐 대기** | **7,280초 = ~2시간** |
| **최대 큐 대기** | **248,401초 = ~69시간 (~3일!)** |
| 평균 실행 시간 | 7.25초 |
| **큐 대기 : 실행 비율** | **1000 : 1** |

**Executor 활용도**:

```
27,641 stages × 7.25s = 55.67h (30일 총 실행)
55.67h / (720h × 8 executor) = 0.97% executor 활용
```

→ **Executor 는 99% idle**. 그런데도 stage 는 큐에서 2시간씩 대기.

**병목은 executor 가 아니라 상위 스케줄링**:

- RabbitMQ consumer, DAG dependency, worker polling 등 후보
- **Spark Connect executor 개수와 무관**
- executor 늘려도 큐 대기 안 줄어듦
- executor 줄여도 큐 대기 안 늘어남

**GCP 이관 시 개선 여지**:

1. **RabbitMQ → Pub/Sub 이관 시 병렬 consumer** — [[5_Pub-Sub 이관 (consumer 패키지 재작성)]] 에서 consumer 처리량 증가 검토
2. **worker polling / batch size 조정** — 대량 처리 시 큐 대기 감소 여지
3. **DAG 스케줄러 검토** — Cloud Composer 등 활용 가능성

**함의**:

- 다운사이즈 결정 (executor 8→2) → 안전 (executor 이미 99% idle, § 13 참고)
- 큐 대기 문제는 **별도 개선 프로젝트**로 분리 필요
