# 6. Neptune → dbt + BigQuery + Composer 마이그레이션 플랜

> athlon Neptune 의 ETL 들을 dbt + BigQuery + Cloud Composer 환경으로 이관하는 실행 플랜.
> 관련: [[5_Neptune SQL 변환의 dbt-BigQuery 대체 검토]] (PoC 결과), [[스케줄러/15_관리 레포 인벤토리]] (운영 모델)

## 0. 요약

- **목표**: athlon Neptune 의 ETL 들을 dbt + BigQuery + Composer 로 이관, 운영을 DE 자율 git-based 모델로 전환
- **PoC 검증 완료**: 5 케이스 + 백필 + 스키마 변경 시나리오 ([[5_Neptune SQL 변환의 dbt-BigQuery 대체 검토]])
- **점진적 4 Phase**: Phase 0 (준비) → 1 (얼리어답터) → 2 (확대) → 3 (Neptune deprecation)
- **안전 장치**: 옵트인 + dual-run + git revert + BQ time travel

## 2. 목표 / 성공 기준

### 2-1. 정량 목표

| 지표 | 현재 | 목표 (Phase 3 종료 시) |
|---|---|---|
| dbt 로 옮긴 ETL 수 | 0 | 525 (100%) |

### 2-2. 정성 목표

- DE 가 자기 도메인 ETL 을 git PR 로 직접 관리
- 플랫폼팀이 게이트키퍼에서 enabler 로 전환
- dbt + Airflow 업계 표준 도구 정착

### 2-3. 비범위 (이번 마이그레이션 안 함)

- ETL 의 비즈니스 로직 변경 (SQL 결과 동일 보장)
- Neptune 의 task template 중 dbt 영역 밖 (`BIGQUERY_SENSOR`, `LOUPE_QUERY_TO_KAFKA` 등 외부 연동) — Python orchestrator 로 별도 처리 ([[5_Neptune SQL 변환의 dbt-BigQuery 대체 검토]])
- 데이터 모델 재설계 (마이그레이션 1:1 우선, 정리는 이관 후)

## 3. 마이그레이션 우선순위

### 3-1. 분류 기준

복잡도 ↑ + 영향 ↑ 일수록 후순위. PoC 검증된 패턴부터.

| 분류 | 특징 | 비고 |
|---|---|---|
| **Tier 1 (단순)** | PLAIN + no_partition + PARQUET | 가장 단순. baseline |
| **Tier 2 (운영 대표)** | PLAIN + daily partition + PARQUET | 389개. 운영 대다수 |
| **Tier 3 (시간별)** | PLAIN + hourly partition + PARQUET | 타임존 변환 검증 필요 |
| **Tier 4 (YAML)** | YAML + daily partition + PARQUET | 다중 temp + ephemeral |
| **Tier 5 (AVRO)** | PLAIN + daily + AVRO | 다운스트림 컨슈머 호환성 검증 필요 |
| **Tier 6 (복잡 의존성)** | 다른 ETL 의 출력에 강하게 의존 | upstream/downstream 동시 이전 권장 |

### 3-2. Tier 별 건수 / Phase 매핑

| Tier | 건수 | Phase |
|---|---|---|
| 1 | 42 | Phase 1 일부 + Phase 2 초반 |
| 2 | 389 | Phase 2 (대다수) |
| 3 | ~15 | Phase 2 후반 (hourly 타임존 검증 후) |
| 4 | 82 | Phase 2 후반 ~ Phase 3 |
| 5 | 12 | Phase 3 (Avro 컨슈머 합의 후) |
| 6 | (의존성 분석 후 산정) | Phase 3 |

### 3-3. 우선순위 측정 항목 (Phase 0 에서 수행)

각 ETL 에 대해:
- **사용 빈도**: 다운스트림 consumer 수 (DataHub lineage 활용)
- **변경 빈도**: 최근 6개월 수정 횟수 (athlon DB 로그)
- **소유 팀**: DE 도메인 매핑
- **복잡도**: 위 Tier 분류
- **의존성**: upstream / downstream ETL 목록

→ Tier × 사용빈도 × 팀 으로 마이그레이션 큐 정렬.

## 4. Phase 별 활동

### Phase 0 — 준비 (1개월 예상)

**목표**: 인프라 + 도구 + Phase 1 시작 조건 충족

| 활동 | 담당 | 산출물 |
|---|---|---|
| Composer prod 환경 셋업 | 플랫폼팀 | `prod-airflow3` (또는 동등) |
| dbt 1.9.x 표준화 (Composer dbt 버전과 lock) | 플랫폼팀 | venv / CI 설정 |

| ETL 인벤토리 + 우선순위 매기기 | 플랫폼팀 + DE 대표 | `inventory.csv` (Tier / 팀 / 빈도) |
| 현재 lead time / 백필 빈도 측정 | 플랫폼팀 | baseline 지표 |

**Gate (Phase 1 진입 조건)**:
- [ ] Composer prod 환경 동작
- [ ] CI/CD 자동 배포 성공
- [ ] 인벤토리 + 우선순위 합의
- [ ] 워크샵 1회 이상 진행
- [ ] 얼리어답터 DE 팀 확정

### Phase 1 — 얼리어답터 (1~2개월)

**목표**: 1~2 DE 팀이 자기 도메인 ETL 1~2개를 dbt 로 이관, dual-run 으로 정합성 검증, 운영 SOP 확정

| 활동 | 담당 | 산출물 |
|---|---|---|
| 마이그레이션 대상 ETL 1~2개 선정 (Tier 1~2) | DE + 플랫폼팀 | 합의 |
| dbt 모델 + DAG 작성 (pair) | DE (lead) + 플랫폼팀 (pair) | PR |
| Neptune 과 dbt dual-run 1~2주 | DE | 결과 diff 자동화 |
| 운영 SOP 작성 (장애 대응 / 백필 / 스키마 변경) | DE + 플랫폼팀 | Runbook |
| 발견 문제 → mitigations 보강 | 플랫폼팀 | 노트 / helper 업데이트 |
| Neptune 측 deprecation 시점 합의 | DE + 매니저 | 일정 (Phase 3 진입 후) |

**Gate (Phase 2 진입 조건)**:
- [ ] dual-run 결과 정합성 OK (row count, partition, 컬럼)
- [ ] DE 가 단독으로 ETL 1회 수정 + 배포 성공
- [ ] DE 가 단독으로 백필 1회 수행 성공
- [ ] 운영 SOP 문서화

### Phase 2 — 점진 확대 (3~4개월)

**목표**: 단순 Tier (1~2) 의 다수를 마이그레이션, Tier 3~4 검증 시작

| 활동 | 담당 | 비고 |
|---|---|---|
| DE 팀별 onboarding 워크샵 | 플랫폼팀 → DE | 팀당 1~2 세션 |
| 마이그레이션 sprint (팀별) | DE | 우선순위 큐 따라 |
| 마이그레이션 자동화 도구 개발 | 플랫폼팀 | Neptune SQL → dbt model 변환 스크립트 (Presto → BigQuery 방언 자동 변환 일부) |
| Tier 3 (hourly) 패턴 검증 | DE + 플랫폼팀 | 타임존 변환 정밀 |

- [ ] Tier 1~2 의 90% 이상 마이그레이션 완료

- [ ] Tier 4 (YAML) 패턴 1개 이상 운영 정착

**목표**: 모든 ETL dbt 이전, Neptune 운영 종료

| 활동 | 담당 | 비고 |
|---|---|---|
| Tier 5 (AVRO) 마이그레이션 | DE + 플랫폼팀 | 컨슈머 호환성 확인 ([[5_Neptune SQL 변환의 dbt-BigQuery 대체 검토]] § 2-6 참조) |

| Neptune factory deprecation 공지 | 매니저 | 일정 + cutover 절차 |
| 잔여 ETL 정리 | DE | unused ETL 폐기 결정 |
| Neptune 관련 athlon 코드 / DB 정리 | 플랫폼팀 | athlon UI 의 잔존 역할 확정 |

- [ ] 운영 중인 ETL 100% dbt 이관

## 5. 리소스 / 책임 (RACI)

### 5-1. 핵심 책임

| 활동 | DE 팀 | 플랫폼팀 | 매니저 | 비고 |
|---|---|---|---|---|
| 인프라 (Composer / BQ / GCS) | I | R/A | I | |
| CI/CD 자동화 | I | R/A | I | |
| 공통 helper / 템플릿 / 문서 | C | R/A | I | |
| Slack 지원 / 워크샵 | I | R/A | I | |
| ETL 마이그레이션 (SQL 번역 + dbt 작성) | R/A | C | I | DE 가 도메인 owner |
| DAG 작성 / 백필 | R/A | C | I | DE |
| 운영 사고 1차 대응 | R/A | C | I | DE |
| 의사결정 (일정 / 우선순위) | C | C | R/A | |

R=Responsible, A=Accountable, C=Consulted, I=Informed

### 5-2. 리소스 산정

- **DE 팀별**: 마이그레이션 sprint 시 ETL 1개당 0.5~2 인일 (Tier 에 따라)
- **플랫폼팀**: Phase 0 풀타임 1~2명 + Phase 1~3 pair / 도구 0.5~1명
- **DE 매니저 / 디렉터**: 의사결정 + DE 시간 OKR 인정

→ DE 의 마이그레이션 시간은 **별도 OKR 또는 정식 업무**로 인정 필요. 일반 업무에 끼워넣으면 진척 안 됨.

## 6. 안전 장치

### 6-1. dual-run 정책

- 각 마이그레이션 ETL 에 대해 **1~2주 dual-run**
- Neptune 산출물 vs dbt 산출물 자동 비교 (row count, partition, 컬럼 hash)
- 정합성 OK → dbt 단독 운영
- 정합성 NG → 원인 분석 후 fix, dual-run 연장

### 6-2. Rollback

- **코드 차원**: git revert (PR 단위)
- **데이터 차원**: BQ time travel (7일 내)
- **운영 차원**: Phase 3 이전엔 Neptune 항상 fallback 가능

### 6-3. Phase gate

- 각 Phase 진입 조건 명시 (§ 4)
- 조건 미충족 시 다음 Phase 보류
- "일정 압박" 으로 gate 건너뛰지 않음

### 6-4. 사고 시 대응

- DE 1차: Cloud Logging + BQ INFORMATION_SCHEMA 로 진단
- DE 2차: `#dbt-support` 채널 → 플랫폼팀 협조
- 심각 사고: Neptune 으로 일시 fallback (Phase 3 이전)
