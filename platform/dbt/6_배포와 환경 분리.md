## 2. 배포 단위 (변경 빈도별)

| 단위                              | 변경 빈도           | 영향                          | 배포 방법                    |
| ------------------------------- | --------------- | --------------------------- | ------------------------ |
| **dbt 모델 SQL** (`models/*.sql`) | 가장 자주           | 그 모델의 다음 run                | GCS sync (dbt 프로젝트 디렉토리) |
| **schema.yml**                  | 자주              | contract 체크에 영향             | GCS sync                 |
| **manifest.json**               | 위 둘 변경마다 재생성 필요 | Cosmos 가 DAG 파싱 시점에 사용      | dbt parse 후 별도 upload    |
| **DAG 파일** (`dags/*.py`)        | 드물게             | 다음 scheduler 파싱 후 적용 (1~2분) | GCS cp                   |
| **common/ 모듈**                  | 가장 드물게          | 모든 DAG 영향                   | GCS sync (`common/` 폴더)  |

→ **dbt 모델만 바뀐 경우 manifest 재생성 + upload 필수**. 둘 다 안 올리면 DAG 은 옛 manifest 로 동작.

## 3. 환경 분리 (dev / prod)

### 3-1. dbt target 분리

`profiles.yml`:
```yaml
dbt_test:
  target: dev
  outputs:
    dev:
      type: bigquery
      method: oauth                       # Composer worker SA via ADC
      project: dev-dp-project-354904
      dataset: dbt_test
      location: asia-northeast3
    prod:
      type: bigquery
      method: oauth                       # prod Composer SA via ADC
      project: prod-dp-project
      dataset: dbt_prod
      location: asia-northeast3
```

### 3-2. Composer 환경 변수로 target 선택

각 Composer 환경에 `DBT_TARGET` env var 설정:
- dev Composer: `DBT_TARGET=dev`
- prod Composer: `DBT_TARGET=prod`

`common/dbt_presets.py` 가 이 env var 를 읽어서 `ProfileConfig.target_name` 에 적용 (기존 코드 그대로 동작).

### 3-3. 두 Composer 인스턴스

| 환경   | Composer 이름              | bucket                         | BQ project              |
| ---- | ------------------------ | ------------------------------ | ----------------------- |
| dev  | `test-airflow3` (현재 PoC) | `gs://dev-airflow-test-bucket` | `dev-dp-project-354904` |
| prod | `prod-airflow3` (예시)     | `gs://prod-airflow-bucket`     | `prod-dp-project-xxx`   |

→ 두 환경의 GCS bucket 이 다르므로 배포 명령에 bucket 만 바꾸면 됨.

## 4. 수동 배포 절차 (PoC 검증 완료)

### 4-1. dbt 프로젝트

```bash
cd /path/to/dbt-test/dbt_test

# 1. Composer 와 같은 dbt 버전 venv 활성화 (1.9.x)
source /tmp/dbt19/bin/activate

# 2. manifest 재생성 (BQ 접속 X)
dbt parse --profiles-dir . --target composer

# 3. GCS sync (exclude 로 잡파일 제외)
gcloud storage rsync -r --delete-unmatched-destination-objects \
  --exclude='target/run/.*' \
  --exclude='target/compiled/.*' \
  --exclude='target/graph.*' \
  --exclude='target/run_results.*' \
  --exclude='target/sources\.json' \
  --exclude='logs/.*' \
  --exclude='dbt-env/.*' \
  --exclude='\.git/.*' \
  --exclude='\.idea/.*' \
  . gs://dev-airflow-test-bucket/dags/dbt_projects/dbt_test
```

### 4-2. DAG 파일

```bash
cd /path/to/dbt-test-airflow-dags

gcloud storage cp dags/*.py gs://dev-airflow-test-bucket/dags/
gcloud storage rsync -r dags/common gs://dev-airflow-test-bucket/dags/common
```

### 4-3. 변경 후 검증

```bash
# 1~2분 대기 후 Composer scheduler 가 새 DAG/manifest 인식했는지
gcloud composer environments run test-airflow3 \
  --location asia-northeast3 \
  dags list 2>&1 | grep <my_dag>

# manifest 의 dbt 버전 확인
gcloud storage cat gs://dev-airflow-test-bucket/dags/dbt_projects/dbt_test/target/manifest.json \
  | jq '.metadata.dbt_version'
```

## 5. CI/CD 자동화 (GitHub Actions)

### 5-1. dbt 레포 워크플로우 (`deploy-dbt.yml`)

```yaml
name: Deploy dbt to Composer

on:
  push:
    branches: [main]
    paths: ['dbt_test/**', '.github/workflows/deploy-dbt.yml']
  workflow_dispatch:

permissions:
  contents: read
  id-token: write

jobs:
  deploy:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      - uses: actions/setup-python@v5
        with: { python-version: '3.11' }

      - name: Install dbt (Composer 와 동일 버전)
        run: pip install 'dbt-core==1.9.*' 'dbt-bigquery==1.9.*'

      - name: dbt parse
        working-directory: dbt_test
        run: dbt parse --profiles-dir . --target composer

      - name: dbt ls (selector 검증)
        working-directory: dbt_test
        run: dbt ls --profiles-dir . --target composer --select tag:neptune_poc

      - uses: google-github-actions/auth@v2
        with:
          workload_identity_provider: ${{ secrets.GCP_WIF_PROVIDER }}
          service_account: ${{ secrets.GCP_SA }}

      - uses: google-github-actions/setup-gcloud@v2

      - name: Sync dbt project to Composer
        run: |
          gcloud storage rsync -r --delete-unmatched-destination-objects \
            --exclude='target/run/.*' \
            --exclude='target/compiled/.*' \
            --exclude='target/run_results.*' \
            --exclude='logs/.*' \
            --exclude='\.git/.*' \
            dbt_test \
            ${{ secrets.COMPOSER_BUCKET }}/dags/dbt_projects/dbt_test
```

⚠️ **dbt 버전 일치 강제**: `pip install 'dbt-core==1.9.*'` — Composer 와 같은 메이저/마이너. 1.10/1.11 manifest 호환성 사고 방지 (PoC 에서 실제 경험).

### 5-2. DAG 레포 워크플로우 (`deploy-dags.yml`)

```yaml
name: Deploy DAGs to Composer

on:
  push:
    branches: [main]
    paths: ['dags/**']
  workflow_dispatch:

permissions:
  contents: read
  id-token: write

jobs:
  deploy:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      - uses: actions/setup-python@v5
        with: { python-version: '3.11' }

      - name: Syntax check
        run: python -m py_compile dags/*.py dags/common/*.py

      - uses: google-github-actions/auth@v2
        with:
          workload_identity_provider: ${{ secrets.GCP_WIF_PROVIDER }}
          service_account: ${{ secrets.GCP_SA }}

      - uses: google-github-actions/setup-gcloud@v2

      # dbt_projects/ 는 dbt 레포가 관리하므로 보존
      - name: Sync DAG files
        run: |
          # 1) 옛 .py 중 로컬에 없는 거 GCS 에서 정리
          gcloud storage ls ${{ secrets.COMPOSER_BUCKET }}/dags/*.py | \
            while read remote; do
              name=$(basename "$remote")
              [ -f "dags/$name" ] || gcloud storage rm "$remote"
            done

          # 2) 로컬 .py 업로드
          gcloud storage cp dags/*.py ${{ secrets.COMPOSER_BUCKET }}/dags/

          # 3) common/ 모듈
          gcloud storage rsync -r dags/common ${{ secrets.COMPOSER_BUCKET }}/dags/common
```

## 6. 두 레포 협조 (변경 순서)

### 6-1. dbt 모델 + DAG 동시 변경 시

**올바른 순서**:
1. dbt 레포에 **양쪽 호환** PR 머지 (예: 모델 alias 추가, 기존 모델도 유지)
2. dbt 레포 자동 배포
3. DAG 레포에서 새 모델 참조 PR 머지
4. DAG 레포 자동 배포
5. dbt 레포에서 옛 모델 제거 PR

**잘못된 순서**: dbt + DAG 한 번에 다 머지 → 그 사이 1~2분 동안 DAG 이 새 모델을 찾는데 dbt 쪽에선 옛 모델만 있어서 실패

## 7. Rollback 절차

### 7-1. dbt 변경 rollback

```bash
# git 으로 이전 커밋 체크아웃
cd /path/to/dbt-test
git revert <commit-sha>      # 또는 git checkout <prev-sha> -- dbt_test/

# 다시 배포
cd dbt_test
dbt parse --profiles-dir . --target composer
gcloud storage rsync ... (위와 동일)
```

### 7-2. DAG 변경 rollback

```bash
cd /path/to/dbt-test-airflow-dags
git revert <commit-sha>
gcloud storage cp dags/<changed_dag>.py gs://<bucket>/dags/<changed_dag>.py
```

### 7-3. BQ 테이블 시점 복구 (BQ time travel)

dbt 가 잘못된 결과 만들었으면:
```sql
-- 7일 이내 시점으로 데이터 복원
CREATE OR REPLACE TABLE `dev-dp-project-354904.dbt_test.case2_kp_stat_ticket_use_daily` AS
SELECT * FROM `dev-dp-project-354904.dbt_test.case2_kp_stat_ticket_use_daily`
  FOR SYSTEM_TIME AS OF TIMESTAMP_SUB(CURRENT_TIMESTAMP(), INTERVAL 1 HOUR);
```

⚠️ BQ time travel 은 **7일** (기본). 더 긴 보존은 별도 backup 정책.

## 9. PoC 에서 부딪힌 실측 함정

### 9-1. dbt 버전 mismatch (manifest 호환성)

**증상**: dbt task 가 `Running with dbt=1.9.3` banner 만 찍고 hang. 로그 없이 5분 후 worker timeout.

**원인**: 로컬에서 1.11 로 manifest 생성 → Composer 의 1.9 가 못 읽음 (manifest schema v13 vs v12).

**해결**: dev venv 에 `pip install 'dbt-core==1.9.*' 'dbt-bigquery==1.9.*'` 강제. CI 도 같은 버전 고정.

→ § 5-1 의 CI 워크플로우에 이미 반영됨. 운영에선 Composer 의 dbt 버전 변경 시 CI 도 같이 바꿔야 함.

### 9-2. gcloud auth 자주 만료

`gcloud storage` 명령이 ADC 만료로 실패. 로컬 작업 시 빈번.

**해결**: WIF 자동화 (CI 에선 불필요). 수동 작업 자주 한다면 `gcloud auth application-default login` 주기적 실행.

### 9-3. Composer worker OOM 으로 task 일괄 죽음

**증상**: 자정에 여러 DAG 의 task 들이 동시에 fail. `Executor reported failed but state is running` 메시지.

**원인**: 같은 worker pod 에서 dbt subprocess 여러 개가 동시에 메모리 잡아먹음.

**해결**:
- 무거운 task 는 K8s executor 로 (POC 의 case3 패턴)
- 자정 DAG 스케줄 분산 (cron 시간 다양화)
- Composer worker 메모리 증설

## 10. 미해결 / 추가 검토

- 모델 변경 영향도를 dbt CI 에서 자동 측정 (slim CI: `--state` 로 변경분만 run)
- DAG 레포 PR 에서 자동으로 syntax check 외에 import 검증 (Cosmos parse 시뮬레이션)
- blue-green 배포 (prod manifest 를 prod_blue / prod_green 두 경로에 두고 atomic swap)
- 배포 실패 시 자동 rollback (CI 가 실패 detection → 이전 GCS 버전 복구)
- 환경 변수의 Composer override (Composer Variables 사용 vs env var) 패턴 표준화
