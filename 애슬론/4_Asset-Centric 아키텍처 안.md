# Asset-Centric 아키텍처 안

> **팀 논의용 제안서.** 기존 athlon (workflow/actions/action_dependencies) 모델을 폐기하고 **"음식(Asset)"** 중심으로 재설계하는 안.
>
> 이 노트의 목표: 비전공자도 이해할 수 있게 풀어쓰고, 팀 논의에 그대로 가져갈 수 있게 정리.

## TL;DR (3줄)

1. 기존 athlon = "주방 일과표 관리" (어떤 작업을 하는가 중심)
2. 새 athlon = "메뉴판 관리" (어떤 데이터를 만드는가 중심)
3. Airflow 3 가 같은 방향으로 진화 중이라 우리 디자인이 자연스럽게 맞물림

---

## 1. 식당 비유로 이해하기

### 1-1. 기존 athlon = "주방 일과표 관리"

```
하루 일과표 (=Workflow):
  06:00 양파 썰기      (action 1)
  06:10 고기 볶기      (action 2, 양파 썰기 후)
  06:20 국 끓이기      (action 3, 고기 볶기 후)
```

사용자가 보는 건 "**작업 일과표**". 각 작업이 뭘 만드는지는 작업 안에 묻혀 있음.

**문제점**:

- "지금 김치찌개는 어디서 만들어지지?" → 모든 일과표 뒤져야 알 수 있음
- "양파 떨어졌어!" → 양파 쓰는 일과표 다 찾으려면 한참 걸림
- 새 요리 도구 추가 = 시스템 코드 변경
- 작업과 결과물이 분리 안 됨 → 시각화도 어색

### 1-2. 새 athlon = "메뉴판 관리"

```
오늘의 메뉴:
  🍲 김치찌개  ← 만드는법: SQL 변환 (DBT_MODEL)
  🥢 양파슬라이스  ← 만드는법: 외부에서 가져옴 (EXTRACT)
  🍱 도시락 포장  ← 만드는법: 외부로 보냄 (EXPORT)

각 메뉴는 자기가 뭘 필요로 하는지 안다:
  김치찌개  ← 필요: 양파슬라이스, 고기, 김치
  도시락 포장 ← 필요: 김치찌개, 흰밥
```

사용자가 보는 건 **결과물(음식)**. 만드는 방법은 부속 정보.

**효과**:

- "김치찌개 누가 만들지?" → 메뉴 카드 한 번에 보임
- "양파 떨어졌어!" → 양파 쓰는 메뉴 자동 추적
- 새 만드는 방법 추가 = producer plugin 등록 (시스템 코드 안 건드림)
- 시각화 = 자연스러운 lineage 그래프

## 2. 4가지 개념

| 개념 | 식당 비유 | 진짜 의미 |
|---|---|---|
| **Asset (자산)** | 음식 | 만들어지는 데이터 한 덩어리. 예: `bigquery://prod.marts.daily_user_summary` |
| **Producer (생산자)** | 레시피 | 그 음식 만드는 방법. 5가지 종류 (아래) |
| **AssetGroup (자산 그룹)** | 한 끼 메뉴 묶음 | 같이 만들고 같이 관리할 자산들. 스케줄·백필 단위 |
| **Profile (프로파일)** | 본점/분점 환경 | 같은 메뉴, 다른 매장 (dev/staging/prod) |

### Producer 5가지 종류

| Producer | 비유 | 무엇 |
|---|---|---|
| **DBT_MODEL** | SQL 레시피 | dbt로 SQL 변환 (대부분의 ETL) |
| **EXTRACT** | 외부에서 재료 받기 | 사내 시스템 / 외부 API → BQ raw |
| **EXPORT** | 외부로 음식 배달 | BQ → GCS / Slack / 외부 시스템 |
| **SENSOR** | 재료 도착 기다림 | 외부 이벤트 / 파일 대기 |
| **CUSTOM** | 특수 처리 레시피 | 우리 팀이 만든 wrapper |

## 3. 진짜 무엇이 바뀌나 — 데이터 모델 비교

### 기존 (workflows / actions / action_dependencies)

```
WorkFlow
  ─ name, schedule_interval, slack_channels, kwargs
  ─ start/end task 강제

Action (= 1 task)
  ─ name, operator_class (enum, ~20개)
  ─ kwargs (free JSON)
  ─ upstream_actions []   (= action_dependencies)
```

### 새 (Asset / Producer / AssetGroup / Profile)

```
Asset
  ─ urn       : 전역 ID (예: bigquery://prod.marts.daily_user_summary)
  ─ schema    : 컬럼/타입
  ─ owner / domain / tags / description
  ─ inputs    : [다른 Asset.urn, ...]   ← 의존성 = 자연스럽게 lineage

Producer (Asset 안에)
  ─ type   : DBT_MODEL | EXTRACT | EXPORT | SENSOR | CUSTOM
  ─ config : 타입별 설정 (jsonb)

AssetGroup
  ─ name, schedule, profile, owner
  ─ assets : [Asset]

Profile
  ─ name : "dev" | "prod"
  ─ vars : { BQ_PROJECT, GCS_BUCKET, SLACK_CHANNEL, ... }
```

→ 4개 엔티티로 단순화. operator_class enum 같은 경직 사라짐.

## 4. 실제 흐름 — YAML 부터 Airflow까지

### Step 1: 사용자가 UI 또는 YAML 편집

`groups/daily_user.yml`:

```yaml
name: "daily_user"
schedule: "0 6 * * *"
profile: prod
assets:
  - user/user_action_raw
  - user/stg_user_action
  - user/daily_user_summary
  - user/export_daily_summary
```

`assets/user/user_action_raw.yml`:

```yaml
urn: "bigquery://${BQ_PROJECT}.raw.user_action_raw"
inputs: ["external://mysql.kakaopage_user.action"]
producer:
  type: EXTRACT
  config:
    source: "mysql"
    conn_id: "kakaopage_user_db"
    table: "user_action"
    incremental: true
```

`assets/user/stg_user_action.yml`:

```yaml
urn: "bigquery://${BQ_PROJECT}.staging.stg_user_action"
inputs: ["bigquery://${BQ_PROJECT}.raw.user_action_raw"]
producer:
  type: DBT_MODEL
  config:
    select: "stg_user_action"
```

`profiles/prod.yml`:

```yaml
BQ_PROJECT: "dataplatform-prod"
GCS_BUCKET: "reports-prod"
SLACK_CHANNEL: "#data-alert"
```

### Step 2: athlon-compiler 가 Python으로 번역

```
사용자 저장 → git commit → CI 트리거 → athlon-compiler 실행
   ├─ YAML 다 읽음
   ├─ Profile 변수 치환 (${BQ_PROJECT} → "dataplatform-prod")
   ├─ Asset 의존성 그래프 빌드 (inputs 따라)
   ├─ Python DAG 코드 emit
   └─ GCS 버킷에 push
```

### Step 3: 생성된 Python (Composer 가 읽는 것)

```python
# generated/dags/daily_user.py
# AUTO-GENERATED by athlon-compiler. DO NOT EDIT.
# Source: groups/daily_user.yml @ git abc123  Profile: prod

from datetime import datetime
from airflow import DAG
from airflow.sdk import Asset
from athlon_runtime import build_extract, build_dbt, build_export, slack_alert

# Asset 선언 (Airflow 3 native!)
USER_RAW = Asset("bigquery://dataplatform-prod.raw.user_action_raw")
STG_USER = Asset("bigquery://dataplatform-prod.staging.stg_user_action")
DAILY    = Asset("bigquery://dataplatform-prod.marts.daily_user_summary")

with DAG(
    dag_id="daily_user",
    schedule="0 6 * * *",
    start_date=datetime(2024, 1, 1),
    tags=["athlon", "asset-group:daily_user", "profile:prod"],
) as dag:

    extract_raw = build_extract(
        task_id="user_action_raw",
        source="mysql",
        conn_id="kakaopage_user_db",
        table="user_action",
        target="dataplatform-prod.raw.user_action_raw",
        outlets=[USER_RAW],
    )

    stg = build_dbt(
        task_id="stg_user_action",
        select="stg_user_action",
        target="prod",
        inlets=[USER_RAW],
        outlets=[STG_USER],
    )

    extract_raw >> stg
```

### Step 4: Airflow 가 실행

- Airflow 가 Python DAG 파싱
- task 실행
- `outlets=[STG_USER]` 덕에 "stg_user_action 갱신됨" 이벤트 발생
- 다른 DAG 가 `schedule=[STG_USER]` 로 등록되어 있으면 자동 트리거

### Step 5: DataHub 자동 lineage

- Airflow 의 inlets/outlets → datahub-airflow-plugin 이 자동 push
- dbt manifest → datahub-dbt 가 자동 push
- DataHub 에 lineage 자동 형성

→ **athlon은 정의만 책임지고, 실행·관찰·lineage 는 표준 도구가 한다.**

## 5. athlon_runtime 모듈

생성된 Python 에서 `build_extract`, `build_dbt`, `build_export` 같은 helper 를 호출하는데, 이게 우리가 만드는 표준 라이브러리:

```python
# athlon_runtime/__init__.py

def build_extract(task_id, source, **cfg):
    """외부 시스템 → BQ 적재"""
    if source == "mysql":
        return MySQLToBigQueryOperator(task_id=task_id, **cfg)
    elif source == "rest_api":
        return RestApiExtractOperator(task_id=task_id, **cfg)
    # ... plugin 으로 확장

def build_dbt(task_id, select, target, inlets=None, outlets=None):
    """dbt run task 생성 (KubernetesPodOperator wrapper)"""
    return KubernetesPodOperator(
        task_id=task_id,
        image="our-dbt-runner:latest",
        cmds=["dbt", "run", "--select", select, "--target", target],
        inlets=inlets or [],
        outlets=outlets or [],
    )

def build_export(task_id, sql, inlets=None, outlets=None):
    return BigQueryInsertJobOperator(
        task_id=task_id,
        configuration={"query": {"query": sql, "useLegacySql": False}},
        inlets=inlets or [],
        outlets=outlets or [],
    )

# ... build_sensor, build_custom 등
```

→ 새 producer type 추가 = 함수 하나 추가. 기존 if-elif 체인 안 늘어남.

## 6. Airflow 3 Asset 활용 — 큰 이득

> 💡 **Airflow Asset 자체에 대한 상세 (Dataset → Asset 진화 / AssetWatcher / AssetAlias / @asset / URI 권고 등)**: [[../스케줄러/9_Airflow Asset과 Dataset]]

### Asset 매핑

우리 Asset URN ↔ Airflow Asset URI ↔ DataHub Dataset URN. **세 시스템이 같은 키 사용**.

### 자동 트리거 (스케줄)

```python
# DAG A: 데이터 생성
with DAG("daily_user", schedule="0 6 * * *") as dag:
    task >> ... >> daily_summary  # outlets=[DAILY]

# DAG B: DAG A 가 끝나면 자동 실행 (Cron 아님!)
with DAG("downstream_report", schedule=[DAILY]) as dag:
    ...
```

→ 기존 ExternalTaskSensor 같은 거 다 폐기. asset 갱신이 자연스러운 트리거.

### AssetWatcher (이벤트 기반)

```python
# 외부 파일 도착 → asset 자동 갱신 → 후속 DAG 트리거
@asset(
    watchers=[AssetWatcher(
        name="user_log_arrival",
        trigger=PubSubMessageTrigger(...),
    )]
)
def user_action_raw():
    ...
```

→ 폴링 sensor 일부 사라짐. 이벤트 기반으로.

### 자동 lineage

`inlets=[A]`, `outlets=[B]` 만 선언하면 Airflow + DataHub 가 알아서 lineage 그림.

## 7. 왜 이게 더 좋은가 (현재 모델 대비)

| 항목 | 현재 (workflow/actions) | 새 (Asset-Centric) |
|---|---|---|
| 추상화 | task 모음 | 데이터 자산 모음 |
| 새 operator 추가 | 시스템 코드 변경 + 배포 | producer plugin 함수 1개 추가 |
| 의존성 모델 | upstream_actions (flat) | asset.inputs (자연스러운 lineage) |
| 시각화 | task 그래프 | data lineage 그래프 (= 운영자가 진짜 보고 싶은 것) |
| 환경 분리 | DAG 복제 | profile 만 변경 |
| dbt 통합 | 외부 | native (Asset의 한 producer type) |
| extract 통합 | task | native (Asset의 한 producer type) |
| sensor 통합 | task | native (Asset의 한 producer type), AssetWatcher로 일부 이벤트 기반 |
| inter-DAG 의존성 | ExternalTaskSensor | Asset URI (Airflow 3 native) |
| DataHub lineage push | 별도 instrument | Airflow + dbt-plugin 이 자동 |
| 버전 관리 | DB 직접 수정 | git 기반 (사용자도 git 흐름 자연스러움) |

## 8. 어려운 점 (솔직히)

### UI 부담

| 화면 | 필요? |
|---|---|
| Asset Explorer (카탈로그) | ✅ 필수 |
| Asset 편집 (producer type 별 form) | ✅ 필수 |
| AssetGroup 편집 + 그래프 | ✅ 필수 |
| Profile (환경 변수) | ✅ 필수 |
| Lineage 그래프 | 🟡 DataHub 에 위임 가능 |
| Materialization 이력 | 🟡 Airflow UI 에 위임 가능 |
| Backfill UI | 🟡 부분적으로 Airflow 의 asset materialize 활용 |
| Test 결과 / 데이터 품질 | 🟡 dbt 자체 UI 활용 가능 |

→ "관찰" 영역은 Airflow + DataHub 에 **위임**. athlon UI 는 "정의/편집"에 집중. 그래도 처음부터 만들 화면 많음.

### UI 부담 줄이는 방법

- JSON Schema → form 자동 생성 라이브러리 (`react-jsonschema-form`)
- MVP 는 YAML 에디터 + 검증만, form 은 단계적
- producer type 마다 form 따로지만 공통 컴포넌트 재사용
- dbt 모델 SQL 편집은 외부 IDE / VSCode 활용 (athlon 안 만들어도 됨)

### 그 외 어려움

| 항목 | 정도 | 대응 |
|---|---|---|
| 큰 패러다임 전환 | 큼 | 점진적이 아니라 새 시스템 빌드 (병행 운영 후 cutover) |
| DE 팀 사고 전환 | 중 | 트레이닝 / 문서 / 마이그레이션 도구 |
| 기존 데이터 마이그레이션 | 큼 | 자동 변환 스크립트 (workflow/action → Asset/Producer) |
| 백엔드 + UI 신규 작업량 | 큼 | 8주 ~ 6개월 추정 (팀 규모에 따라) |
| 사내 첫 사례 | 중 | dbt-style 패러다임은 검증됨 (dbt, Dagster 등) |

## 9. 팀 논의 항목 (회의 안건)

### A. 방향 자체

- [ ] 안1: 기존 workflow/actions 진화 (점진적, 익숙함)
- [ ] 안2: Asset-Centric 신설계 (재작성, 미래 정합성)
- [ ] 안3: 하이브리드 (workflow 유지 + Asset abstraction 부분 도입)

### B. 만약 안 2 (Asset-Centric) 라면

- [ ] 백엔드 / 프론트 / DE 인력 확보 가능?
- [ ] 일정: 6개월 ~ 1년 예상. GCP 이관 데드라인과 sync 가능?
- [ ] dbt project를 athlon 안에 host? 별도 git repo로 분리?
- [ ] Compile 시점: athlon backend (실시간) / CI (git push) / Composer DAG Bundle
- [ ] Cosmos 도입 여부 (dbt 모델 = 모델별 Airflow task)
- [ ] athlon_runtime 표준 operator library 어디서 호스팅 / 버저닝

### C. 데이터 마이그레이션

- [ ] 기존 manual actions ~3,952개 자동 변환 가능한가?
- [ ] 변환 안 되는 케이스 (Hive 의존, custom 로직) 의 비율 / 처리 방안
- [ ] 마이그레이션 기간 dual-run 가능한가

### D. 어떤 화면이 athlon UI 필수인지 (vs Airflow/DataHub 위임)

- [ ] Asset Explorer / 편집 — athlon (필수)
- [ ] AssetGroup 그래프 — athlon (필수)
- [ ] Lineage 통합 뷰 — DataHub 위임?
- [ ] DAG run / 실행 이력 — Airflow UI 위임?
- [ ] Backfill — athlon (정책 중요) + Airflow asset materialize 활용

### E. 위험 / 의문점

- [ ] 우리 사내 표준이 아닌 패러다임 — 다른 팀이 받아들일 수 있나?
- [ ] Airflow 3 Asset 의 production maturity (2025-04 GA 후 1년)
- [ ] AssetWatcher 의 GCP 환경 호환성 (PubSub trigger 등)
- [ ] DataHub 의 Asset/DataFlow 모델이 우리 정의와 매끄럽게 매핑되는지

## 10. 일정 / 단계 (Asset-Centric 채택 시)

```
[Phase 0] 팀 합의 + Spec 확정 (1~2개월)
   ├─ 본 노트 + [[1_개요]] 기반 팀 워크샵
   ├─ Asset YAML 스키마 v1 확정
   ├─ Producer type 인벤토리 (잔존 + 신규)
   └─ 마이그레이션 가능성 점검

[Phase 1] MVP — Compiler + Runtime (2~3개월)
   ├─ athlon-compiler v1 (YAML → Python)
   ├─ athlon_runtime v1 (build_extract / build_dbt / build_export / build_sensor)
   ├─ 샘플 ETL 1개 end-to-end (Asset YAML → Airflow → BQ)
   └─ Composer + Airflow 3 환경 검증

[Phase 2] Backend + 기본 UI (2~3개월)
   ├─ Asset / Producer / AssetGroup / Profile CRUD API
   ├─ YAML 편집 UI (Monaco + 검증)
   ├─ Asset Explorer (검색 / 트리)
   └─ AssetGroup 그래프 뷰 (단순)

[Phase 3] Producer Form + dbt 통합 (2개월)
   ├─ producer type 별 form (JSON Schema 기반)
   ├─ dbt manifest 자동 import → Asset 등록
   └─ Profile 편집 UI

[Phase 4] DataHub 통합 + 운영 (1~2개월)
   ├─ Asset URN ↔ DataHub Dataset 매핑 검증
   ├─ Backfill UI
   └─ Materialization 이력

[Phase 5] 마이그레이션 (2~3개월)
   ├─ 기존 workflow/action 자동 변환 스크립트
   ├─ 점진 cutover (Group 단위)
   └─ 옛 athlon 모듈 deprecate
```

총 1년 ~ 1년 6개월 예상. 인력에 따라 변동.
