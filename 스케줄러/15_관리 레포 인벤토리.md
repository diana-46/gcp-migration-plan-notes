# Composer 운영 관리 레포 인벤토리 — DE 자율 모델로의 전환

> Cloud Composer 3 운영을 위해 **직접 관리해야 하는 레포 = 3개**. 동시에 이는 **athlon DB-driven 모델 → DE 자율 git-based 모델** 로 가는 전환 자료.
>
> 회의 / DE 온보딩 / 의사결정용 단일 문서.

## TL;DR

> Composer 운영 자산은 3개 레포로 정리. **athlon DB 에 묻혀있던 DAG / ETL 정의가 git 으로 끌어내져 DE 가 직접 PR 로 관리**한다.
>
> - **레포 1: 공통 Operator 패키지** (플랫폼 팀 관리, AR 배포)
> - **레포 2: dbt project** (DE 직접 관리, git 형상)
> - **레포 3: DAG repo** (DE 직접 관리, GCS sync 배포)
>
> 플랫폼 팀은 **공통 자산 (Operator / 인프라 / 표준)** 만 책임, DE 는 **자기 도메인의 ETL / DAG** 를 책임. **단일 athlon factory 의 bottleneck 해소**.

## 1. 관리해야 할 3개 레포

### 1.1 인벤토리 표

| # | 레포 | 책임 영역 | 담당 | 배포 메커니즘 |
|---|---|---|---|---|
| **1** | **공통 Custom Operator 패키지** (`apache-airflow-providers-kakaoent`) | 사내 공통 Operator / Hook / Sensor / Connection 타입 | **플랫폼 팀** | Artifact Registry Python repo (`twine upload` → Composer `pip install`) |
| **2** | **dbt project** (예: `kakaoent-dbt-models`) | ETL/변환 로직 (SQL + schema.yml + sources + tests) | **DE 도메인 팀** | DAG repo 안 동봉 또는 별도 레포. CI 가 `manifest.json` 생성 → GCS / dbt artifact bucket |
| **3** | **DAG repo** (예: `kakaoent-airflow-dags`) | Airflow DAG / 스케줄 / 의존성 / 백필 설정 | **DE 도메인 팀** | GitDagBundle (또는 GCS sync) — git push → 자동 Composer 반영 |

### 1.2 각 레포의 역할 / 비역할

#### 레포 1 — 공통 Operator 패키지 (플랫폼 팀)

✅ **여기 들어감**:
- 사내 시스템 연동 Operator (예: `KakaoentSlackOperator`, `AthlonQueryOperator`)
- 사내 Connection / Hook 표준
- 공통 Sensor (특히 deferrable)
- 사내 DataHub / OpenLineage emit 표준 hook

❌ **여기 안 들어감**:
- 도메인 비즈니스 로직
- ETL 변환 SQL (→ dbt)
- DAG 정의 (→ DAG repo)

→ **plumbing 만**. DE 가 `from airflow.providers.kakaoent... import` 로 끌어다 씀.

#### 레포 2 — dbt project (DE)

✅ **여기 들어감**:
- 모든 SQL 변환 로직 (`.sql` 모델)
- 모델 schema / 테스트 (`schema.yml`, `tests/`)
- Source 선언 (`source('schema', 'table')`)
- Macro / Jinja
- Profile (환경별 BQ 연결)

❌ **여기 안 들어감**:
- 스케줄 (→ DAG repo)
- 외부 시스템 통신 (→ DAG / Operator)
- Sensor (→ DAG / Operator)

→ **순수 변환 로직만**. dbt 의 책임 경계 ([[애슬론/3_dbt 능력 경계와 영역 분담]] 참조).

디렉토리 구조 (PoC 기준):

```
dbt_test/
  models/
    <domain>/
      *.sql           ← SQL 변환 로직
      schema.yml      ← 컬럼 / 테스트 / contract
  sources/            ← 외부 raw 데이터 선언
  macros/             ← 재사용 Jinja
  tests/              ← singular tests
  dbt_project.yml
  profiles.yml        ← 환경별 BQ 연결 (DBT_TARGET env var)
  target/manifest.json ← CI 가 dbt parse 로 생성 → GCS sync
```

#### 레포 3 — DAG repo (DE)

✅ **여기 들어감**:
- DAG 정의 (스케줄 / 트리거 / 의존성)
- task 그래프 (Cosmos `DbtTaskGroup` 또는 수동 dbt 호출)
- Sensor / Trigger 호출
- 백필 / SLA / 알림 설정

❌ **여기 안 들어감**:
- SQL 변환 (→ dbt)
- 공통 Operator 정의 (→ Operator 패키지)
- 인프라 셋업 (→ IaC, 별도)

→ **오케스트레이션만**.

디렉토리 구조 (PoC 기준):

```
dags/
  <domain>/
    dag_*.py          ← Cosmos DbtTaskGroup + 스케줄
  experiments/        ← 검증용 DAG
  archive/            ← deprecated DAG
common/
  dbt_presets.py      ← 플랫폼팀 제공 helper (dbt_taskgroup, grouped_dbt_taskgroups 등)
```

### 1.3 세 레포의 관계 도식

```
┌──────────────────────────────────────────────────────┐
│  Layer 1 — Custom Operator Package (플랫폼 팀)       │
│   pip install apache-airflow-providers-kakaoent      │
│                  ↓                                   │
│              import 가능                              │
└──────────────────────────────────────────────────────┘
                      │
                      ↓
┌──────────────────────────────────────────────────────┐
│  Layer 3 — DAG repo (DE)                             │
│   - from airflow.providers.kakaoent... import        │
│   - from cosmos import DbtTaskGroup                  │
│   - dbt_projects/ 참조 (manifest.json)               │

                      │
                      ↓ Cosmos 가 dbt 호출
                      ↓
┌──────────────────────────────────────────────────────┐
│  Layer 2 — dbt project (DE)                          │
│   models/ + schema.yml + sources + tests             │
│   manifest.json (CI 가 미리 빌드 → GCS)              │
└──────────────────────────────────────────────────────┘
```

## 2. athlon DB-driven vs DE 자율 git 모델

### 2.1 큰 그림 비교

| 측면 | AS-IS (athlon DB-driven) | TO-BE (DE 자율 git) |
|---|---|---|
| **DAG 정의 위치** | athlon_db (workflows / actions / action_dependencies) | git repo (Python 코드) |
| **ETL 정의 위치** | athlon DB + neptune-sql 일부 수동 | dbt project (git) |
| **변경 메커니즘** | UI 또는 DB 직접 수정 | PR + review + merge |
| **버전 관리** | DB row 시점만 (history 약함) | git log 완전 형상관리 |
| **review 가능** | ❌ (UI 변경에 review 없음) | ✅ (PR review 표준) |
| **테스트 가능** | ❌ (live 환경만) | ✅ (dbt test + DAG unit test) |
| **rollback 가능** | ❌ (DB row 복원 어려움) | ✅ (git revert) |
| **DAG 일관성 검증** | athlon factory 가 유일 진실 | CI lint / type check |
| **bottleneck** | athlon DB / factory 가 SPOF | DE 가 자기 도메인 자율 |
| **운영 책임** | 플랫폼 팀 (DB / factory 관리) | DE (자기 DAG 책임) + 플랫폼 (인프라) |

### 2.2 athlon DB-driven 의 한계 (현 시점)

[[7_2_리소스 다이어트 포인트]] 발굴 + 코드 분석에서 확인된 한계:

1. **DAG parse 마다 athlon_db 폴링** — 분당 300~900 queries (DAG ~150개 × 30s parse 간격)
2. **DAG 파일이 5줄짜리 wrapper** — `airflow_dag('data_xxxx')` 한 줄. 정작 task 정의는 DB 안에
3. **review / 테스트 불가** — DB row 가 UI 로 변경됨. PR 워크플로 없음
4. **GCP 이관 시 athlon_db 자체가 Cloud SQL 로 가야 함** — 추가 비용 + 운영 부담
5. **factory 가 SPOF** — `athlon/airflow.py` 하나 깨지면 모든 DAG 깨짐
6. **import 비용** — DAG processor subprocess 매번 350 MB / 95% CPU ([[7_1_실제 스펙 산정#1.4]] 의 manager 노드 분석)

→ **athlon-as-platform 의 가치는 dbt 시대에 사라짐**. dbt + git 이 같은 역할을 더 잘 함.

### 2.4 정량화 권장 지표

전환 의사결정 / 회의용 객관 근거:

| 지표 | 측정 방법 |
|---|---|
| ETL 수정 요청의 평균 lead time | Athlon 티켓 → 운영 반영까지 |
| 백필 요청 빈도 | 월별 `BackfillService` 호출 수 |
| 사고 핸드오프 시간 | 사고 인지 ~ Athlon 작업 시작 |
| Athlon 팀의 운영 task 비중 | 분기별 작업 분류 |

### 2.5 PoC 에서 검증된 dbt 대응 패턴

dbt 가 athlon 의 기능을 실제로 대체 가능한지 검증한 PoC 결과:

| athlon 기능 | dbt 대응 패턴 | 검증 노트 |
|---|---|---|
| PLAIN / YAML SQL 변환 | materialization 6종 + ephemeral 인라인 | [[dbt/1_materialization]] |
| `TableSynchronizer` (자동 ALTER) | `contract` + `on_schema_change` + `pre_hook` | [[dbt/2_schema 관리]] |
| `BackfillService` (DAG fork) | 백필 DAG + dbt 자산 reuse | [[dbt/3_backfill]] |
| `${var}` 치환 + `EtlInputType.macro` | `{{ var() }}` + Airflow context Jinja | [[dbt/4_parameter 치환]] |
| `EtlDependencies` (수동 upstream) | `ref()` + Cosmos 자동 wiring | [[dbt/5_의존성 관리]] |
| Git/Jenkins 자동 배포 | GitHub Actions + GCS sync | [[dbt/6_배포와 환경 분리]] |
| AVRO 출력 (`merge_and_move`) | `post_hook` 에 `EXPORT DATA format='AVRO'` | [[dbt/1_materialization]] § 2-6 |

5 케이스 (`case1`~`case5`) + 백필 + 스키마 변경 (`contract` + `pre_hook`) 까지 dev Composer 에서 실측 검증 완료. 상세: [[애슬론/5_Neptune SQL 변환의 dbt-BigQuery 대체 검토]]

### 2.6 DE / 플랫폼팀이 launch 시 사용할 자산

PoC 산출물 — 자율운영 시작 시 DE 가 즉시 활용 가능:

| 자산 | 위치 | 역할 |
|---|---|---|
| `dbt_taskgroup()` helper | `dbt-test-airflow-dags/dags/common/dbt_presets.py` | Cosmos boilerplate 제거 |
| `grouped_dbt_taskgroups()` helper | 같은 위치 | 그룹 분리 시 manifest 기반 자동 wiring + heads/tails 계산 |
| `attach_datahub_dbt_outlets()` | 같은 위치 | DataHub URN outlet 부착 |
| 검증된 백필 DAG 패턴 | `dag_backfill_case2.py` | Neptune fork 패턴의 dbt 대응 |
| 노트 6편 (dbt/) | `gcp-migration-plan-notes/dbt/1~6` | DE 가 막힐 때 reference |

### 2.3 DE 가 받는 것 / 주는 것 / 책임

#### DE 가 새로 받는 것 ✅

| 받는 것 | 가치 |
|---|---|
| **dbt project 의 git 자율 관리** | PR review / 테스트 / rollback / 형상관리 |
| **DAG 직접 작성 가능** | 스케줄 / 의존성 / 알림 / 백필 정책을 직접 결정 |
| **dbt 표준 도구** | 업계 표준. 학습 ROI 높음 |
| **공통 Operator 표준 import** | `from airflow.providers.kakaoent... import` 한 줄 |
| **개발 환경 통일** | dbt + Cosmos + Airflow CLI 로 로컬에서 그대로 검증 가능 |

#### DE 가 주는 것 (포기) ⚠️

| 포기하는 것 | 보상 |
|---|---|
| **athlon UI 의 클릭 워크플로** | git PR / dbt CLI 가 대체. DE 에게 더 익숙한 도구 |
| **athlon factory 가 알아서 task 생성** | dbt + Cosmos 가 같은 역할 (모델 → task 자동 분해) |
| **단일 진실 (DB)** | git 이 단일 진실. tag / branch / commit 으로 환경별 분리 |

#### DE 의 새 책임 📋

| 책임 | 범위 |
|---|---|
| **자기 도메인의 dbt model 작성 / 테스트** | SQL + schema.yml + dbt test |
| **자기 도메인의 DAG 작성 / 스케줄** | DAG 파이썬 코드 + 의존성 / 알림 |
| **PR 워크플로 준수** | review 통과 + CI 통과 후 merge |
| **dbt manifest CI 빌드 검증** | manifest 가 정상 생성되는지 |

#### 플랫폼 팀의 새 책임 🛠️

| 책임 | 범위 |
|---|---|
| **공통 Operator 패키지 관리** | 사내 공통 자산 SemVer / 배포 |
| **Composer 인프라 / 환경 / 권한** | 환경 생성 / 모니터링 / 비용 / 보안 |
| **표준 정책 / CI 가드 / template** | DAG template / dbt project template / lint 규칙 |
| **DE 지원 / 마이그레이션 가이드** | 초기 학습 지원 |

→ **공통은 플랫폼, 도메인은 DE**. 깨끗한 책임 분리.

## 3. DE 의 흔한 우려와 답

### Q1. "각자 알아서 하면 일관성 깨지는 거 아니냐?"

**답**: 일관성은 **자동화된 가드** 로 보장:
- **공통 Operator 패키지** — 같은 패턴은 같은 Operator 사용 강제
- **dbt project template** — `dbt init kakaoent-template` 같은 starter
- **DAG template** — boilerplate 통일
- **CI lint** — `ruff` / `mypy` / `dbt parse` / `airflow dags list-import-errors`
- **review 정책** — PR 시 platform 팀 codeowner 일부 영역

→ athlon UI 의 "강제" 보다 git-based 의 "자동화 + 사회적 가드" 가 더 robust.

### Q2. "athlon DB 에 있던 backfill / parameter / dependency 관리는?"

**답**: dbt + Airflow 표준 기능으로 다 됨:

| AS-IS (athlon) | TO-BE (dbt + Airflow) |
|---|---|
| `EtlParameter` | dbt `var()` + Airflow `params` |
| `EtlPartition` | dbt `incremental` 모델 + `partition_by` |
| `EtlDependencies` | dbt `ref()` (모델 간) + Airflow Asset (DAG 간) |
| backfill UI | `airflow dags backfill` CLI + dbt `--vars` |
| `actions_meta` 템플릿 | dbt macro |

상세: [[애슬론/3_dbt 능력 경계와 영역 분담]]

### Q3. "Composer / dbt 학습 비용은?"

**답**: athlon-specific 학습 비용보다 **작거나 같음 + 외부 이전 가능**:
- dbt 는 업계 표준 — 다음 회사에서도 그대로 사용
- Airflow 는 데이터 엔지니어 거의 필수 도구
- athlon 은 사내 한정 — 외부 이전 불가

### Q4. "이관 중에 운영은? 점진적으로 가능?"

**답**: Phase 별로:

1. **Phase 0**: 공통 Operator 패키지 분리 (athlon 안 변경)
2. **Phase 1**: dbt project 셋업 + 일부 ETL 우선 전환 (athlon 과 dbt 병행)
3. **Phase 2**: 대규모 모델 dbt 로 전환, DAG 도 git 으로 옮김
4. **Phase 3**: athlon factory 폐기, 잔존 athlon 은 UI / extract 만

상세: [[0_결론#5. 권장 마이그레이션 경로]], [[애슬론/2_Git 동기화·dbt 전환 계획]]

### Q5. "공통 자산 (Operator) 변경 시 모든 DAG 깨질 수 있지 않냐?"

**답**:
- Operator 패키지는 **SemVer + 환경별 버전 lock** ([[7_3_공통 Custom Operator 제공 방안]])
- DE 는 자기 환경에서 사용 중인 버전 명시 (`apache-airflow-providers-kakaoent==1.2.3`)
- 플랫폼 팀이 breaking change 시 **major bump + 마이그레이션 가이드** 제공
- 호환 기간 (예: 6개월) 동안 양쪽 버전 운영

## 5. 핵심 정리 (1슬라이드)

1. **레포 3개로 정리됨** — Operator (플랫폼) / dbt (DE) / DAG (DE).
2. **자산의 위치 이동** — athlon DB → git. review / 테스트 / rollback / 형상관리 표준 도구로.
3. **책임 분리** — 플랫폼팀은 공통 자산 (Operator / 인프라 / 표준), DE 는 도메인 자산 (dbt / DAG).
4. **기술 스택** — dbt + Airflow 는 업계 표준 (athlon 은 사내 한정).
5. **GCP 이관 시점과 동시 진행** — athlon DB 의 Cloud SQL 이관 작업과 git 이관 작업이 겹침.
6. **점진적 이관 가능** — Phase 0~3, athlon 과 병행 운영 구간 있음.
