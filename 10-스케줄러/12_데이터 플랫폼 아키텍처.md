# 데이터 플랫폼 아키텍처

> Cloud Composer 3 + Airflow 3.1.7 이관을 계기로 사내 데이터 플랫폼 운영 모델을 다시 설계. Athlon 을 **파이프라인 관리 플랫폼**으로 명확히 포지셔닝하고, dbt 영역은 DE 자율로 분리, Composer + cosmos 가 실행, DataHub 가 메타데이터를 통합.

## TL;DR

> **Athlon = orchestration (파이프라인 정의 / 운영자 UI). dbt = DE 자유 영역 (모델 SQL 작성 IDE + AI). Composer + cosmos = 실행 엔진. DataHub = cross-tool 메타데이터. 4 component, 책임 명확히 분리.**

## 4-component 아키텍처 도식

```
┌─────────────────────────────────────────────────────────────────────┐
│                      [Athlon] — 파이프라인 관리                      │
│                                                                       │
│   Workflow Builder UI                                                 │
│     ├─ workflows / actions / action_dependencies (DB 3-table)        │
│     ├─ action_type:                                                  │
│     │    - dbt_select       (select 패턴만 입력)                     │
│     │    - custom_xxx       (사내 Custom Operator)                  │
│     │    - bash / sensor                                             │
│     └─ Publish → codegen → git PR 자동                              │
│                                                                       │
│   기타 자체 모듈:                                                   │
│     ├─ Userlake (사용자 코호트)                                     │
│     ├─ Dimsum (실시간 스트리밍)                                     │
│     ├─ CDC consumer                                                  │
│     └─ 권한 / RBAC                                                  │
└─────────────────────────┬───────────────────────────────────────────┘
                          │ codegen → PR 자동
                          ▼
┌─────────────────────────────────────────────────────────────────────┐
│                          [Git Repo]                                   │
│   ├─ dags/                                                            │
│   │   └─ data_*.py            ← Athlon codegen (전체 DAG)            │
│   ├─ dbt_project/                                                    │
│   │   ├─ models/              ← DE 가 IDE + AI 로 자유 작성         │
│   │   ├─ schema.yml                                                 │
│   │   └─ target/manifest.json ← CI 가 빌드                          │
│   └─ kakao_operators/         ← DE 가 Custom Operator 개발 (wheel)  │
└─────────────────────────┬───────────────────────────────────────────┘
                          │ CI/CD: dbt compile + wheel build + GCS sync
                          ▼
┌─────────────────────────────────────────────────────────────────────┐
│              [Cloud Composer 3 + Airflow 3.1.7]                       │
│   ├─ cosmos DbtTaskGroup       (dbt 모델 task 자동 생성)             │
│   ├─ Custom Operators (wheel from Artifact Registry)                  │
│   ├─ Athlon-codegen DAGs (전체 DAG 정의, runtime DB 조회 없음)        │
│   └─ Slack callback / Audit log / Monitoring                          │
└─────────────────────────────────────────────────────────────────────┘

        ↑ DataHub Ingestion (각 source 에서 메타데이터 수집)
        │
┌───────┴─────────────────────────────────────────────────────────────┐
│                          [DataHub]                                    │
│   - dbt manifest → 모델 lineage                                       │
│   - Airflow DAG → orchestration lineage                              │
│   - BigQuery → 스키마 / 쿼리                                         │
│   - Userlake / 기타 source                                           │
│                                                                       │
│   Athlon UI 에서 "View in DataHub ↗" 로 deep link                   │
└─────────────────────────────────────────────────────────────────────┘
```

## 핵심 결정 사항 (Decision Log)

회의에서 합의 필요한 결정들과 답:

| # | 결정 | 답 | 이유 |
|---|---|---|---|
| 1 | DAG 정의 source of truth | **Athlon DB (3-table)** | UI 친화 + 기존 운영 패턴 유지 |
| 2 | YAML / JSON 파일 도입 | **❌ 안 함** | 실무자 YAML 비선호 + UI 가 충분히 표현 |
| 3 | 운영자 인터페이스 | **Athlon UI only** | 운영팀이 git/코드 학습 부담 X |
| 4 | DE 인터페이스 (dbt) | **VSCode + AI 자유** | dbt Cloud 도입 안 함, 비용 절감 + 유연 |
| 5 | dbt 모델 관리 책임 | **DE 가 자율 관리** | 도메인 전문성, 모던 데이터 스택 표준 |
| 6 | 플랫폼팀의 dbt 영역 | **인프라 / CI / 거버넌스 / 메타 / 라이브러리 / 모니터링 / 비용** | DE 모델 내용 외 전부 |
| 7 | Athlon 의 dbt 인식 범위 | **`select 패턴` 만 알면 됨** | DE 자유 영역 침범 X |
| 8 | codegen 결과 | **전체 DAG 박기 (stub X)** | Composer 파싱 성능 / git diff |
| 9 | Athlon Publish 흐름 | **Git PR 자동 생성 + 리뷰 + merge** | 변경 추적 / 감사 |
| 10 | Composer ↔ dbt 통합 | **cosmos `DbtTaskGroup` (manifest 모드)** | 모델별 task 분리 / 가시성 |
| 11 | dbt 인증 | **ADC (Composer 환경 SA)** | keyfile 관리 불필요 |
| 12 | dbt 모델 검색 (운영자) | **dbt docs 정적 호스팅** | 무료 + 자체 검색 UI 안 만듦 |
| 13 | DataHub 통합 | **dbt + Airflow + BQ ingestion** | 기존 통합 확장 |
| 14 | dbt Cloud 도입 | **❌ 보류** | DE 가 IDE + AI 로 충분 |
| 15 | Athlon Python SDK | **Phase 2 이후** | 일단 UI only 로 시작 |
| 16 | PR validation | **✅ CI 에서 dbt list / sqlfluff / dbt build** | 운영자 select 패턴 오타 등 사전 차단 |
| 17 | Custom Operator 배포 | **wheel → Artifact Registry** | Step 3 PoC 검증 완료 |
| 18 | 3-table 스키마 확장 | **`actions.action_type` 에 dbt_xxx 추가 + `config` JSON** | 모델 변경 최소 |

## Athlon 의 정체 — 파이프라인 관리 플랫폼

### 하는 일

| 영역 | 책임 |
|---|---|
| **워크플로우 정의** | workflows / actions / dependencies (3-table 모델) |
| **dbt orchestration** | when / which group of models / depends on what |
| **Custom Operator 호출** | Slack / Kafka / API extract / sensor 등 사내 시스템 |
| **cross-team 의존성** | DAG 간 의존성 (ExternalTaskSensor 등) |
| **운영 권한 / RBAC** | 사내 SSO + 자체 역할 모델 |
| **PR 자동화** | UI 편집 → codegen → git push → PR |
| **DataHub link** | 메타데이터 조회 진입점 (UI 깊은 통합 X) |
| **자체 데이터 플랫폼 기능** | Userlake / Dimsum / CDC (기존 유지) |

### 하지 **않는** 일

| 영역 | 누가 / 어디서 |
|---|---|
| 모델 SQL 편집 | DE 가 VSCode + AI |
| 모델 lineage 시각화 | dbt docs 정적 사이트 / DataHub |
| 모델 검색 / dropdown | dbt docs / DataHub |
| 데이터 catalog | DataHub |
| ad-hoc 쿼리 | BigQuery Console |
| 모델 dry-run | 로컬 dbt CLI |
| dbt 디테일 (ref / test / materialization) | DE 자유 |
| SQL IDE | 없음 (필요시 dbt Cloud 별도 도입) |

### 정체성 한 줄

> **"파이프라인 정의 + 사내 시스템 통합 + 운영자 UI = Athlon. 그 외는 표준 도구."**

## DE 의 dbt 자유 영역

### DE 가 자율로 하는 것

- 모델 SQL 작성 (VSCode + dbt-power-user / Cursor / Copilot / Claude Code)
- 모델 의존성 (ref / source)
- 테스트 / schema.yml
- macros / packages
- materialization 선택 (view / table / incremental / ephemeral)
- 로컬 `dbt run` / `dbt test`
- git PR

### DE 의 제약 = CI 가 강제하는 룰

| 강제 | 도구 |
|---|---|
| SQL 스타일 | `sqlfluff` |
| dbt 베스트 프랙티스 | `dbt-project-evaluator` |
| 테스트 통과 | `dbt build` PR CI |
| 비용 임계치 | `bq query --dry_run` 결과 검증 |
| 보안 (PII / Secret) | 자동 검출 도구 |
| 큰 모델 incremental | 정책 + CI 검증 |

→ **사람 통제 X. 도구 강제 O**.

### dbt Cloud 도입 안 하는 이유

- DE 가 VSCode + AI 도구로 충분 (Cursor / Copilot / Claude Code 등)
- dbt Cloud Developer plan $100/seat/월 = 30명 기준 연 ~$36k
- 자체 IDE 신규 개발 비용도 미정
- 분석가 / 비-DE 가 SQL 본격 작성하기 시작하면 그때 재검토

## 플랫폼팀의 dbt 책임 — 7개 영역

### 1. 인프라 (Infrastructure)
- Composer 환경에 dbt-bigquery 설치 / 버전 관리
- ADC 인증 (Composer 환경 SA)
- cosmos 통합 (`DbtTaskGroup` 표준 패턴)
- GCS DAGs / dbt_project sync
- dbt 버전 업그레이드 호환성 검증
- profile 환경 분리 (dev / staging / prod)
- Secret Manager backend 셋업

### 2. CI/CD
- PR 단계 dbt 검증: `dbt deps` + `dbt parse` + `dbt compile` + `dbt build --select state:modified+`
- SQL lint (`sqlfluff`)
- 베스트 프랙티스 검증 (`dbt-project-evaluator`)
- 모델 변경 영향 분석 PR 코멘트
- BQ dry-run + 비용 추정 PR 코멘트
- merge 시 manifest.json 빌드 + GCS 업로드
- dbt docs 자동 빌드 + 정적 호스팅 sync
- 환경별 promote 파이프라인 (dev → staging → prod)

### 3. 거버넌스 / 표준
- dbt 베스트 프랙티스 문서 (staging / intermediate / marts 구조)
- 모델 템플릿 / cookiecutter
- column 명명 컨벤션 (`*_at`, `*_id`)
- 금지 패턴 강제 (`select *` 금지 등)
- PII 컬럼 자동 태깅
- materialization 정책 (marts.* = incremental 강제)
- PR 리뷰 규칙 (CODEOWNERS / downstream owner)
- breaking change versioning 정책

### 4. Observability
- 모델 실행 모니터링 (cosmos task 단위)
- dbt test 실패 → Slack 알림
- freshness 모니터링 (`dbt source freshness`)
- 모델별 duration 추이 dashboard
- 모델별 BQ scan / slot 사용량 dashboard
- 데이터 quality anomaly detection (`elementary-data`)
- DAG 실행 표준 `on_failure_callback`

### 5. 메타데이터 / Discovery
- DataHub dbt ingestion source 셋업 + 정기 실행
- DataHub Airflow ingestion source
- DataHub BigQuery ingestion source
- dbt docs 정적 호스팅 (GCS / Cloud Run)
- end-to-end lineage 보장 (source → Airflow → dbt → BQ → BI)
- owner 자동 할당

### 6. 공통 라이브러리 / 도구
- 사내 dbt macros 패키지 (`{{ kakao_timezone_convert() }}` 등)
- 사내 표준 staging 모델 패키지
- 외부 dbt package 큐레이션 (`dbt_utils`, `dbt_expectations`)
- 신규 도메인 dbt project 템플릿
- Custom Operator wheel 빌드 / Artifact Registry 운영
- pre-commit hooks 표준
- 사내 환경변수 자동 주입 `kakao-dbt` CLI wrapper

### 7. 비용 / 성능 거버넌스
- BQ slot reservation (dbt 전용)
- 비용 한도 alert (모델별 / 도메인별)
- scan size 제한 (PR 단계 검증)
- incremental 권장 정책 강제
- partition / clustering 가이드
- dbt run scheduling 최적화 (시간대 분산)
- caching 전략 (state caching)
- 성능 dashboard (가장 느린 / 비싼 모델)

## Composer + cosmos 통합 디테일

### cosmos render 모드 — `DBT_MANIFEST` 강제

```python
from cosmos import DbtTaskGroup, ProjectConfig, RenderConfig, ProfileConfig
from cosmos.constants import LoadMode

PROJECT_CONFIG = ProjectConfig(
    dbt_project_path="/home/airflow/gcs/dags/dbt_project",
    manifest_path="/home/airflow/gcs/dags/dbt_project/target/manifest.json",
)

PROFILE_CONFIG = ProfileConfig(
    profile_name="kakao_dbt",
    target_name="prod",
    # ADC 사용
)

dbt_models = DbtTaskGroup(
    group_id="dbt_marts",
    project_config=PROJECT_CONFIG,
    profile_config=PROFILE_CONFIG,
    render_config=RenderConfig(
        load_method=LoadMode.DBT_MANIFEST,  # CI 가 빌드한 manifest 사용
        select=["+marts.user_summary"],
    ),
)
```

→ **DAG 파싱 시 dbt CLI 실행 안 함** (파싱 성능). manifest.json 만 읽음.

## Athlon DB 스키마 확장

### 기존 3-table 모델 (그대로)

```
workflows
  ├─ uid, name, schedule_interval, catchup, ...

actions
  ├─ uid, workflow_uid, name
  ├─ action_type   ← enum 확장 (dbt_xxx 추가)
  ├─ config        ← JSONB, action_type 별 자유 스키마
  ├─ retries, retry_delay, pool, execution_timeout, ...

action_dependencies
  ├─ upstream_action_uid
  └─ downstream_action_uid
```

### 새로 추가할 action_type

| action_type | config 예시 | codegen 결과 |
|---|---|---|
| `dbt_select` | `{"select": "+marts.user_summary", "exclude": "tag:wip"}` | `DbtTaskGroup(render_config=RenderConfig(select=..., exclude=...))` |
| `dbt_test` | `{"select": "tag:critical"}` | `DbtTestLocalOperator(select=...)` |
| `dbt_snapshot` | `{"select": "snapshots.users"}` | `DbtSnapshotLocalOperator(...)` |
| `dbt_seed` | `{"select": "country_codes"}` | `DbtSeedLocalOperator(...)` |

→ `config` JSON 스키마는 `action_type` 별로 강제 (validation).

### 기존 action_type 매핑 (재검토)

| Athlon TemplateType (기존) | Composer 대응 |
|---|---|
| GCS_UPLOAD | 유지 (Custom Operator) |
| BIGQUERY_JOB | 유지 또는 dbt 모델로 일부 이관 |
| BQ_LOAD | 유지 |
| BIGQUERY_SENSOR | 유지 (deferrable 전환) |
| ATHLON_QUERY_SENSOR | 유지 (Athlon API 통신) |
| LOUPE_QUERY_TO_KAFKA | 유지 (Custom Operator) |
| **HIVE_TO_GCS_SYNC** | **폐기 → dbt 모델로** |
| LOUPE_SIGNAL_HTTP | 유지 |
| (신규) dbt_select / dbt_test / dbt_snapshot / dbt_seed | ✅ 추가 |

## codegen — 전체 DAG 생성

### 기존 (stub 방식)

```python
# data_xxx.py — stub
from athlon.airflow import airflow_dag
dag = airflow_dag('dag_name')   # 매 파싱마다 Athlon DB 조회
```

문제:
- Composer 환경에선 Athlon DB 가 멀어 매 파싱마다 네트워크 호출 → dag-processor 부담
- git diff 로 변경 추적 어려움 (실제 내용이 DB)

### 변경 (전체 DAG 박기)

```python
# data_xxx.py — Athlon codegen 결과
from datetime import datetime
from airflow import DAG
from kakao_operators import (
    ThirdPartyPullingOperator,
    SlackStatOperator,
    BigQueryQuerySensor,
)
from cosmos import DbtTaskGroup, ProjectConfig, RenderConfig

from common.composer_config import PROJECT_CONFIG, PROFILE_CONFIG

with DAG(
    dag_id="user_pipeline",
    schedule="0 2 * * *",
    start_date=datetime(2026, 5, 28),
    catchup=False,
    tags=["user", "daily"],
    default_args={"retries": 2, "on_failure_callback": slack_fail},
) as dag:
    extract = ThirdPartyPullingOperator(
        task_id="extract_users",
        endpoint="https://api.example.com/users",
        token_var="USERS_API_TOKEN",
    )

    dbt_staging = DbtTaskGroup(
        group_id="dbt_staging",
        project_config=PROJECT_CONFIG,
        profile_config=PROFILE_CONFIG,
        render_config=RenderConfig(select=["stg_users"]),
    )

    dbt_marts = DbtTaskGroup(
        group_id="dbt_marts",
        project_config=PROJECT_CONFIG,
        profile_config=PROFILE_CONFIG,
        render_config=RenderConfig(select=["+marts.user_summary"]),
    )

    notify = SlackStatOperator(
        task_id="notify",
        channel="#data-daily",
        query_var="SUMMARY_QUERY",
    )

    extract >> dbt_staging >> dbt_marts >> notify
```

→ DAG 파싱 시 Athlon DB hit X. git diff 에 변경 내역 명확히 표시.

## PR 자동화 흐름

```
[Athlon UI]
  운영자가 워크플로우 편집
       ↓ Save → DB update (staging)
       ↓ Publish to Production 버튼
[Athlon Backend]
  1. codegen → data_xxx.py 생성 (전체 DAG)
  2. git branch 생성 (athlon-publish-YYYYMMDD-HHMM)
  3. commit + push (메시지: workflow uid / 변경 요약)
  4. GitHub API → PR 자동 생성
     - 제목: "Athlon: update workflow [name]"
     - body: 변경 요약 + UI 스크린샷 (option)
  5. Slack 알림: "운영자 X 가 PR Y 생성"
       ↓
[GitHub Actions (PR validation)]
  - python -m py_compile dags/*.py        (syntax)
  - airflow dags test --dry-run            (파싱 가능?)
  - sqlfluff (dbt 모델은 안 봄, codegen Python 만)
  - dbt 모델 변경 있으면 dbt list --select  (운영자 select 검증)
  - 결과 PR 코멘트
       ↓
[Reviewer (운영자 / DE / lead)]
  - PR diff 확인
  - Approve 또는 Request changes
       ↓
[Merge → CI]
  - kakao_operators wheel 빌드 → Artifact Registry
  - dbt compile → manifest.json + catalog.json
  - GCS sync (DAGs + dbt_project + manifest)
       ↓
[Composer]
  - dag-processor 가 새 DAG 인식 (1~2분)
  - cosmos 가 manifest 읽어 DbtTaskGroup 생성
  - 다음 schedule 부터 실행
```

## PR validation 종류

| 검증 | 어떻게 |
|---|---|
| Python syntax | `python -m py_compile dags/*.py` |
| DAG 파싱 가능 | `airflow dags list-import-errors` 또는 `dags test` |
| SQL 스타일 | `sqlfluff lint dbt_project/models/` |
| dbt project 컴파일 | `dbt compile` |
| dbt 모델 select 검증 | `dbt list --select <pattern> --output json` → PR 코멘트 |
| 모델 변경 영향 분석 | `dbt list --select state:modified+ --output json` |
| BQ 비용 추정 | `bq query --dry_run` 각 모델 |
| Custom Operator import 가능 | wheel install + `python -c "import kakao_operators"` |
| action config schema 적합성 | JSON Schema validation |
| 금지 패턴 (`select *` 등) | grep 또는 dbt-project-evaluator |

## 잠재적 위험 / 함정

### 1. 운영자가 dbt select 패턴 실수

위험: prod 에서 task fail 또는 의도와 다른 모델 실행

완화:
- PR validation 단계에서 `dbt list --select` 자동 실행 + 결과 코멘트
- 0 매칭 시 PR fail
- 운영자가 dbt docs 사이트로 사전 검색

### 2. DE 가 dbt 베스트 프랙티스 안 따름

위험: 모델 품질 / 비용 폭주

완화:
- CI 강제 (sqlfluff / dbt-project-evaluator)
- BQ dry-run 비용 추정 PR 코멘트
- 베스트 프랙티스 문서 + 신규 DE 온보딩

### 3. Composer ↔ Athlon DB 네트워크

위험: 만약 codegen 이 동적 호출이면 dag-processor 부담

완화: codegen 을 전체 DAG 박기 방식으로 변경 (위 결정 #8)

### 4. dbt 모델과 Athlon action 의 의존성 이중화

위험: dbt 내부 의존성 (ref) + Athlon 외부 의존성 (action_dependencies) 두 시스템 공존

완화:
- 운영자는 dbt 내부 의존성 모름 (cosmos 가 알아서 처리)
- Athlon 의 의존성은 workflow 단위 (전체 dbt task group → notify 등)
- 두 레벨이 다르므로 충돌 없음 — 운영자 학습 가이드만 명확히

### 5. cross-workflow dbt 모델 의존성

예: workflow A 의 dbt 가 끝나야 workflow B 의 dbt 가 실행

완화:
- Phase 1: `ExternalTaskSensor` (deferrable)
- Phase 2: Airflow 3 Asset / Dataset 모델
- Phase 3: cosmos cross-DAG 통합 (지원되면)

### 6. dbt run 비용 폭주

위험: 잘못된 incremental / 큰 scan / 무한 backfill

완화:
- BQ slot reservation 으로 격리
- 일 비용 limit alert
- PR 단계 dry-run 비용 추정
- `dbt build --select state:modified+` 로 변경분만 실행

### 7. 팀장 / 의사결정자 반대

논점: "DE 자율 dbt 면 표준 / 품질 무너진다"

대답:
- 표준은 사람 통제 아니라 도구 강제
- CI / DataHub / lint 로 거버넌스 자동화
- 플랫폼팀이 위 7개 영역 책임 (놓는 게 아님)
- GitLab / HubSpot / Netflix 등 모던 데이터 스택 표준

## 회의 핵심 메시지 (1슬라이드 후보)

1. **"Athlon = 파이프라인 관리 플랫폼. dbt 영역은 DE 자율."**
2. **"두 영역의 경계 = dbt_select action 의 select 패턴 한 줄."**
3. **"플랫폼팀은 dbt 의 인프라 / CI / 거버넌스 / 메타 / 라이브러리 / 모니터링 / 비용 7개 영역 책임."**
4. **"3-table 모델 유지, codegen 전체 DAG 박기, PR 자동화."**
5. **"4 component 아키텍처: Athlon + git + Composer/cosmos + DataHub."**
