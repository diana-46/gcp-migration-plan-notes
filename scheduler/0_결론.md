# GCP 이관 — Airflow 스케줄러 최종 결론

> 지금까지의 리서치 + PoC 통합 결론. 디테일은 각 섹션의 link 참조.

## TL;DR

> **Cloud Composer 3 채택**. 단, **이관 전 sensor → trigger 다이어트 필수**.
>
> - 비용: 월 **~₩700~720만** (Phase 1, on-demand) → **~₩430~510만** (Phase 2, sensor 다이어트 후)
> - PoC 검증 결과 **호환성 / 권한 / 자동 안정성** 모두 통과
> - 핵심 사전 작업: **Sensor → Trigger 전환** 1순위, **manager 노드 다운사이즈** 즉시 가능

## 1. 최종 의사결정

### 1.1 채택: Cloud Composer 3 + Airflow 3.1.7

| 후보 | 월 비용 | 운영 부담 | 자동 안정성 | 최종 |
|---|---|---|---|---|
| GCE 상시 가동 | ₩1,890만 | 높음 | 낮음 | ❌ |
| GCE 다이어트 | ₩952만 | 높음 | 낮음 | ❌ |
| GKE Spot 옵션 A | ₩550만 | 중간 (K8s 운영) | 중간 | △ Plan B |
| GKE Spot 옵션 B | **₩344만** | 중간 | 중간 | △ Plan B |
| **Composer 3 옵션 A** | **₩721만** | **낮음** | **높음** | **✅ Phase 1** |
| **Composer 3 옵션 B** | **~₩435~510만** | **낮음** | **높음** | **✅ Phase 2** |

### 1.2 GKE 가 더 저렴한데 왜 Composer 3 인가

GKE 옵션 B 와 Composer 3 옵션 B 의 차이 = 약 **₩150~170만/월** (연 ₩1,800~2,000만).

이 차이가 가져가는 것:
- ✅ **GKE 클러스터 / Triggerer / Cloud SQL / Memorystore HA 직접 관리 제거**
- ✅ **Google SSO + IAM 통합 권한 관리** (사내 LDAP 대체 가능)
- ✅ **자동 인프라 업그레이드** (보안 패치 / K8s 버전업 자동, [[13_Composer 3 환경 업그레이드 정책]])
- ✅ **Spot preemption 으로 인한 task 재시도 / lost work 위험 제거**
- ✅ **조핸 이슈 패턴 (GKE 자동 업그레이드 → Airflow 깨짐) 구조적 차단**

→ **운영 인력 0.5~1명 비용 미만으로 이 모든 책임을 Google 에 위임**. ROI 명확.

### 1.3 GKE 옵션은 언제

다음 조건 중 하나 이상 해당 시:
- Composer 3 가 **서울 리전 미지원** 으로 확정 → 오사카 latency / 데이터 주권 부담 큼
- **연 ₩2,000만+ 절감이 운영 인력 1명 비용을 명확히 상쇄**하는 규모일 때
- 사내 GKE 운영 역량 / 자동화가 이미 충분히 갖춰진 경우

→ 현재 우리 상황 (운영 인력 보수적, GCP 이관 첫 단계, 데이터 주권 중요) 에서는 **Composer 3 가 합리적**.

## 4. 핵심 사전 작업 (이관 전 필수)

### 🥇 1순위: Sensor → Trigger 전면 전환

> 효과: 워커 메모리 다이어트 **₩200~280만/월** 절감 + 자동 인프라 업그레이드 시 24h 유예 호환

| 작업 | 난이도 | 효과 |
|---|---|---|
| `athlon/airflow.py` 표준 sensor 들에 `deferrable=True` 추가 | 한 줄 × 5개 (1일) | 사내 거의 모든 DAG 에 즉시 반영 (factory 구조) |
| `AthlonQuerySensor` async 마이그레이션 | 중간 (1~2주) | 커스텀 sensor 의 70%+ 점유 시간 해소 |
| `BigqueryQuerySensor` → 표준 sensor 갈음 | 쉬움 (1~2일) | 추가 절감 |
| Triggerer 활성화 + capacity 튜닝 | 한 줄 (cfg) | Phase 1 진입 전제 |

→ 상세: [[7_2_리소스 다이어트 포인트]]

### 🥈 2순위: Manager 노드 다운사이즈

> 효과: ₩100만/월 추가 절감. 코드 변경 X.

- 현재: 24코어 × 2대 / 64 GB × 2대 (실측 메모리 9% 사용)
- 권장: **Composer 3 의 manager pool** 을 작은 사이즈로 (n4-standard-8 × 2대 수준)
- 자세히: [[7_1_실제 스펙 산정]] 의 2.2 ~ 3.1 절

### 🥉 3순위: 메타데이터 DB cleanup 정책

> 효과: Composer 3 업그레이드 가능성 확보 (DB > 20GB 면 업그레이드 불가)

- Airflow DAG run / task instance history retention 정책 (예: 90일)
- XCom 큰 데이터 → GCS 로 전환 (스냅샷/업그레이드 오류 방지)
- 자세히: [[5_Metadata DB 운영]]

## 5. 권장 마이그레이션 경로

### Phase 0 — 이관 전 사전 다이어트 (4~6주)

| 액션 | 담당 | 비고 |
|---|---|---|
| `athlon/airflow.py` sensor → deferrable 전환 | 코어 팀 | 1순위 |
| `AthlonQuerySensor` async 마이그레이션 | 코어 팀 | 2순위 |
| 메타DB retention / cleanup 정책 수립 | 운영 팀 | DB < 20GB 확보 |
| `max_active_runs`, `max_active_tasks` 명시 강제 | 코어 팀 | catchup 폭증 방지 |

→ **이 작업은 GCP 이관 여부와 무관하게 가치** (on-prem 에서도 즉시 비용/안정성 개선).

## 7. 발표 / 회의 메시지 (1슬라이드)

1. **방향**: Cloud Composer 3 (Airflow 3.1.7) 채택. PoC 호환성 ~80% 통과.
2. **비용**: 월 ₩721만 (Phase 1) → ₩435~510만 (Phase 2, sensor 다이어트 후). GCE 상시 대비 **-62~77%**.
3. **운영 가치**: Google SSO + IAM 권한 / 자동 인프라 업그레이드 / HA·메트릭 자동 / Cloud SQL · Redis 위임. 운영 인력 0.5~1명 비용 절약.
4. **사전 작업**: `athlon/airflow.py` 의 sensor → deferrable 전환 (1순위). 코드 한 줄 × 5곳 + 커스텀 sensor 2개 마이그레이션.
5. **타임라인**: Phase 0 (4~6주) + Phase 1 (4~8주) + Phase 2 (2~4주) = **약 3~5개월**.
6. **가장 큰 변수**: **Composer 3 서울 리전 지원 여부**. 미지원 시 GKE Plan B 로 전환.
