# 2. 문제 정의 — 왜 Cosmos + Asset 만으로 부족한가

## 시작점

Story 팀의 시연 파이프라인:

```
berriz_0101_bizberry_hourly_integration (producer, hourly)
    dbt_summary → export_to_kafka → signal
    dbt_overview_trend → export → signal
    dbt_userpost → export → signal
    dbt_artistpost → export → signal
        │
        │ (cosmos 자동 outlet: bigquery/.../table_integration)
        ▼
berriz_bizberry_downstream_demo (consumer)
    schedule=[SUMMARY_ASSET, OVERVIEW_TREND_ASSET]  ← AND
    mart_ready (EmptyOperator, 처리 로직 자리)
```

**의도**: Producer 의 mart 완료 → downstream 자동 트리거. ExternalTaskSensor 없이 event-driven.

**첫 인상**: 잘 됨. Cosmos 가 outlet 을 자동 부착해서 producer 는 `outlets=` 를 명시하지 않아도 됨.

**그런데 실사용에 가까이 가면**: 3가지 gap 이 드러남.

## Gap 1 — Payload 가 없다

### 증상

Cosmos 자동 outlet 은 URI 만 emit 하고, `extra` 에 아무것도 안 담는다.

Downstream 의 `triggering_asset_events` 에서 얻을 수 있는 것:

| 필드 | 값 | 채우는 주체 |
|---|---|---|
| `source_dag_id` | producer DAG id | Airflow 자동 |
| `source_task_id` | dbt run task id | Airflow 자동 |
| `source_run_id` | producer 의 run_id | Airflow 자동 |
| `timestamp` | event 생성 시각 | Airflow 자동 |
| `extra` | `{}` | ❌ 비어있음 |

**Downstream 이 "어느 파티션의 데이터냐" 를 알 방법이 없음.**

### 우회 방법 (모두 fragile)

**Option A — run_id 문자열 파싱**
```python
# "scheduled__2026-07-24T05:00:00+00:00" 형식 기대
_, iso = ev.source_run_id.split("__", 1)
logical_date = datetime.fromisoformat(iso)
```
- Backfill (`backfill__...`), manual (`manual__...`) run 은 형식이 다름
- Airflow minor 버전에서 format 이 바뀔 수 있음 (public API 아님)

**Option B — DagRun DB 조회**
```python
producer_dr = DagRun.find(dag_id=ev.source_dag_id, run_id=ev.source_run_id)[0]
logical_date = producer_dr.logical_date
```
- 정확하지만 매 event 마다 DB 조회
- Airflow internal API 의존 → 이식성 낮음

### 왜 Cosmos 가 stamp 를 안 해주나

Cosmos 의 outlet 은 dbt manifest 의 target relation 에서 URI 만 뽑아냄. **"이 model 이 이 시각에 실행됐다" 를 outlet 계약에 실을 이유가 없다** — dbt 는 SQL 실행기지 이벤트 브로커가 아니다.

Cosmos 버전에 따라 `extra` 에 dbt 자체 메타 (`{"model_name": ..., "materialization": ...}`) 정도가 들어가지만, **팀이 downstream 에서 쓸 시간축 payload 는 안 담김**.

## Gap 2 — 조건부 emit 이 없다

### 증상

Cosmos 의 dbt run task 는 성공하면 **무조건** outlet event 를 emit 한다.

Downstream 에서 문제가 되는 시나리오:

**시나리오 1 — Producer 백필**
- Producer 를 h1..h10 (10시간치) 백필
- 각 hour 별 dbt task 가 성공 → 10개 event emit
- Downstream 이 시나리오에 따라 1~10번 트리거
- **문제**: 시연 중이거나, downstream 이 알림 발송이면 알림 폭탄

**시나리오 2 — Downstream 이 특정 시간대만 필요**
- Producer 는 hourly, downstream 은 KST 자정 파티션만 처리하고 싶음
- Cosmos outlet 은 매 시간 emit → downstream 이 켜져서 스스로 필터
- **문제**: 매 시간 dag_run 이 생성되는 리소스 낭비 + UI 노이즈

### 무엇을 원했나

Producer 가 "이건 downstream 을 깨울 이벤트, 이건 아님" 을 **명시적으로 선택** 하고 싶다:

- Backfill run 은 downstream 안 깨움
- KST 23시 파티션만 EOD downstream 을 깨움
- QC 통과한 데이터만 downstream 을 깨움

Cosmos 자동 outlet 은 이 통제권을 주지 않음.

## Gap 3 — Partition 매칭이 없다

### 증상

`schedule=[Asset1, Asset2]` 의 AND 조건은 **"두 asset 이 각각 최소 1개 이상 갱신됐음"** 만 본다. **"같은 시간대의 짝"** 이라는 개념이 없다.

**예시**:
```
Producer 를 h1..h5 백필:
  이벤트: S1, O1, S2, O2, S3, O3, S4, O4, S5, O5
  (S=summary, O=overview_trend)
```

원하는 것: h1 짝 처리, h2 짝 처리, ... h5 짝 처리 (5회 downstream 실행, 각자 자기 hour 담당).

**실제 벌어지는 것**:
- 스케줄러는 시간축 매칭 안 함
- Downstream `max_active_runs=1` 상황에서:
  - dag_run #1 이 S1, O1 을 consume 하고 시작
  - 그 사이 S2..S5, O2..O5 가 다 대기
  - dag_run #1 종료 → dag_run #2 가 S2..S5 + O2..O5 를 **한 번에** consume
- **결과**: 5 짝인데 dag_run 은 2개, 매칭도 안 됨

### 왜 스케줄러가 매칭을 안 해주나

Airflow asset 은 **event-based** 이지 **partition-based 가 아니다**. Asset 은 원래 "이 리소스가 갱신됐다" 라는 **fact** 를 표현하도록 설계됐다. Fact 는 시간축에 묶이지 않음 — pub/sub 이벤트에 가까움.

전통적 Airflow 스케줄링 (ExternalTaskSensor) 은 `execution_delta` 로 1:1 시간 매칭이 되지만, asset 은 이 개념이 없다.

## 그래서 결국

**Cosmos 자동 outlet 만 쓴다** = downstream 에게 다음을 부담시킴:
- "언제의" 이벤트인지는 run_id 로 역추적
- 조건부 처리는 매번 dag_run 켜고 스스로 필터
- 파티션 매칭은 스스로 상태 관리

이건 downstream 이 producer 의 사정을 너무 많이 알아야 하고, 각 팀 downstream 이 같은 로직을 반복 재발명하게 만든다.

**필요한 것**: Producer 가 **self-describing event + 조건부 emit + partition-aware URI** 를 통제하는 layer. 이게 [[4_해결_패턴]] 에서 다룰 stamp task + AssetAlias 이유.

## 그런데 이건 Airflow 의 결함인가?

**아니다**. Airflow 3 는 도구를 다 제공한다:
- `outlet_events[asset].extra` 로 payload 세팅 가능
- `AirflowSkipException` 으로 조건부 emit 가능
- `AssetAlias` 로 partition-specific 구독 가능

**단지 Cosmos 자동 outlet 이 이 도구들을 사용하지 않을 뿐**. Cosmos 의 관심사가 "dbt 실행" 이라 payload / 조건 / alias 는 팀 코드가 담당해야 할 영역.

이걸 인식하면, "Cosmos 자동 outlet 이 부족하다" 가 아니라 **"Cosmos 는 dbt 만 하고 팀이 이벤트 계약을 얹어야 한다"** 로 프레임이 바뀐다. 이 프레임이 [[5_계층_분리_원칙]] 의 출발점.

## 요약

| Gap | 원인 | 해결 방향 |
|---|---|---|
| Payload 없음 | Cosmos 는 URI 만 emit | Stamp task 에서 `outlet_events[asset].extra` 세팅 |
| 조건부 emit 없음 | dbt 성공 = 무조건 emit | Stamp task 에서 `AirflowSkipException` 으로 조건 게이트 |
| Partition 매칭 없음 | Asset 은 event-based, 시간축 매칭 안 함 | Consumer 에서 payload 로 매칭 + dynamic task mapping |
