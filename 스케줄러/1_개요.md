# 스케줄러 — Cloud Composer 3 운영 방향

## 결론

> **Cloud Composer 3 (= 구글이 운영해주는 Airflow 3) 채택 방향.**
>
> 인프라 청구는 직접 띄우는 것보다 ~20~35% 비싸요. 그런데 **운영 인력 · 로그인 인증 · 무중단 운영 · DB/Redis 관리**를 구글이 알아서 해줘서, 그 가치가 더 큽니다. → 발표에서 강조할 부분.

## 0. 큰 그림 — Composer 쓰면 뭘 잃고 뭘 얻나

**잃는 것 (우리가 자유롭게 못 함)**

- 워커마다 다른 네트워크 / 다른 이미지 설정
- 시스템 패키지(apt-get 같은 거) 자유 설치
- DAG 배포 방식 자유 (GCS 방식만 가능)
- 로그인 방식 자유 (구글 Workspace 계정 강제 — Okta 같은 외부 IdP는 Workspace SSO 설정을 통해 우회로만 가능)
- Spot 인스턴스 · 약정 할인(CUD) 적용

**얻는 것 (구글이 알아서 해줌)**

- 워커 갯수 자동 조절 (트래픽 늘면 자동으로 늘어남)
- 스케줄러 무중단(HA) · 메트릭 · 로그 자동 셋업
- Redis · 메타DB 관리(백업/패치/모니터링) 위임
- 구글 SSO 로그인 자동 (사내 구글 계정으로 바로 로그인)
- 권한 부여를 GCP IAM에서 한 번에 (Airflow에 사용자 따로 만들 필요 X)

→ 우리 규모/팀에선 **위에 있는 자유보다 아래에 있는 위임 쪽이 더 이득**.

## 1. 환경 셋팅 (어떻게 띄웠나)

> _PoC에서 셋팅한 내용 정리 — 추후 채움_

| 항목 | 내용 |
|---|---|
| **GCS** | DAG 코드 / 플러그인 / 데이터 저장 폴더 구조 — _작성 예정_ |
| **네트워크** | VPC / 내부 IP / IAP 로그인 설정 — _작성 예정_ |
| **PyPI 패키지** | `requirements.txt` 에 적으면 자동 설치. 시스템 패키지(apt-get 종류)는 못 깔음 → 필요하면 KubernetesPodOperator로 별도 컨테이너 띄워서 처리 |

## 2. 어떻게 쓰게 되나 (Airflow 컴포넌트별)

### 2.1 Worker — 작업 실제로 실행하는 곳

|                         | Cloud Composer 3                     | 직접 구축               |
| ----------------------- | ------------------------------------ | ------------------- |
| 큐별로 워커 따로 두기            | ❌ 워커는 한 종류만                          | ⭕ 큐마다 다른 워커 띄울 수 있음 |
| 워커마다 네트워크 / 외부통신 다르게 설정 | ❌ 단일 (전체 동일)                         | ⭕ 워커별로 설정 가능        |
| **워커 갯수 자동 조절**         | **⭕ 자동** (Celery 워커 수가 자동으로 늘었다 줄었다) | ❌ 직접 구성             |

> **포인트**: 워커 갯수가 자동으로 늘었다 줄었다 하는 게 Composer 강점.
> 다만, 특별한 패키지나 다른 네트워크가 필요한 작업은 별도 Pod로 띄워야 함 (2.4 참고).

### 2.2 Scheduler — DAG 읽고 작업 분배하는 곳

|                           | Cloud Composer 3         | 직접 구축                      |
| ------------------------- | ------------------------ | -------------------------- |
| **무중단 운영(HA, 여러 대로 띄우기)** | ⭕ 자동                     | ❌ 직접 설정                    |
| **메트릭 / 모니터링**            | ⭕ Cloud Monitoring 자동 연결 | ❌ Prometheus 같은 거 직접 붙여야 함 |
| 로그 보기                     | ⭕ Cloud Logging 자동       | ❌ 직접 구성                    |

> **포인트**: 안 죽게 만들기 / 메트릭 보기 같은 운영 일이 그냥 따라옴.

### 2.3 Webserver — Airflow UI 띄우는 곳

|                            | Cloud Composer 3             | 직접 구축                 |
| -------------------------- | ---------------------------- | --------------------- |
| **UI 로그인**                 | ⭕ 구글 SSO 자동 (사내 계정으로 바로 로그인) | ❌ 직접 구성 (Okta/SAML 등) |
| **GCP 권한 → Airflow 권한 매핑** | ⭕ 자동 매핑                      | ❌ 사용자 이중 관리           |

> **포인트**: **로그인 / 권한 관리를 구글에 맡길 수 있는 게 가장 큼.**
> 신규 입사자 권한 부여, 퇴사자 권한 회수가 GCP IAM에서 한 번에 끝남.
>
> _참고: Okta 등 외부 IdP를 쓰고 싶다면 — Google Workspace의 SSO 설정에서 Okta를 SAML IdP로 등록하는 우회 방식으로 가능. 사용자 입장에선 Okta 로그인처럼 보이지만, 뒤에선 Workspace 계정이 broker 역할._

### 2.4 어떤 작업을 어디서 실행할까 (Celery vs Pod)

> **혼합 방식**: 가벼운 작업은 Celery로, 무거운/특수한 작업만 별도 Pod로.

**1) 어떻게 가르나**

작업마다 `executor` 옵션으로 정함:

```python
# 그냥 두면 → Celery 워커에서 실행 (가벼운 작업)
quick = BashOperator(task_id='quick', bash_command='echo hi')

# executor 명시하면 → 별도 Pod 띄워서 실행 (무거운 작업)
heavy = BashOperator(
    task_id='heavy',
    bash_command='dbt run --select large_model',
    executor="KubernetesExecutor",
    executor_config=HEAVY,
)
```

**2) Pod 사양은 미리 정해둔 프리셋에서 골라서 씀**

작업마다 일일이 Pod 스펙 쓰면 코드가 지저분해지니까, 자주 쓰는 사양을 미리 정의해두고 가져다 씀:

| 프리셋 | 메모리 | CPU | 비고 |
|---|---|---|---|
| `SMALL`  | 1Gi   | 0.5 | 가벼운 작업 |
| `MEDIUM` | 4Gi   | 2   | |
| `LARGE`  | 16Gi  | 8   | |
| `HEAVY`  | 32Gi  | 16  | 큰 노드 풀에서 실행 |
| `GPU`    | 16Gi  | 4   | GPU 노드에서 실행 |

→ DAG 작성자는 사이즈만 고르면 됨. "이건 LARGE로 돌려라" 정도.

**3) Pool — 동시 실행 갯수 제한**

너무 많이 한 번에 돌면 노드가 폭발하니까, 풀로 묶어서 제한.

- Airflow UI → Admin → Pools 에서 설정 (Composer / 직접 구축 동일)
- 예: `heavy_pool` 만들고 동시 5개까지만 허용

**4) Composer 3에서 되는 것 / 안 되는 것**

| 항목 | Composer 3 | 직접 구축 |
|---|---|---|
| `executor=KubernetesExecutor` 로 Pod 분리 | ⭕ | ⭕ |
| 프리셋 + 노드 지정 (`node_selector`) | ⭕ | ⭕ |
| **Celery 워커를 큐별로 나누기** | ❌ (워커 한 종류) | ⭕ |
| 이미지 미리 받아두기 (DaemonSet) | ⚠️ 노드 직접 제어 안 됨 | ⭕ |

> **포인트**: Composer 3에서도 **프리셋 + 노드 지정 방식은 그대로 동작**. 단 Celery 워커를 큐별로 못 쪼개니까 특수한 작업은 무조건 Pod로 빼야 함. 상세 — [[4_Queue 라우팅과 Pod 스펙 설정]]

## 3. Redis · 메타DB

> 구글이 알아서 **Redis(Memorystore)** + **PostgreSQL(Cloud SQL)** 띄워서 관리해줌.
> 우리가 직접 띄우거나 백업하거나 패치할 일 없음. **비용은 환경 비용에 통합 청구** (별도 청구 X).
>
> 직접 구축하면 이 두 개도 따로 띄워야 함 ([[5_Metadata DB 운영]] 참조).

## 4. 배포 (DAG 어떻게 올리나)

> **DAG Bundle (Airflow 3의 신규 배포 방식)은 못 씀** (PoC에서 확인).
> **GCS sync 방식만 가능** — GCS 버킷에 DAG 파일 올리면 Airflow가 읽어감.

운영안:

- GitHub Actions: PR merge → `gsutil cp` 로 GCS 버킷에 파일 sync
- 또는 외부에서 트리거 (Webhook → Cloud Function → GCS write)

> _상세 — [[11_DAG Bundles와 배포 전략]]_

## 6. 비용 (가장 신경 써서 설명할 부분)

> 표면적으론 Composer가 비싸 보이지만, **인건비까지 따지면 손익분기점이 달라짐**.

| 규모 | Composer 3 | 직접 구축 (정가) | 직접 구축 (Spot + 약정 할인) |
|---|---|---|---|
| 작음 (DAG 50개) | ~$300~500 | ~$400~550 | ~$250~350 |
| 중간 (DAG 200개) | ~$900~1,200 | ~$750~950 | ~$500~700 |
| 큼 (DAG 500개+) | ~$2,000~2,800 | ~$1,800~2,400 | ~$1,200~1,700 |

> - **Spot 인스턴스** = 갑자기 회수될 수 있는 대신 저렴한 서버 (~60~70% 할인)
> - **약정 할인(CUD)** = 1년/3년 약정 시 할인 (~25~55%)

**핵심 메시지 4개**:

1. **정가끼리는 비등** — Composer가 살짝 비싸지만 차이 작음
2. Spot + 약정 할인 풀로 쓰면 직접 구축이 -40~60% 저렴해 보이지만,
3. **여기에 운영 담당자 0.2~0.5명 분 인건비를 더하면 손익분기점이 뒤집힘** (월 인건비 > 인프라 절감액)
4. 게다가 직접 구축은 **무중단 운영 / 인증 / 모니터링**도 다 직접 만들어야 함
