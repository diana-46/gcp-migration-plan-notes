# 8. 실행 계획과 안전장치

> Phase 0~3 로 나눈 실행 계획, 각 phase 의 안전장치, DE 팀에 요청드리는 것.
> 관련: [[애슬론/6_마이그레이션 플랜]], [[스케줄러/0_결론]]

## Phase 0 — 준비 (4-6주)

### 목표

- 인프라 준비 (Composer 환경, Provider 패키지, dbt template, 팀 저장소 template)
- 지원 체계 (슬랙 채널, 워크샵, pair 프로그래밍)
- **OKR / 시간 확보 합의** (매니저 · 디렉터 사인오프)

### 완료 조건

- [ ] Composer 3 dev / integration 환경 세팅 (지금은 `test-airflow3`)
- [ ] `apache-airflow-providers-kakaoent-dataplatform` 최소 버전 배포 (완료: `0.3.0`)
- [ ] 팀 저장소 template 준비 (완료: `storydata-*` 셋업 완료)
- [ ] 자동 변환 도구 초기 버전 (Presto → BQ, Actions UI → Python DAG)
- [ ] `#dbt-support`, `#airflow-support` 슬랙 채널 활성화
- [ ] Story 팀 워크샵 1회 완료
- [ ] OKR 인정 문서 합의

### 안전장치

- 이 조건 미충족 시 **Phase 1 진입 보류**
- 옛 시스템 (Neptune / Actions UI) 그대로 유지 → 언제든 fallback

## Phase 1 — 얼리어답터 팀 이관 (4-8주)

### 목표

Story 팀이 대표 얼리어답터. Bizberry hourly workflow (10 개 ETL) 을 dbt + 팀별 DAG 로 이관.

### 진행 상황 (2026-07 기준)

- ✅ 4 mart 이관 완료 (userpost / artistpost / overview_trend / contents_summary)
- ✅ 저장소 셋업 완료 (`storydata-dbt`, `storydata-airflow-dags`)
- ✅ Provider 패키지 소비 검증 (`apache-airflow-providers-kakaoent-dataplatform==0.3.0`)
- ✅ Producer + Consumer DAG (Asset 기반) 실증
- 🧪 진행: 나머지 6 개 ETL 이관 (notice / media / live / fanclub_overview / fanclub_trend / community_overview)
- 📋 준비: Dual-run (Neptune vs dbt 결과 비교 1-2주)

### 안전장치

- **Dual-run**: Neptune 원본 vs dbt 산출물 자동 비교. 정합성 확인 후 dbt 단독.
- **Git revert**: 코드 실수 → PR 단위 되돌리기
- **BQ time travel**: 데이터 실수 → 7일 이내 복원
- **얼리어답터 우선**: 1-2 팀 성공 사례 후 확산
- **PR 리뷰 SLA**: 24시간 이내 응답 (플랫폼팀)
- **첫 3 개 DAG pair 프로그래밍**

## Phase 2 — 확산 (2-4주 x 팀 수)

### 목표

Phase 1 성공 사례를 기반으로 다른 팀 (kpayment, tissue 등) 이관.

### 진행

각 팀:
1. Story 팀 이관본 참고
2. 자동 변환 도구로 초안 생성
3. Story 팀 코드를 template 로 복사 → 수정
4. 팀별 dbt / DAG 저장소 셋업 (플랫폼팀 template)
5. Dual-run 검증
6. Prod 전환

### 안전장치

- Phase 1 의 안전장치 동일 적용
- Neptune / Actions UI 여전히 유지 (fallback)

## Phase 3 — Neptune 정리 (팀 수 × 2 주)

### 목표

전 팀 이관 완료 후 Neptune / athlon / Actions UI 정리.

### 순서

1. 모든 팀 Prod 전환 완료 확인 (dashboard)
2. Neptune Prod 트래픽 0 확인 (1개월)
3. athlon MySQL 접근 로그 확인 → 완전 idle 확인
4. Neptune / athlon / Actions UI shutdown
5. 관련 리소스 정리 (Hive metastore, HDFS 경로 등)

## 안전장치 요약

이관 전 과정 관통하는 안전장치:

| 안전장치 | 내용 |
|---|---|
| **Dual-run** | Neptune 산출물 vs dbt 산출물 자동 비교 1-2주 |
| **Git revert** | 코드 실수 → PR 단위 되돌리기 |
| **BQ time travel** | 데이터 실수 → 7일 이내 복원 가능 |
| **Tier 순서** | 단순 → 파티션 → YAML multi-temp 순 |
| **얼리어답터 우선** | 성공 사례가 다음 팀 참고 |
| **옛 시스템 유지** | Phase 3 전까지 Neptune / Actions UI 유지 |
| **자동 변환 도구** | Presto → BQ (~80% 커버리지 목표), YAML → dbt |
| **페어 프로그래밍** | 첫 3 개 DAG 는 플랫폼팀과 함께 |
| **PR 리뷰 SLA** | Phase 1-2 동안 24시간 이내 응답 |
| **Slack 실시간 지원** | `#dbt-support`, `#airflow-support` 최소 6개월 |

## 요청 사항

### 1. 얼리어답터

- Phase 1 에서 자기 팀 ETL 1-2 개 이관해주실 팀 모집
- Story 팀 사례가 참고
- 페어 프로그래밍 + PR 리뷰 지원

### 2. 피드백

- 이 문서 세트 [[README]] 부터 훑고, 논의할 점 남기기
- 특히 [[3_결정B_팀별_DAG_저장소]] 의 비용 · 리소스 논거에 대한 반응
- 걱정 · 우려 · 반박 환영 (Phase 0 조건에 반영)

### 3. 워크샵 참여

- Phase 0 온보딩 세션 팀별 2회
- dbt 기초 + Python DAG + PR 워크플로우

### 4. 자동 변환 도구 검증

- 각 팀 ETL 하나를 자동 변환해보고 커버리지 리뷰
- 남는 수동 작업이 어느 정도인지 정량화
