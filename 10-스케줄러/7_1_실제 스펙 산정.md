# 실제 스펙 기반 Composer 비용 산정 (GCE / GKE / Composer 3)

> [[7_Composer 비용]] 는 일반론. 본 문서는 **우리 현재 운영 스펙 + 30일 실측 사용률** 을 기준으로 GCE / GKE / Composer 3 세 가지로 옮겼을 때의 GCP 청구액을 산정한다.
>
> 서울 리전(asia-northeast3) 기준. on-demand 가격이 기본, 다이어트 시나리오 두 가지 (A: 현 상태 / B: 적극 다이어트) 병기.

## 0. 사전 지식 — DCU

**DCU (Data Compute Unit)** = Composer 3 의 추상 과금 단위. GCE/GKE 가 vCPU·메모리 단가로 직관적인 반면, Composer 3 는 둘을 묶어서 DCU 로 청구.

**환산식** (공식은 모호, [커뮤니티 리버스 엔지니어링](https://discuss.google.dev/t/cloud-composer-3-pricing-explanation/158381) 기준):

> `DCU/h ≈ vCPU 수 + GB RAM 수`
>
> 예: Composer 3 Small preset = 3 vCPU + 9 GB → 12 DCU/h ✅ 실측 일치

**소비 컴포넌트**: worker, scheduler, DAG processor, triggerer, web server  
→ worker 외엔 항상 떠있으므로 **DAG 0개여도 floor 비용 발생**.

**단가**:
- us-central1: $0.06 / DCU-hour (공식 사례)
- 서울 (asia-northeast3): **~$0.072 / DCU-hour 추정** ⚠️ 공식 확인 필요

**별도 청구** (DCU 에 안 포함): Cloud SQL 디스크, GCS 스토리지, 네트워크 egress.

### 1.3 ⚠️ 물리 코어 → GCP vCPU 매핑

**GCP 공식**: `1 vCPU = 1 hyperthread` (= **물리 코어의 절반**). on-prem N physical core (HT on) → GCP 동등 capacity 는 **2N vCPU**.

| 매핑 | 총 vCPU | 비고 |
|---|---|---|
| **B. HT 동등 (기본)** — core × 2 | **360 vCPU** | GCP 공식 가이드. 현 thread 수 그대로 보존 |
| A. 다운사이징 — core × 1 | 180 vCPU | CPU 사용률 낮을 때 가능 |

본 문서는 **B 방식 (360 vCPU, 352 GB)** 을 lift-and-shift 기준으로 잡고, 실측 사용률 기반 다이어트 시나리오를 별도 산정.

기존 엑셀의 30일 측정은 `sar -r` 의 컬럼 시프트 + `%memused` (buff/cache 포함) 가 섞여서 부풀려진 값이었음:

|---|---|---|---|

→ 특히 **Manager** 는 page cache 비중이 커서 큰 격차. 기존 견적에서 manager 메모리 다이어트 못 한다고 봤지만 **실측 기준으로는 큰 폭 가능**.

#### 인사이트

1. **Worker 는 진짜 memory-bound**. 피크 시 92~96% 메모리 사용. `worker_concurrency=8 × task당 ~3.6 GB`. → 메모리 다이어트의 lever 는 **노드 사양이 아니라 `worker_concurrency`**.
2. **Manager 는 메모리 압도적 과잉**. 64 GB 노드를 평균 6 GB 만 사용 (9%). CPU 도 평균 18% / 피크 38% → **manager 노드 큰 폭 다운사이즈 가능**.
3. **ext 는 평소 idle, CPU 만 간헐 풀가동**. Spot 0대 → 띄움 패턴이 정답.

### 1.5 worker_concurrency 와 메모리

```
worker_concurrency = 8
노드당 평균 메모리 = 15.8 GB → task 당 평균 ~2 GB
노드당 피크 메모리 = 28 GB  → task 당 피크 ~3.6 GB
```

→ task 당 메모리 부담은 클라우드에서도 동일. **워커 노드 메모리 사이즈는 `concurrency × task당 메모리` 로 결정**.

| `worker_concurrency` | 노드당 필요 RAM | sensor 다이어트 동반 필요? |
|---|---|---|
| **8 (현 상태)** | ~32 GB | X (현 상태 유지) |
| **4 (적극 다이어트)** | ~16 GB | ✅ deferrable sensor 전환 필수 (throughput 손실 보상) |

throughput 영향: concurrency 절반이면 동시 task 도 절반. 단 우리 워크로드는 상위 task 가 wait sensor 로 점유 시간이 길어서, **sensor → deferrable 전환 시 실 task 점유 시간 감소** 로 보상 가능. 자세한 분석은 [[7_2_리소스 다이어트 포인트]] (작성 예정).

### 3.4 GKE 의 특성

- ✅ Pod 단위 fine-grained 스케일링 + Spot 적극 활용 → 비용 최저

- ✅ HA / 롤링 업데이트 K8s 표준
- ⚠️ Kubernetes 운영 부담 (Pod 설계, autoscaler 튜닝, RBAC)
- ⚠️ Spot preemption 시 task 재시도 설계 필요

## 4. 시나리오 C — Cloud Composer 3

### 4.1 견적 (엑셀 기준)

| 항목 | 수량 | 월 비용 (USD) |
|---|---|---|
| Composer 3 standard milliDCU-hours | 64,686,760 milliDCU-h ≈ **64,687 DCU-h** | $4,968 |
| Composer 3 database storage | 40 GB | $9 |
| **합계** | | **$4,977 / 월 (~₩721만)** |

> ⚠️ **리전이 `asia-northeast2` (오사카)** — 서울은 Composer 3 미지원 가능성. 공식 확인 필요.

### 4.2 DCU 환산 의미

64,687 DCU-hour / 730h = **~88.6 DCU/h 평균**

`DCU/h ≈ vCPU + GB RAM` 으로 역산하면 환경에 **평균 ~90 unit (예: 30 vCPU + 60 GB)** 떠있는 셈. 워커 autoscale 로 24/7 풀가동보다는 낮음.

### 4.3 다이어트 가능성

- **concurrency 조정**: Composer 3 도 환경 변수로 `worker_concurrency` 설정 가능 → 워커 DCU 소비 감소 가능
- **deferrable sensor**: triggerer 가 별도 컴포넌트로 떠있어서 sensor task 점유시간 감소 효과 가능
- **단, Spot/CUD 적용 거의 불가** → GCE/GKE 만큼 큰 절감은 어려움

옵션 B 적용 시 DCU 가 ~30~40% 감소 가능 (추정) → **~$3,000~3,500/월 (₩430~510만)** 수준 추정. 단, **공식 calculator 재산정 필수**.

### 4.4 Composer 3 의 특성

- ✅ Airflow 운영 부담 거의 없음
- ✅ Autoscale 내장
- ❌ Spot/CUD 적용 거의 불가
- ❌ 서울 리전 미지원 가능성 — 오사카 사용 시 latency / 데이터 주권 이슈
- ❌ Pod 스펙 / 워커 풀 분리 같은 fine-tuning 제한

## 6. 결론 / 함의

1. **비용만 보면 GKE 옵션 B 가 압도적**: 월 ~₩344만, GCE 상시 대비 **82% 절감**. 단 코드 변경 (concurrency + sensor) 필요.

2. **옵션 A vs B 차이 ≈ ₩200만/월** (GKE 기준):
   - 옵션 A 는 인프라만 옮기는 lift-and-shift
   - 옵션 B 는 [[7_2_리소스 다이어트 포인트]] 의 sensor / executor_config 작업이 동반돼야 함
   - 작업 ROI: 한 번 코드 변경으로 **연 ₩2,400만 절감** → 충분히 큰 동기

3. **Composer 3 는 GKE 보다 ~₩170만/월 비쌈** (옵션 A 기준).
   - 운영 인력 비용을 그 차이로 흡수 가능한가가 의사결정 포인트
   - 단, **서울 리전 미지원** 이면 후보에서 사실상 빠짐

4. **Manager 다이어트 = 가장 손쉬운 추가 절감 ($600/월 수준)**:
   - 엑셀 견적의 manager pool (n4-standard-16 × 2) 를 **n4-standard-8 × 2** 로 줄여도 안전
   - 실측 메모리 9% / CPU 18% 라 충분
   - **이건 옵션 A 에도 즉시 적용 가능** — 코드 변경 없이

5. **Worker 는 진짜 memory-bound**:
   - 피크 시 메모리 94% 사용 → 클라우드에서도 RAM 보수적으로 잡아야
   - 옵션 B 가려면 **`worker_concurrency` 변경 + sensor 다이어트 동반 필수**
   - 그냥 메모리만 줄이면 OOM 직격

6. **추가 절감 여지 (모든 시나리오 공통)**:
   - **CUD 1년 약정**: GCE/GKE regular 부분 -25%
   - **deferrable sensor**: 워커 점유 시간 절감 → 노드 수 추가 감축 여지
   - **executor_config 도입**: task 별 메모리 명시로 K8s 환경 추가 효율화
