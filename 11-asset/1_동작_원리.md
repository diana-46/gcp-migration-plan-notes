# 1. 동작 원리 — Asset event 는 실제로 어떻게 흘러가는가

> [[2_문제_정의]] 에서 짚은 gap 을 이해하려면 asset 이 **DB → 스케줄러 → downstream** 3층에서 어떻게 다뤄지는지 알아야 한다.

## 3층 구조

```
┌────────────────────────────────────────────┐
│  Producer task (outlets=[Asset(...)])      │
│  task.execute() 성공                        │
└──────────────────┬─────────────────────────┘
                   │ emit
                   ▼
┌────────────────────────────────────────────┐
│  Layer 1: DB (asset_event 테이블)          │
│  row 하나씩 append, dedup 없음              │
└──────────────────┬─────────────────────────┘
                   │ 스케줄러 스캔
                   ▼
┌────────────────────────────────────────────┐
│  Layer 2: Scheduler (batching)             │
│  unconsumed event 를 dag_run 으로 묶음      │
└──────────────────┬─────────────────────────┘
                   │ dag_run 생성
                   ▼
┌────────────────────────────────────────────┐
│  Layer 3: Consumer (triggering_asset_events)│
│  raw event 리스트를 context 로 접근         │
└────────────────────────────────────────────┘
```

## Layer 1 — DB

### AssetEvent row 하나가 갖는 필드


| 필드                 | 값                         | 채우는 주체                  |
| ------------------ | ------------------------- | ----------------------- |
| `id`               | auto increment            | DB                      |
| `asset_id`         | Asset URI 의 내부 id         | DB (URI 로 lookup)       |
| `timestamp`        | event 생성 시각               | Airflow                 |
| `source_dag_id`    | producer DAG id           | Airflow                 |
| `source_task_id`   | outlet 이 붙은 task          | Airflow                 |
| `source_run_id`    | producer 의 run_id         | Airflow                 |
| `source_map_index` | dynamic task 인덱스 (없으면 -1) | Airflow                 |
| `extra`            | JSON dict, 기본 `{}`        | **Producer 가 명시적으로 세팅** |


### Emit 규칙

- Producer task 가 **성공 상태로 끝날 때만** emit
- Skipped / Failed 는 emit 안 함 — 이걸 이용한 게 stamp task 의 `AirflowSkipException` 게이트
- 같은 URI 에 여러 번 emit 하면 그만큼 row 가 append (dedup 없음)

### 스토리지 시사점

- Hourly producer 가 1년 도는 동안 **8,760 rows/URI** 축적
- AssetAlias 를 쓰면 concrete asset URI 가 partition 별로 다르므로 **URI 개수 자체도 증가**
- Retention 정책은 Airflow 3 기본 없음 (버전마다 다를 수 있음) → 운영 시 크기 모니터링 필요

## Layer 2 — Scheduler batching

### 판단 규칙

스케줄러가 downstream dag_run 을 만드는 시점:

1. Downstream 이 subscribe 하는 asset 들의 unconsumed event 를 확인
2. `schedule=[A, B]` (AND) 면 A 와 B 각각에 unconsumed event 가 최소 1개씩 있어야 함
3. `schedule=AssetAny(A, B)` (OR) 면 둘 중 하나에만 있어도 됨
4. 조건 만족 + downstream 이 실행 가능 상태 (`max_active_runs` 미만) → dag_run 생성
5. **생성된 dag_run 이 그 시점까지 unconsumed 인 event 를 모두 consume**

### "이벤트 개수 ≠ dag_run 개수" 의 근본 원인

같은 unconsumed 이벤트 여러 개가 하나의 dag_run 에 뭉쳐 들어감. 언제 뭉치느냐는:

- Downstream 이 놀고 있으면 → 조건 만족 즉시 dag_run 생성, 그 사이에 쌓인 이벤트 다 consume
- Downstream 이 이미 돌고 있으면 → 새 이벤트는 대기, 현재 run 끝나면 그동안 쌓인 것 한 번에 consume

**타이밍 나름**이라 backfill 같은 상황에서 예측이 어려움.

### 시나리오 예시

Producer 를 h1~h5 백필. Downstream 은 `schedule=[A, B]`, `max_active_runs=1`.

**시나리오 A — Producer 병렬 처리 빠름**

```
t0: h1 완료 → A, B emit
t0+: downstream dag_run #1 생성 (consume A_h1, B_h1)
t1: h2 완료 → A, B emit  (대기, downstream 도는 중)
t2: h3 완료 → A, B emit  (대기)
t3: h4 완료 → A, B emit  (대기)
t4: h5 완료 → A, B emit  (대기)
t5: dag_run #1 종료
t5+: 조건 재검사 → 대기 중 event 다 있음 → dag_run #2 생성 (consume A_h2..h5, B_h2..h5)

결과: 5 짝 → dag_run 2개
```

**시나리오 B — Downstream 처리 빠름**

```
t0: h1 완료 → A, B emit → dag_run #1 → 빠르게 종료
t1: h2 완료 → A, B emit → dag_run #2 → 빠르게 종료
...

결과: 5 짝 → dag_run 5개
```

**시사점**: Downstream 로직은 **"1개 dag_run 에 event 몇 개가 있어도 다 처리"** 로 짜야 안전.

## 스케줄링 매트릭스

`schedule` 파라미터의 다양한 형태:


| 문법                                           | 의미                                |
| -------------------------------------------- | --------------------------------- |
| `schedule=[A]`                               | A 갱신 시 트리거                        |
| `schedule=[A, B]`                            | A **AND** B (둘 다 갱신 시)            |
| `schedule=AssetAny(A, B)`                    | A **OR** B                        |
| `schedule=AssetAll(A, B)`                    | A AND B (명시적)                     |
| `schedule=[AssetAlias("...")]`               | Alias 아래 emit 된 모든 concrete asset |
| `schedule=AssetOrTimeSchedule(cron, assets)` | cron 트리거 **OR** asset 트리거         |
| `schedule=AssetTimetable(...)`               | 커스텀 조합 (고급)                       |


`AssetOrTimeSchedule` 은 하이브리드 케이스에 유용 — "매일 자정에도 돌고, upstream 완료 시에도 돔".

## Backfill 의 실제 동작

### Producer 백필

- Airflow CLI 로 `airflow backfill create ...` 실행
- 각 백필 run 이 실제 task 를 실행 → **outlet event 도 정상 emit**
- Downstream 이 asset scheduling 이면 트리거됨 (억제 옵션은 [[4_해결_패턴]] Pattern A 참조)

### Downstream 백필

- Asset 기반 downstream 은 `**airflow backfill` 명령이 잘 안 맞음** — 시간축으로 실행 인터벌을 지정하는 방식인데, downstream 이 asset event 로 트리거되니 개념이 어긋남
- 대신 producer 를 백필하면 downstream 이 자동으로 따라옴 (asset 방식의 자연스러운 흐름)
- 정말 downstream 만 재실행하려면: dag_run 을 clear → downstream 이 자기 asset event 를 다시 consume

### Manual trigger

- 사람이 UI/CLI 로 `airflow dags trigger` 하면 run_id 가 `manual__...`
- Outlet event 는 정상 emit → downstream 트리거됨
- Producer 를 수동 trigger 로 실행해도 downstream 에 파급

## 재실행 / clear 시 asset event

- Consumed event 는 재사용되지 않음 (Airflow 가 consumed 표시)
- Downstream dag_run 을 clear 하면 그 dag_run 이 consume 했던 이벤트도 unconsumed 로 되돌아감 → 재실행 시 다시 consume
- Producer task 를 clear 하고 재실행하면 outlet emit 이 다시 일어남 → downstream 이 새 이벤트로 트리거될 수 있음

## `outlet_events` API — producer 가 event 를 조작하는 인터페이스

Producer task 안에서 context 를 통해 이벤트를 커스터마이즈:

```python
@task(outlets=[MY_ASSET])
def stamp(**context):
    # extra 세팅 (Asset)
    context["outlet_events"][MY_ASSET].extra = {"partition": "20260724"}
    
    # AssetAlias 아래에 concrete asset 추가
    context["outlet_events"][MY_ALIAS].add(
        Asset("story://.../partition=20260724"),
        extra={"partition": "20260724"},
    )
```

이게 stamp task 의 핵심 API. Consumer 에서 오는 이벤트의 payload 는 여기서 결정됨.

## 요약 표


| 층위        | 무엇을 관리                                 | 시사점                                |
| --------- | -------------------------------------- | ---------------------------------- |
| DB        | AssetEvent row (append-only)           | Retention 필요, backfill 시 크기 급증     |
| Scheduler | Unconsumed event → dag_run batching    | 이벤트 개수와 dag_run 개수 불일치             |
| Consumer  | triggering_asset_events 로 raw event 접근 | Payload 없으면 producer 정보 유도 fragile |
