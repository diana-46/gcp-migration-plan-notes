# 4. 해결 패턴 — Stamp task + AssetAlias + Dynamic mapping

> [[2_문제_정의]] 의 3가지 gap 을 [[1_동작_원리]] 의 API 로 메꾸는 실전 패턴.

## 패턴 지도

| Gap | 대응 패턴 | 층위 |
|---|---|---|
| Payload 없음 | **Pattern A** — Stamp task + `outlet_events[...].extra` | Producer |
| 조건부 emit 없음 | **Pattern A-ext** — `AirflowSkipException` 게이트 | Producer |
| Partition 매칭 없음 | **Pattern B** — AssetAlias fan-out<br>**Pattern C** — Consumer dynamic mapping | Producer + Consumer |

세 패턴은 독립적으로 도입 가능하고, 함께 쓸 때 시너지가 큼.

---

## Pattern A — Stamp task (self-describing event)

### 목적

Producer 완료 시점에 **팀이 명시한 payload** 를 asset event 에 실어 downstream 에 전달.

### 코드

```python
from airflow.sdk import Asset, task
from airflow.exceptions import AirflowSkipException

SUMMARY_READY = Asset("story://berriz/bizberry/summary_hourly_ready")

@task(outlets=[SUMMARY_READY])
def stamp_summary_ready(**context):
    dr = context["dag_run"]
    start = context["data_interval_start"]
    kst = start.in_timezone("Asia/Seoul")
    
    # 조건부 emit 게이트
    if dr.run_type == "backfill":
        raise AirflowSkipException("backfill 은 downstream 안 깨움")
    
    # Payload 세팅
    context["outlet_events"][SUMMARY_READY].extra = {
        "partition_kst": kst.strftime("%Y%m%d%H"),
        "kst_date": kst.strftime("%Y%m%d"),
        "kst_hour": kst.hour,
        "kst_weekday": kst.isoweekday(),  # 1=월, 7=일
        "execution_date_utc": start.isoformat(),
        "producer_dag_id": dr.dag_id,
        "producer_run_id": dr.run_id,
        "producer_run_type": dr.run_type,
    }

# 배선
dbt_summary >> export_to_kafka >> signal >> stamp_summary_ready()
```

### 표준 payload 필드 (제안)

| 필드 | 타입 | 설명 |
|---|---|---|
| `partition_kst` | str `YYYYMMDDHH` | KST 파티션 키 (hourly 기준) |
| `kst_date` | str `YYYYMMDD` | KST 일자 (일단위 그룹핑용) |
| `kst_hour` | int 0~23 | KST 시각 (EOD 판정용) |
| `kst_weekday` | int 1~7 | KST 요일 (EOW 판정용) |
| `execution_date_utc` | ISO 8601 | UTC 기준 timestamp |
| `producer_dag_id` | str | 소스 DAG |
| `producer_run_id` | str | 소스 run |
| `producer_run_type` | str | scheduled/backfill/manual |

Provider 로 표준화하면 [[7_Provider_확장_제안]] Pattern B 처럼 operator 가 자동 세팅.

### 조건부 emit 예시

**Backfill 억제**
```python
if dr.run_type == "backfill":
    raise AirflowSkipException("backfill")
```

**특정 시간대만**
```python
if kst.hour not in [0, 6, 12, 18]:
    raise AirflowSkipException("6시간 간격만 emit")
```

**QC 통과 후에만**
```python
qc_result = context["ti"].xcom_pull(task_ids="qc_task", key="passed")
if not qc_result:
    raise AirflowSkipException("QC 미통과, downstream 안 깨움")
```

**Feature flag**
```python
from airflow.models import Variable
if not Variable.get("bizberry_downstream_enabled", default_var=True):
    raise AirflowSkipException("feature flag off")
```

### 왜 skip 이 안전한가

Airflow 의 outlet emit 은 **task 가 성공 상태로 끝났을 때만** 발생. Skip 은 emit 대상 아님. 즉 `AirflowSkipException` 을 던지면:

- Task 는 skipped 상태
- Outlet event 는 emit 안 됨
- Downstream 은 트리거되지 않음
- DAG 자체는 정상 종료 (skip 이 실패로 취급되지 않음)

### 시사점

- Stamp task 는 **"downstream 을 깨우는 결정" 이 응집되는 지점**. 조건이 코드로 명시적
- Producer 파일을 리뷰할 때 "언제 downstream 이 뜨는가?" 를 stamp task 만 보면 됨
- 조건이 바뀌면 stamp task 만 수정. Downstream 은 무관

## Pattern B — AssetAlias 로 partition-specific 구독

### 목적

같은 producer 이벤트를 **downstream 마다 다른 조건**으로 골라 받게 함. Filtering 로직을 subscription 자체에 인코딩.

### 코드 — Producer 쪽

```python
from airflow.sdk import Asset, AssetAlias

# 채널 3개
SUMMARY_HOURLY = AssetAlias("story.berriz.bizberry.summary.hourly_ready")
SUMMARY_EOD    = AssetAlias("story.berriz.bizberry.summary.eod_ready")
SUMMARY_EOW    = AssetAlias("story.berriz.bizberry.summary.eow_ready")

@task(outlets=[SUMMARY_HOURLY, SUMMARY_EOD, SUMMARY_EOW])
def stamp_summary_ready(**context):
    dr = context["dag_run"]
    kst = context["data_interval_start"].in_timezone("Asia/Seoul")
    
    if dr.run_type == "backfill":
        raise AirflowSkipException("backfill")
    
    partition = kst.strftime("%Y%m%d%H")
    concrete = Asset(f"story://berriz/bizberry/summary_ready/{partition}")
    extra = {
        "partition_kst": partition,
        "kst_date": kst.strftime("%Y%m%d"),
        "kst_hour": kst.hour,
        "kst_weekday": kst.isoweekday(),
        "producer_run_id": dr.run_id,
    }
    
    # 매 시간 채널: 무조건
    context["outlet_events"][SUMMARY_HOURLY].add(concrete, extra=extra)
    
    # EOD 채널: KST 23시만
    if kst.hour == 23:
        context["outlet_events"][SUMMARY_EOD].add(concrete, extra=extra)
    
    # EOW 채널: 일요일 KST 23시만
    if kst.hour == 23 and kst.isoweekday() == 7:
        context["outlet_events"][SUMMARY_EOW].add(concrete, extra=extra)
```

### 코드 — Consumer 쪽

**Hourly downstream**
```python
with DAG(
    dag_id="bizberry_hourly_downstream",
    schedule=[SUMMARY_HOURLY],
    catchup=False,
    max_active_runs=1,
) as dag:
    ...  # 매 시간 처리
```

**EOD downstream**
```python
with DAG(
    dag_id="bizberry_eod_rollup",
    schedule=[SUMMARY_EOD],   # KST 23시에만 트리거
    catchup=False,
) as dag:
    @task
    def rollup_day(**context):
        # 지난 24시간 파티션을 종합해 일단위 집계
        ...
    rollup_day()
```

**EOW downstream**
```python
with DAG(
    dag_id="bizberry_eow_report",
    schedule=[SUMMARY_EOW],   # 일요일 KST 23시에만
    catchup=False,
) as dag:
    ...  # 주간 리포트
```

### 이 구조의 장점

**1. Producer 가 도메인 지식으로 채널을 나눔**
"KST 23시가 하루의 끝이다" 라는 판단은 데이터 도메인 지식. Producer 가 이 판단을 담당하고, downstream 은 채널만 subscribe.

**2. Consumer 는 조건을 선언적으로 표현**
Consumer 코드에 "hour == 23 일 때만" 이라는 조건 없음. `schedule=[SUMMARY_EOD]` 만으로 표현됨.

**3. 새 downstream 이 필요하면 alias 추가만**
- 예: "매월 말일 파티션만" → `SUMMARY_EOM` alias 추가
- Producer stamp task 에 조건 한 줄 (`if kst.day == kst.days_in_month`)
- Consumer 는 그 alias 만 subscribe

**4. Lineage 상 partition 단위 추적 가능**
Concrete asset URI 에 partition 이 박혀 있어서, Airflow UI / DataHub 에서 partition 단위 dependency 를 볼 수 있음.

### 시사점

- Asset registry 크기가 partition 개수만큼 증가. Hourly x 30일 = 720 rows/mart. 대규모 운영 전 retention 정책 확인 필요
- Alias 이름은 조직 컨벤션 필요 (`{team}.{domain}.{mart}.{condition}_ready` 등)
- Consumer 가 AND 조건 필요하면 alias 여러 개 subscribe (`schedule=[SUMMARY_EOD, OVERVIEW_EOD]`)

## Pattern C — Consumer 쪽 dynamic task mapping

### 목적

한 dag_run 에 여러 event 가 뭉쳐 와도 partition 별로 병렬 처리. [[1_동작_원리]] 의 batching 문제 흡수.

### 코드

```python
from collections import defaultdict
from airflow.sdk import task

@task
def unpack_events(**context):
    """triggering_asset_events → partition 별로 group."""
    by_partition = defaultdict(dict)
    
    for asset, events in context["triggering_asset_events"].items():
        for ev in events:
            partition = ev.extra["partition_kst"]
            # asset 종류 판별 (URI 로)
            kind = "summary" if "summary" in asset.uri else "overview"
            by_partition[partition][kind] = ev.extra
    
    # 모든 subscribed asset 이 다 온 partition 만 반환
    matched = [
        {
            "partition_kst": p,
            "summary_extra": v["summary"],
            "overview_extra": v["overview"],
        }
        for p, v in by_partition.items()
        if "summary" in v and "overview" in v
    ]
    return matched

@task(max_active_tis_per_dag=4)
def process_partition(payload: dict):
    """partition 하나를 처리."""
    partition = payload["partition_kst"]
    # BQ 쿼리, 알림 발송 등
    ...

process_partition.expand(payload=unpack_events())
```

### 무엇을 흡수하는가

**시나리오**: Producer 백필로 h1..h5 (5짝) 이 한 번의 dag_run 에 몰려 옴.

- `triggering_asset_events` 에 event 10개 (2 asset x 5 partition)
- `unpack_events` 가 partition 별로 group → 5개 dict 반환
- `process_partition.expand(...)` → **5개 병렬 task** 자동 생성
- 각 task 는 자기 partition 만 처리

**결과**: dag_run 개수가 몇 개든 상관없이 **partition 별 정확히 1번 처리** 보장.

### 매칭 안 된 event 처리

**Orphan event** (예: summary 만 오고 overview 는 아직 안 옴):
```python
# unpack_events 안에서
orphans = [p for p, v in by_partition.items() if len(v) < 2]
if orphans:
    context["ti"].log.warning(f"orphan partitions: {orphans}")
    # 다음 dag_run 에서 짝이 도착하면 다시 등장할 것
```

Airflow 는 consumed event 를 재사용하지 않으므로, orphan 이 다음 run 에서 다시 오려면:
- 짝이 도착해서 자연스럽게 다음 dag_run 이 뜰 때, orphan 도 그 dag_run 에 포함되지 않음 (이미 consumed)
- 이걸 원하면 별도 상태 저장 필요 (BQ / Variable / XCom 외부화)
- 실무적으로는 **"짝이 항상 함께 온다" 를 producer 에서 보장** 하는 게 정답 (예: 같은 stamp task 가 두 asset 모두 emit)

### 시사점

- Consumer 는 event count 에 무관한 로직으로 짤 수 있음
- Backfill / normal 흐름을 같은 코드로 처리
- `max_active_tis_per_dag` 로 병렬도 제어

## 세 패턴 조합 예시 (Story 팀 실제 적용안)

```python
# Producer: berriz_0101_bizberry_hourly_integration.py
from airflow.sdk import Asset, AssetAlias, task
from airflow.exceptions import AirflowSkipException

SUMMARY_HOURLY = AssetAlias("story.berriz.bizberry.summary.hourly_ready")
SUMMARY_EOD    = AssetAlias("story.berriz.bizberry.summary.eod_ready")

@task(outlets=[SUMMARY_HOURLY, SUMMARY_EOD])
def stamp_summary_ready(**ctx):
    dr = ctx["dag_run"]
    kst = ctx["data_interval_start"].in_timezone("Asia/Seoul")
    
    if dr.run_type == "backfill":
        raise AirflowSkipException("backfill")
    
    partition = kst.strftime("%Y%m%d%H")
    concrete = Asset(f"story://berriz/bizberry/summary_ready/{partition}")
    extra = {
        "partition_kst": partition,
        "kst_date": kst.strftime("%Y%m%d"),
        "kst_hour": kst.hour,
        "producer_run_id": dr.run_id,
    }
    ctx["outlet_events"][SUMMARY_HOURLY].add(concrete, extra=extra)
    if kst.hour == 23:
        ctx["outlet_events"][SUMMARY_EOD].add(concrete, extra=extra)

# 기존 chain 뒤에 붙임
dbt_summary >> export >> signal >> stamp_summary_ready()
```

```python
# Consumer: bizberry_eod_rollup.py
with DAG(schedule=[SUMMARY_EOD], ...) as dag:
    
    @task
    def unpack(**ctx):
        dates = set()
        for evs in ctx["triggering_asset_events"].values():
            for ev in evs:
                dates.add(ev.extra["kst_date"])
        return sorted(dates)
    
    @task
    def rollup_day(kst_date: str):
        # BQ 에서 kst_date 의 24시간 파티션 스캔해 일단위 집계
        ...
    
    rollup_day.expand(kst_date=unpack())
```

## 조합의 힘

| 조합 | 얻는 것 |
|---|---|
| A only | Payload + 조건부 emit. AND 매칭은 여전히 스케줄러 |
| A + B | + Partition-specific 구독. Consumer 조건 로직 사라짐 |
| A + B + C | + Backfill / event batching 안전 흡수. 완전한 실전 준비 |

Story 팀 목표는 **A + B + C** 다.
