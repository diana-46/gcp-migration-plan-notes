# 스케줄러 — Cloud Composer 3 운영 방향

## 결론

> **Cloud Composer 3 (= 구글이 운영해주는 Airflow 3) 채택 — 확정.**
>
> 인프라 청구는 직접 띄우는 것(GKE)보다 비싸지만, **운영 인력 · 로그인 인증 · 무중단 운영 · DB/Redis 관리**를 구글에 위임하는 가치가 더 크다.
> 채택 근거·비용 대표 수치(실측)·잔여 리스크의 **유일본은 [[0_결론]]** — 이 문서는 "채택 후 어떻게 운영하나"만 다룬다.

## 0. 큰 그림 — Composer 쓰면 뭘 잃고 뭘 얻나

**잃는 것 (우리가 자유롭게 못 함)**

- 워커마다 다른 네트워크 / 다른 이미지 설정
- 시스템 패키지(apt-get 같은 거) 자유 설치
- DAG 배포 방식 자유 (GCS 방식만 가능)
- 로그인 방식 자유 (구글 Workspace 계정 강제 — Okta 같은 외부 IdP는 Workspace SSO 설정을 통해 우회로만 가능)
- Spot 인스턴스 · 약정 할인(CUD) 적용

**얻는 것 (구글이 알아서 해줌)**

- 워커 갯수 자동 조절 (트래픽 늘면 자동으로 늘어남)
- 스케줄러 무중단(HA) · 메트릭 · 로그 자동 셋업
- Redis · 메타DB 관리(백업/패치/모니터링) 위임
- 구글 SSO 로그인 자동 (사내 구글 계정으로 바로 로그인)
- 권한 부여를 GCP IAM에서 한 번에 (Airflow에 사용자 따로 만들 필요 X)

→ 우리 규모/팀에선 **위에 있는 자유보다 아래에 있는 위임 쪽이 더 이득**.

## 1. 환경 셋팅 (어떻게 띄웠나)

### 1.1 환경 사양 — 워크로드 구성 + 핵심 인프라

Composer 3 환경은 **두 영역**으로 나뉘어 사양 결정:

```
[Composer 3 환경]
  ├─ 워크로드 구성 (개별 설정)   ← 컴포넌트별 vCPU/메모리/스토리지 직접 조정
  │   ├─ 스케줄러
  │   ├─ DAG 프로세서
  │   ├─ 트리거
  │   ├─ 웹 서버
  │   └─ 작업자 (워커, autoscale min~max)
  │
  └─ 핵심 인프라 (환경 크기)      ← 사실상 메타DB (Cloud SQL) 사양만
      └─ 환경 크기: 소형 / 중형 / 대형
```

> **포인트**: 컴포넌트별 부하가 달라서 분리 운영. 예: deferrable sensor 많이 쓰면 트리거만 크게, 작은 DAG 많으면 DAG 프로세서만 크게. 한 통으로 묶으면 낭비.

#### 현재 PoC (`test-airflow3`)

| 컴포넌트 | 사양 | 개수 |
|---|---|---|
| 스케줄러 | vCPU 1 / 메모리 4GB / 스토리지 1GB | 1 |
| DAG 프로세서 | vCPU 1 / 메모리 4GB / 스토리지 1GB | 1 |
| 트리거 | vCPU 1 / 메모리 2GB / 스토리지 1GB | 1 |
| 웹 서버 | vCPU 1 / 메모리 4GB / 스토리지 1GB | 1 |
| 작업자 | vCPU 0.5 / 메모리 2.5GB / 스토리지 10GB | 1~2 (autoscale) |
| **환경 크기** | **소형** (메타DB 1 vCPU / 3.75GB) | — |

추정 월 비용: ~$300~400

#### 실제 환경 사양 / 비용 (유일본 위임)

- **실구축 사양의 정본** = [[6_Composer3 신규 환경 구축 (Terraform)]] (dev/prod 실제 스펙, `asia-northeast3`)
- **사양·비용 산정 근거** = [[1_실제 스펙 산정]] (30일 실측 사용률 → Composer 환산), 대표 비용 수치 = [[0_결론]] §1.1
- 운영 원칙: **시작은 보수적으로**, 모니터링 후 조정. 워크로드 구성은 거의 무중단 변경 가능, **환경 크기(메타DB)는 1~2시간 다운타임**이므로 신중히.
- 환경 크기 3단(소형 1vCPU/3.75GB · 중형 2vCPU/7.5GB · 대형 4vCPU/15GB)은 메타DB 사양 선택 — 규모 산정은 7_1 참조.

#### 모니터링 — 사양 조정 시점

운영 시작 후 다음 지표 보고 조정:

| 지표 | 임계치 | 조정 |
|---|---|---|
| Scheduler heartbeat 지연 | > 10초 | 스케줄러 vCPU ↑ |
| DAG parsing time | > 30초 | DAG 프로세서 사양 ↑ |
| Worker autoscale 항상 max | 매일 max 도달 | 작업자 max ↑ |
| Worker autoscale 거의 min | 평균 1~2 | max ↓ (비용 절감) |
| Cloud SQL CPU | > 70% 지속 | 환경 크기 ↑ |
| Webserver 응답 | > 3초 지속 | 웹 서버 사양 ↑ |
| Triggerer 부하 | deferrable task 많음 | 트리거 vCPU ↑ |

→ 콘솔 → 환경 → 모니터링 탭에서 모두 확인.

### 1.2 기타 환경 설정

| 항목 | 내용 |
|---|---|
| **GCS** | DAG 코드 / 플러그인 / 데이터 저장 폴더 구조 — _작성 예정_ |
| **네트워크** | VPC / 내부 IP / IAP 로그인 설정 — _작성 예정_ |
| **PyPI 패키지** | `requirements.txt` 에 적으면 자동 설치. 시스템 패키지(apt-get 종류)는 못 깔음 → 필요하면 KubernetesPodOperator로 별도 컨테이너 띄워서 처리 |
| **사내 wheel** | Artifact Registry + pip.conf 셋업 (PoC 검증 완료, [[PoC/03_custom_operator_pypi]]) |

## 2. 어떻게 쓰게 되나 (Airflow 컴포넌트별)

### 2.1 Worker — 작업 실제로 실행하는 곳

|                         | Cloud Composer 3                     | 직접 구축               |
| ----------------------- | ------------------------------------ | ------------------- |
| 큐별로 워커 따로 두기            | ❌ 워커는 한 종류만                          | ⭕ 큐마다 다른 워커 띄울 수 있음 |
| 워커마다 네트워크 / 외부통신 다르게 설정 | ❌ 단일 (전체 동일)                         | ⭕ 워커별로 설정 가능        |
| **워커 갯수 자동 조절**         | **⭕ 자동** (Celery 워커 수가 자동으로 늘었다 줄었다) | ❌ 직접 구성             |

> **포인트**: 워커 갯수가 자동으로 늘었다 줄었다 하는 게 Composer 강점.
> 다만, 특별한 패키지나 다른 네트워크가 필요한 작업은 별도 Pod로 띄워야 함 (2.4 참고).

### 2.2 Scheduler — DAG 읽고 작업 분배하는 곳

|                           | Cloud Composer 3         | 직접 구축                      |
| ------------------------- | ------------------------ | -------------------------- |
| **무중단 운영(HA, 여러 대로 띄우기)** | ⭕ 자동                     | ❌ 직접 설정                    |
| **메트릭 / 모니터링**            | ⭕ Cloud Monitoring 자동 연결 | ❌ Prometheus 같은 거 직접 붙여야 함 |
| 로그 보기                     | ⭕ Cloud Logging 자동       | ❌ 직접 구성                    |

> **포인트**: 안 죽게 만들기 / 메트릭 보기 같은 운영 일이 그냥 따라옴.

### 2.3 Webserver — Airflow UI 띄우는 곳

|                            | Cloud Composer 3             | 직접 구축                 |
| -------------------------- | ---------------------------- | --------------------- |
| **UI 로그인**                 | ⭕ 구글 SSO 자동 (사내 계정으로 바로 로그인) | ❌ 직접 구성 (Okta/SAML 등) |
| **GCP 권한 → Airflow 권한 매핑** | ⭕ 자동 매핑                      | ❌ 사용자 이중 관리           |

> **포인트**: **로그인 / 권한 관리를 구글에 맡길 수 있는 게 가장 큼.**
> 신규 입사자 권한 부여, 퇴사자 권한 회수가 GCP IAM에서 한 번에 끝남.
>
> _참고: Okta 등 외부 IdP를 쓰고 싶다면 — Google Workspace의 SSO 설정에서 Okta를 SAML IdP로 등록하는 우회 방식으로 가능. 사용자 입장에선 Okta 로그인처럼 보이지만, 뒤에선 Workspace 계정이 broker 역할._

### 2.4 어떤 작업을 어디서 실행할까

> **기본은 Celery + Triggerer.** 가벼운 작업은 Celery 워커, 대기성 작업(sensor)은 deferrable + Triggerer.
> **아주 무거운/특수한 작업만 K8s Operator로 별도 실행** (예: Spark 은 GKE Spark Operator 에 `SparkApplication` CRD 제출 — [[../spark-apps/2_Composer에서 GKE Spark Operator 제출]] 검증 완료).

- ⚠️ Composer 3 의 `executor="KubernetesExecutor"` 는 **비추** — cold start 7분 46초 실측 + idle 즉시 deprovision(warm 불가). heavy task 는 Celery worker 사양 상향 또는 별도 GKE 제출 ([[PoC/04_worker_pool_queue]] · [[0_결론]] §2).
- ⚠️ **`queue=` 파라미터는 묵음 실패** — `default` 외 queue 의 task 는 에러 없이 영원히 queued. 이관 시 전부 제거 필수 ([[PoC/04_worker_pool_queue]]).
- 동시 실행 제한은 **Airflow Pool** 로 (예: `heavy_pool` slot 5). Pool 동작은 PoC 검증 완료.
- Pod 스펙·라우팅 메커니즘 상세의 유일본 — [[1_Queue 라우팅과 Pod 스펙 설정]]

## 3. Redis · 메타DB

> 구글이 알아서 **Redis(Memorystore)** + **PostgreSQL(Cloud SQL)** 띄워서 관리해줌.
> 우리가 직접 띄우거나 백업하거나 패치할 일 없음. **비용은 환경 비용에 통합 청구** (별도 청구 X).
>
> 직접 구축하면 이 두 개도 따로 띄워야 함 ([[2_Metadata DB 운영]] 참조).

## 4. 배포 (DAG 어떻게 올리나)

> **DAG Bundle (Airflow 3의 신규 배포 방식)은 못 씀** (PoC에서 확인).
> **GCS sync 방식만 가능** — GCS 버킷에 DAG 파일 올리면 Airflow가 읽어감.

운영안:

- GitHub Actions: PR merge → `gsutil cp` 로 GCS 버킷에 파일 sync
- 또는 외부에서 트리거 (Webhook → Cloud Function → GCS write)

> _상세 — [[5_DAG Bundles와 배포 전략]]_

## 5. 권한 관리

> **GCP IAM(접근 게이트) + Airflow FAB RBAC(UI 내 액션) 2단 구조** — PoC 확인 완료.
> 신규 입사 = IAM Role 부여(Google Group 추천) → 자동 등록, 퇴사 = IAM 회수. 운영 부담 매우 낮음.
>
> Role 모델·CLI·함정(12h 캐시, 재등록, DAG 단위 권한, Okta 직결 불가)의 **유일본 — [[4_Composer 권한 및 인증]]**
