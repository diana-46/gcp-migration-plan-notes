# 8. 시연 스토리라인 — Chapter 1~5

> Story 팀이 관계자에게 asset scheduling 을 시연할 때의 흐름. 단순 "새 기능 소개" 가 아니라 **"asset 을 사용해야 할 자리와 그 실전 설계 원칙"** 을 전달하는 이야기.

## 시연 목표

1. Asset scheduling 의 **정확한 유효 범위** 를 전달 (sensor 완전 대체가 아님)
2. Cosmos + stamp task 의 **계층 분리 원칙** 을 이해시킴
3. Provider 확장 제안을 자연스러운 후속 로드맵으로 제시

**청중**: 데이터플랫폼팀, 다른 팀 리드, 매니저.

**청중이 얻어갈 것**:
- "우리 팀 DAG 에서 asset 을 어떻게 도입할지" 판단 프레임
- Story 팀의 실전 발견 (gap 3가지 + 해결 3가지)
- 다음 조직 차원 액션 (provider 확장)

## Chapter 1 — Cosmos 자동 outlet 의 편의성

### 스크립트

> "우선 Airflow 3 의 asset scheduling 과 Cosmos 자동 outlet 이 얼마나 편한지부터 보여드리겠습니다. 이 두 DAG 을 보시죠."

**보여줄 것**:
- `berriz_0101_bizberry_hourly_integration.py` — producer
- `berriz_bizberry_downstream_demo.py` — consumer

**하이라이트**:
```python
# Producer: outlets= 를 명시적으로 안 씀. Cosmos 가 자동 부착
dbt_summary = DbtTaskGroup(...)

# Consumer: 그 URI 만 알면 subscribe
schedule = [Asset("bigquery://project.dataset.bizberry_..._integration")]
```

**메시지**:
- Producer 는 "내가 뭘 만드는지" 만 알면 됨
- Consumer 는 "내가 뭘 소비하는지" 만 알면 됨
- ExternalTaskSensor 대비 worker slot 절약, event-driven

### 시각 자료

Airflow UI 스크린샷:
- Producer 의 dbt task 완료 → downstream 이 자동 트리거되는 모습
- Assets 탭에서 URI 등록 확인

## Chapter 2 — 실제로 붙여보면 나오는 3가지 gap

### 스크립트

> "이렇게 시작했는데, 실제 downstream 로직을 넣어보니 3가지 부족한 점이 드러났습니다. 하나씩 보여드리겠습니다."

### Gap 1 — Payload 없음

**시연**:
```python
# Downstream 에서 producer 정보를 꺼내보려 하면...
@task
def check(**ctx):
    for asset, events in ctx["triggering_asset_events"].items():
        for ev in events:
            print(ev.extra)   # → {} 비어있음
            print(ev.source_run_id)   # 문자열, 파싱하려면 fragile
```

**메시지**:
- Downstream 이 "언제의 데이터냐" 를 알 방법이 없음
- run_id 파싱은 Airflow 버전 dependent (public API 아님)

### Gap 2 — 조건부 emit 없음

**시연**:
- Producer 를 백필 → downstream 이 우르르 트리거되는 모습
- 백필 억제 옵션이 어디에도 없음

**메시지**:
- 시연 중 알림 폭탄 위험
- 특정 시간대만 처리하고 싶은 downstream 이 매 시간 켜지는 낭비

### Gap 3 — Partition 매칭 없음

**시연**:
- `schedule=[A, B]` 는 AND 지만 "짝맞춤" 이 아님
- 백필 h1..h5 시 dag_run 개수가 예측 불가능하게 변함 (실제 timing 예시)

**메시지**:
- Asset scheduling 은 event-based, 시간축 매칭은 스케줄러가 안 해줌
- 이걸 모르고 도입하면 실전에서 함정

### 시각 자료

각 gap 별 실제 로그 / UI 스크린샷. 특히 gap 2 는 **백필 → downstream 폭주** 를 실제로 보여주면 강렬.

## Chapter 3 — Stamp task 로 계약 명시화

### 스크립트

> "이 3가지 gap 을 하나의 아이디어로 해결할 수 있습니다. Producer 쪽에 stamp task 를 하나 추가하는 겁니다."

### 시연 코드

**Before**:
```python
dbt_summary = DbtTaskGroup(...)
# Cosmos 자동 outlet 만 있음
```

**After**:
```python
dbt_summary = DbtTaskGroup(...)

@task(outlets=[SUMMARY_READY])
def stamp_summary_ready(**ctx):
    if ctx["dag_run"].run_type == "backfill":
        raise AirflowSkipException("backfill 억제")
    ctx["outlet_events"][SUMMARY_READY].extra = {
        "partition_kst": ...,
        "producer_run_id": ctx["dag_run"].run_id,
    }

dbt_summary >> stamp_summary_ready()
```

**메시지**:
- 조건부 emit (`AirflowSkipException` 게이트)
- Self-describing event (payload 명시)
- **Producer 소유의 이벤트 계약이 코드로 표현됨**

### Downstream 개선

```python
@task
def unpack(**ctx):
    partitions = set()
    for evs in ctx["triggering_asset_events"].values():
        for ev in evs:
            partitions.add(ev.extra["partition_kst"])
    return sorted(partitions)

@task
def process(partition: str):
    ...

process.expand(partition=unpack())
```

**메시지**:
- Dynamic task mapping 으로 event 개수에 무관하게 안전 처리
- 백필로 이벤트 여러 개 몰려와도 partition 별 병렬 처리

### 시각 자료

- 백필 시연 (before): downstream 폭주
- 백필 시연 (after): downstream 트리거 안 됨 (skip 로그)
- Dynamic mapping 시연: 백필로 5개 partition → 5개 병렬 task 자동 생성

## Chapter 4 — Cosmos vs Stamp 계층 분리

### 스크립트

> "여기서 중요한 아키텍처 원칙 하나. Cosmos 의 자동 outlet 을 끄고 stamp task 로 대체할 필요는 없습니다. 두 outlet 은 서로 다른 층위의 사실이거든요."

### 슬라이드

두 outlet 비교표 (from [[5_계층_분리_원칙]]):

| 층위 | Cosmos outlet | Stamp task outlet |
|---|---|---|
| 사실의 종류 | 물리적 (SQL 완료) | 논리적 (파이프라인 readiness) |
| 시점 | dbt run 직후 | 전체 chain 완료 후 |
| 조건 | 무조건 | 비즈니스 조건 |
| 소유권 | Cosmos | 팀 |
| 주 소비자 | Lineage 도구 (DataHub) | Downstream DAG |

### 메시지

- Cosmos 는 "물리적 lineage" 이벤트 전담 → DataHub 등이 소비
- Stamp 는 "비즈니스 readiness" 이벤트 전담 → downstream DAG 이 소비
- **역할 분리** 가 되니 두 이벤트가 공존해도 혼란 없음
- 팀 컨벤션: "Cosmos URI 는 lineage 전용, subscription 은 stamp URI 만"

### 시각 자료

두 layer 를 나란히 그리는 다이어그램 (from [[5_계층_분리_원칙]] "아키텍처 그림" 섹션).

## Chapter 5 — AssetAlias 로 partition-specific 구독

### 스크립트

> "여기서 한 단계 더 나아갑니다. 같은 producer 이벤트를 downstream 마다 다른 조건으로 골라 받게 할 수 있습니다."

### 시나리오

- Producer: hourly (기존 그대로)
- Consumer A: hourly downstream (매 시간)
- Consumer B: EOD rollup (KST 23시 파티션만)
- Consumer C: EOW report (일요일 KST 23시만)

### 시연 코드

**Producer 쪽 stamp**:
```python
SUMMARY_HOURLY = AssetAlias("story.berriz.bizberry.summary.hourly_ready")
SUMMARY_EOD = AssetAlias("story.berriz.bizberry.summary.eod_ready")
SUMMARY_EOW = AssetAlias("story.berriz.bizberry.summary.eow_ready")

@task(outlets=[SUMMARY_HOURLY, SUMMARY_EOD, SUMMARY_EOW])
def stamp(**ctx):
    kst = ctx["data_interval_start"].in_timezone("Asia/Seoul")
    partition = kst.strftime("%Y%m%d%H")
    concrete = Asset(f"story://berriz/bizberry/summary_ready/{partition}")
    extra = {...}
    
    ctx["outlet_events"][SUMMARY_HOURLY].add(concrete, extra=extra)
    if kst.hour == 23:
        ctx["outlet_events"][SUMMARY_EOD].add(concrete, extra=extra)
    if kst.hour == 23 and kst.isoweekday() == 7:
        ctx["outlet_events"][SUMMARY_EOW].add(concrete, extra=extra)
```

**Consumer 3종**:
```python
DAG("hourly_downstream", schedule=[SUMMARY_HOURLY])   # 매 시간
DAG("eod_rollup",        schedule=[SUMMARY_EOD])      # KST 23시만
DAG("eow_report",        schedule=[SUMMARY_EOW])      # 일요일 KST 23시만
```

### 메시지

- **Filtering 로직이 subscription 자체에 인코딩**됨
- Consumer 코드가 깔끔 (`if hour == 23` 같은 조건 없음)
- Producer 가 도메인 지식으로 채널을 나눔 ("KST 23시가 EOD 다")
- 새 downstream 필요하면 alias 하나 추가

### 시각 자료

한 stamp task 가 세 alias 로 fan-out 되는 다이어그램. Consumer 3종이 각각 다른 색으로 구독하는 그림.

## Asset 이 sensor 를 대체 못 하는 케이스도 언급

### 스크립트

> "마지막으로 하나. Asset scheduling 이 sensor 를 완전 대체한다는 오해가 있는데, 실제로는 부분 대체입니다."

### 판단표 (from [[6_Asset_vs_Sensor_판단표]])

간단히 3가지 케이스 언급:
1. Sensor 가 DAG 중간에 있는 경우 → asset 못 씀
2. 데이터 조건 (count / freshness) 검사 → sensor 유지
3. 자원 문제만 걸린 경우 → deferrable sensor 로 저렴하게 해결

### 메시지

- Asset 은 event-driven DAG 을 위한 도구
- Sensor 는 time-driven DAG 안의 조건 대기 도구
- **판단 기준을 팀에 제공** 하는 게 이 시연의 진짜 가치

## 예상 Q&A

**Q. Cosmos 를 안 쓰고 순수 dbt 로 하면 이 문제가 없나?**
A. Cosmos 를 안 써도 stamp 는 필요합니다. Payload / 조건부 emit / alias 는 dbt 자체가 제공하는 게 아니라 airflow 레벨의 이야기예요. Cosmos 는 편의를 주는 것이고, stamp 는 계약 명시성을 주는 것.

**Q. Stamp task 를 매번 붙이면 boilerplate 아닌가?**
A. Factory helper (또는 provider operator) 로 pack 하면 됩니다. Chapter 4 뒷부분 (계층 분리) 에서 factory 를 언급.

**Q. `AssetAlias` 는 안정된 기능인가?**
A. Airflow 3.0 에서 GA. 다만 `AssetWatcher` 등 다른 asset API 는 아직 진화 중. 시연 chapter 5 스코프는 alias 까지만.

**Q. 기존 sensor 기반 DAG 을 다 asset 으로 바꿔야 하나?**
A. 아니에요. Chapter 5 뒤에 판단표 (asset vs sensor) 를 반드시 언급하세요. Sensor 유지가 나은 케이스가 여전히 많음.

**Q. Provider 확장 일정은?**
A. Story 팀 로컬 프로토타입 (~2주) → provider PR (~1개월) → 안정화. 데이터플랫폼팀과 협의 필요.
