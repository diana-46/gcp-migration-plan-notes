# 1. 배경과 두 가지 결정

> 이번 전환을 왜 지금 하는지, 어떤 두 축을 바꾸는지 한눈에.
> 상세: [[2_결정A_dbt로_왜_가는가]], [[3_결정B_팀별_DAG_저장소]]

## 왜 지금 바꾸는가

세 가지가 동시에 겹치는 시점.

### 1. BQ 이관 확정 (기술적 강제)

- Presto / Hive → BigQuery 이관 결정.
- Neptune 의 `ADD PARTITION` / `merge_and_move.sh` / HDFS 경로 관리 등은 BQ 에서 의미가 사라지거나 재구성 필요.
- **어차피 대부분의 파이프라인 SQL 이 재작성 대상**.

### 2. Composer 이관 (인프라 강제)

- 사내 self-managed Airflow → Cloud Composer 3 이관 결정 (관련: [[스케줄러/0_결론]]).
- Composer 3 은 Airflow 3.1.7 번들 — Task SDK, Asset, DAG Bundles 등 큰 변화.
- **Airflow 2 → 3 breaking change 도 어차피 수반됨**.

### 3. 비용·리소스 축소 목표 (경영 목표)

- GCP 요금 = DCU (vCPU + RAM 시간, 24×7 상주) — 관련: [[스케줄러/14_Composer 3 비용 구조]]
- 현재 Neptune athlon 은 DB 기반 스케줄링 → MySQL 300~900 queries/minute (관련: [[스케줄러/15_관리 레포 인벤토리]])
- **리소스 다이어트 안 하면 GCP 요금이 그대로 부담** (관련: [[스케줄러/7_1_실제 스펙 산정]], [[스케줄러/7_2_리소스 다이어트 포인트]])

즉 재작성을 피할 수 없고, 재작성 대상이 있고, 비용 축소 압박이 있음. 이 시점이 도구 전환의 자연스러운 지점.

## 두 축 요약

### 축 A — SQL: Neptune → dbt

| 지금 | 이후 |
|---|---|
| SQL 이 MySQL TEXT 컬럼 (DB 안) | `.sql` 파일 (git 안) |
| 저장 → Airflow → 로그 ~10분 사이클 | `dbt run --select` ~10초 사이클 |
| 리뷰 = 슬랙 스크린샷 | GitHub PR + CODEOWNERS |
| 의존성 = UI 클릭 | `{{ ref('...') }}` 자동 감지 |
| 파티션 = ADD PARTITION 수동 | `partition_by` + `insert_overwrite` |
| 테스트 = 별도 구축 | `dbt test` |
| Lineage = 파편 / 컬럼 없음 | dbt manifest → DataHub column-level |

**상세**: [[2_결정A_dbt로_왜_가는가]]

### 축 B — Orchestration: Python DAG + 팀별 저장소 + 팀별 Composer

두 하위결정을 세트로:

**하위결정 1** — Actions UI → Python DAG (authoring):

| 지금 | 이후 |
|---|---|
| UI 텍스트 필드에 SQL / kwargs 입력 | IDE + `.py` 파일 |
| kwargs 스트링 JSON (오타 검증 X, 자동완성 X, 타입 힌트 X) | Python 인자 (IDE 자동완성, 타입 체크, Ctrl+클릭 소스 확인) |
| 오퍼레이터 = UI dropdown 사내 것만 | `pip install` + `import` (오픈소스 Provider 수백 개 + 사내 `apache-airflow-providers-kakaoent-dataplatform`) |
| 조건분기 · 반복 = 우회 | Python `if` / `for` / 함수 / 모듈 자연 |

**하위결정 2** — Centralized `airflow-dags` → 팀별 저장소:

| 지금 | 이후 |
|---|---|
| 한 저장소 여러 팀 공유 | 팀별 저장소 (`storydata-airflow-dags`, ...) |
| 배포 페이스 강제 동기화 | 팀 자율 배포 |
| 팀 간 이슈 전파 | 팀 내 격리 |
| Ownership 흐림 | 저장소 = 팀 |
| **athlon MySQL 매 분·초 폴링** | **GCS 파일 + manifest 캐시 (DB 폴링 소멸)** |
| Composer 공유 | **팀별 Composer 운영** (DCU 요금 도메인별 명확) |

**핵심 논거 (다층)**:
- **Authoring 편의**: kwargs JSON 지옥 해소, IDE / Provider 생태계
- **자율성**: 팀 배포 자율, ownership 명확, blast radius 격리, 리뷰 문화 팀 내 완결
- **비용·리소스**: athlon DB 폴링 소멸 + Composer DCU 팀별 관리
- **정합성**: dbt 프로젝트도 팀별 → 저장소·Composer 대응이 대칭

**상세**: [[3_결정B_팀별_DAG_저장소]]

## 두 결정의 공통 원리

**DB / UI 안에 갇힌 자산을 git + PR + CI 로.**

- 편집 위치: UI 텍스트 필드 → IDE + 파일
- 저장: MySQL 컬럼 → git
- 검증: 배포 후 runtime → CI (parse, test, DAG import)
- 롤백: 수동 → `git revert` + BQ time travel
- Ownership: 흐림 → 저장소·CODEOWNERS 명시
- 확장: 플랫폼팀 요청 대기 → 팀 자율
