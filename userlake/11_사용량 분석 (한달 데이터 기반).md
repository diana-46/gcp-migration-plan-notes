## 0. 핵심 발견 (TL;DR)

> 이 데이터가 **이관 의사결정 3개의 가정을 깨뜨림**:
> 1. ❌ "userlake-worker 는 업무 시간에 집중" → ✅ **시간대별 거의 균일, 24h 상주 필수**
> 2. ❌ "batch 모드도 옵션" → ✅ **Gate/Sync 평균 4~10초 < cold start 30~60초, Interactive Session 만**
> 3. ❌ "DCU 126 적정 사이즈" → ✅ **75% 코호트가 10만 행 이하, 다운사이즈 가능 (DCU 21~30)**
>
> 추가 발견:
> - 일 평균 코호트 ~230 건, stage ~1,500 건
> - 이벤트/캠페인 burst 시 평소의 **2~3배**
> - 재시도 거의 없음 (FAILED 0.05%, max attempt 5)
> - STOPPED 8~10% (timeout / cancel — 추가 분석 필요)

| EXTRACT_RUN | 521 | 1.7 | 0 | 55 |

**핵심 발견**:

1. **GATE 4.3초 / SYNC 9.8초** ← Spark Connect 잡 단위
   → Dataproc Serverless **cold start (30~60초) 가 stage 실행시간보다 김**
   → **batch 모드 절대 불가능** (cold start 가 오버헤드 압도)
   → **Interactive Session 만 가능**

2. **TARGET 평균 71초** (Presto 쿼리)
   → BQ 가도 비슷한 시간 예상. JDBC streaming 성능 / Storage Read API 검증 필요
   → max 871초 (14.5분) → **stage timeout 은 적어도 15분 잡아야 함**

3. **SYNC max 129초, GATE max 84초** → 보통 잡은 빠르게 끝남

**핵심 발견**:

1. **FAILED 가 매우 적음** — TARGET 8건 (0.05%), SYNC 1건, GATE 0건
2. **재시도 거의 없음** — COMPLETED 의 avg attempts = 1.0 (사실상 1회만)
3. **max attempt = 5** (TARGET 만, 단 1건의 FAILED 가 5회까지 시도)
4. **STOPPED 가 의외로 많음**:
   - TARGET: 1,683 (10%)
   - GATE: 1,176 (8.7%)
   - SYNC: 673 (4.3%)

→ **Pub/Sub DLT max delivery**:
- TARGET: 5 (현재 max 와 일치)
- GATE / SYNC: 1~3 (재시도 사실상 없음)

→ **STOPPED 의 정체 파악 필요** — timeout 인지, cohort 자체 cancel 인지. 의미 따라 Pub/Sub 매핑 방식 다름.

## 7. 일별 cohort 실행량 / Burst 분석 (Q7)

```
5/30 ~ 6/14: 평소        일 ~150~200 코호트 (1,000~1,600 stage)
6/8  ~ 6/13: BURST 주간   일 423~495 코호트 (4,250~5,600 stage) ← 2~3배
6/14 이후 ~: 평소 복귀    일 ~150~200 코호트

특이 일자:
2026-06-12: 495 코호트 / 5,593 stage  ← peak day
2026-06-11: 480 코호트 / 5,442 stage
2026-06-10: 488 코호트 / 5,508 stage
2026-06-09: 478 코호트 / 5,365 stage
2026-06-08: 423 코호트 / 4,252 stage
```

**해석**:
- **5일간 burst** (6/8~6/13). 이벤트/캠페인 추정
- **평소 대비 2.5~3배** 증가
- 평소 일 ~1,200 stage → burst 시 일 ~5,500 stage
- 시간당 burst peak: 5,500 / 24 ≈ **230 stage/h** (평균치)
- 실제 burst 시간대 집중 가능성 → 시간당 400+ 도 가능

→ **Dynamic Allocation 필수** (정적 사이즈로 burst 대응 어려움)
→ Pub/Sub subscription backlog 기반 HPA 가 burst 대응에 효과적

## 8. 의사결정 영향 정리

### Spark Connect / Dataproc Serverless

| 의사결정 | 이전 가정 | 데이터 기반 결론 |
|---|---|---|
| 운영 모델 | Batch / Interactive 둘 다 가능 | **Interactive 만 가능** (cold start > stage time) |
| Usage time | 240h/월 (8h 가정) | **720h/월 (24h)** — 시간대 균일 |
| DCU | 126 (현재 사이즈) | **21~30** (75% 가 10만↓) |
| Dynamic Allocation | 옵션 | **필수** (burst 2~3배) |
| 다운사이즈 | "가능하면" | **강력 권장 + 검증** |
| 월 비용 | $1,500~1,800 (8h 240h) | **~$900~1,300** (24h + 다운사이즈) |

### Pub/Sub

| 의사결정 | 이전 가정 | 데이터 기반 결론 |
|---|---|---|
| DLT max delivery | 5 (max_attempt_count) | TARGET 5 / GATE,SYNC 1~3 |
| Topic 8개 vs 1개 | 8개 (현재 구조) | **8개 유지** (TARGET/SYNC/GATE 가 95%) |
| HPA 트리거 | Pub/Sub backlog | **확정** — burst 대응에 필수 |
| Ordering key | "필요할 수도" | **필요** (cohort 내 stage 순서) — Q6 의 STOPPED 흐름이 cohort 단위 cancel 일 가능성 |

### BigQuery

| 의사결정 | 이전 가정 | 데이터 기반 결론 |
|---|---|---|
| Target/Extract 의 BQ slot 사용 | 미지 | **TARGET 평균 71초** → slot 사용 충분 |
| Result row count | 미지 | **평균 45만 (TARGET)**, max 22M → Storage Read API 비용 미미 |
| Query timeout | 미지 | **15분 이상** 필요 (max 871초) |
| 재시도 정책 | 미지 | **거의 안 일어남** (FAILED 0.05%) — retry 정책 단순화 가능 |
