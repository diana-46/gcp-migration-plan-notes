# 5. 의존성 관리 (ETL/모델 간 dependency)

> Neptune 의 `EtlDependencies` 와 dbt 의 `ref()` 그래프가 어떻게 매핑되는지, 같은 DAG 안의 의존성과 다른 DAG 간 의존성이 어떻게 다르게 풀리는지.
> 관련: [[1_materialization]], [[3_backfill]], [[4_parameter 치환]]

## 0. 다루는 범위

- Neptune 의 명시적 의존성 선언 (upstream/dependency 엔티티)
- dbt 의 암시적 의존성 (ref / source 가 SQL 안에 있으면 자동 추론)
- Cosmos 가 dbt DAG → Airflow task 순서로 변환하는 방식
- 같은 DAG 안의 의존성 vs 다른 DAG 간 의존성 (Asset/Dataset)
- 순환 의존성 감지

---

## 1. Neptune 의 의존성 관리

### 1-1. 어떻게 선언되나

Neptune 의 ETL 은 **명시적으로 upstream 을 등록**:

```
Etl
  ├─ id, destTable, code, ...
  └─ upstreamEtlIds: [42, 71]    ← 명시적 의존성 선언
```

→ `EtlService.saveUpstreamDependencies()` 가 `EtlUpstream` (또는 비슷한 join 테이블) 에 row 저장.

ETL 의 SQL 본문은 upstream 테이블을 직접 참조하지만 (`FROM datawarehouse.foo_table`), **이 참조 자체로 의존성이 추론되지는 않음**. 사용자가 별도로 upstream 을 선언해줘야 Airflow DAG 의 task 순서가 잡힘.

### 1-2. 순환 의존성 감지

`EtlService` 의 사이클 체크 (이전 survey 에서 lines 166–209 언급):
- ETL 저장 시 upstream chain 을 따라가며 자기 자신이 나오는지 확인
- 사이클 발견 → 저장 거부 (`CircularDependencyException` 류)

### 1-3. Airflow DAG 으로 변환

ETL 들이 같은 DAG 에 묶여 있을 때:
```
ETL A (upstream: [])
ETL B (upstream: [A])
ETL C (upstream: [A, B])
```
→ Airflow DAG 의 task 의존성: `A_end >> B_start`, `B_end >> C_start`

각 ETL 의 action chain 도 (CREATE_TEMP → ... → END) 자체적으로 순서 있고, ETL 끼리는 위처럼 연결.

### 1-4. 한계

- **수동 선언** — 사용자가 upstream 빠뜨리면 잘못된 순서로 실행
- SQL 본문의 FROM 절과 분리 — drift 가능 (SQL 만 바꾸고 upstream 안 갱신)
- 다른 DAG 의 ETL 을 upstream 으로 두려면 별도 트리거 메커니즘 필요 (Airflow ExternalTaskSensor 등)

## 2. dbt 의 의존성 관리

### 2-1. `ref()` — 다른 모델 참조

```sql
-- models/marts/daily_orders.sql
SELECT user_id, SUM(amount) AS total
FROM {{ ref('stg_orders') }}
GROUP BY user_id
```

→ dbt 가 manifest 파싱 시 자동으로 의존성 그래프 구성: `daily_orders` depends on `stg_orders`.

**핵심 차이**: 의존성이 SQL 본문에서 추론됨. 별도 선언 없음.

### 2-2. `source()` — 외부 raw 데이터 참조

```sql
SELECT * FROM {{ source('raw_events', 'orders') }}
```

→ `sources/` schema.yml 에 정의된 외부 테이블. dbt 가 변환하지 않는 입력.

### 2-3. 자동 DAG 구성

`dbt parse` 시 모든 모델의 ref()/source() 를 분석:
- 각 모델 = node
- ref/source = edge
- 결과: 방향성 비순환 그래프 (DAG)

`manifest.json` 에 저장됨. `dbt run` 은 topological order 로 실행.

### 2-4. 자동 순환 감지

dbt 는 그래프 빌드 단계에서 사이클이 있으면 **parse error**:
```
Found a cycle: daily_orders -> aggregated_user -> daily_orders
```

→ 사용자가 일부러 사이클 만들기 불가능. ref() 가 양방향이 안 되니까 구조적으로 안전.

### 2-5. 선택적 실행

```bash
dbt run --select stg_orders+              # stg_orders 와 그 downstream
dbt run --select +daily_orders             # daily_orders 와 그 upstream
dbt run --select stg_orders+1              # 1 단계만
dbt run --select tag:case2                 # tag 로 묶어서
```

→ 의존성 그래프 기반으로 부분 실행 자유로움. backfill 시 유용.

## 3. Cosmos 가 dbt DAG → Airflow DAG 으로 변환

### 3-1. 변환 메커니즘

`DbtTaskGroup` 이 manifest.json 읽어서:
1. 각 (non-ephemeral) 모델 → Airflow task 생성
2. dbt 의 ref() edge → Airflow `task1 >> task2` 의존성
3. ephemeral 모델 → task 안 만들고 다운스트림에 CTE 인라인

예시 (case3):
```
dbt 측:
  tmp_open_web (ephemeral) ─┐
  tmp_open (ephemeral)      │
  tmp_click (ephemeral)     ├─→ tmp_stat_result (ephemeral) ─→ stat_first_open_detail_daily (incremental)
  tmp_imp (ephemeral)       │
  tmp_pv (ephemeral)        ┘

Cosmos 가 만드는 Airflow task:
  stat_first_open_detail_daily.run    ← 1개만. ephemeral 들은 SQL 안에 CTE 로 들어감
```

만약 ephemeral 이 아니라 view/table 이면:
```
tmp_open_web.run ─┐
tmp_open.run      │
tmp_click.run     ├─→ tmp_stat_result.run ─→ stat_first_open_detail_daily.run
tmp_imp.run       │
tmp_pv.run        ┘
```
→ 7개 task, 자동으로 위 순서.

### 3-2. 운영자가 신경 쓸 게 없음 (한 TaskGroup 내)

dbt 의 ref 만 제대로 쓰면 Airflow task 순서는 자동. Neptune 처럼 upstream 따로 등록 안 함.

**단, 같은 TaskGroup 안에서만**. 모델들을 여러 DbtTaskGroup 으로 나누면 Cosmos 가 그룹 간 dep 자동 안 잡음 → § 3-3 참고.

### 3-3. 여러 DbtTaskGroup 으로 나눌 때 — 수동 wiring 필요

운영 모델이 많아져서 한 TaskGroup 이 과부하 우려되면 그룹 분리. 이때 ref 동작:

| 레벨 | 자동? |
|---|---|
| SQL 의 ref() 컴파일 → 정확한 BQ 경로 | ✅ 항상 |
| 같은 TaskGroup 안 task 순서 | ✅ Cosmos 자동 |
| 다른 TaskGroup 간 task 순서 | ❌ 수동 `group_a >> group_b` 필요 |

수동 wiring 빼먹으면 → 그룹 동시 시작 시도 → upstream 그룹의 BQ 테이블 없는 상태에서 downstream 실행 → fail.

### 3-4. 자동 wiring helper (PoC 검증 완료)

manifest 기반으로 그룹 간 wiring 을 자동 생성하는 helper. 운영에 다수 모델 운영 시 boilerplate 제거.

```python
# common/dbt_presets.py
def grouped_dbt_taskgroups(
    groups_spec: dict[str, list[str]],
    *,
    manifest_path: str = f"{DBT_PROJECT_PATH}/target/manifest.json",
    **common_kwargs,
) -> dict[str, ...]:
    """그룹별 DbtTaskGroup 생성 + manifest 기반 자동 wiring.

    Returns:
        {
          "groups": {group_id: DbtTaskGroup},
          "heads":  list of entry 그룹 (upstream group 없음),
          "tails":  list of exit 그룹 (downstream group 없음),
        }
    """
    # 1. model → group_id 매핑
    model_to_group = {m: gid for gid, models in groups_spec.items() for m in models}

    # 2. 그룹 생성
    task_groups = {
        gid: dbt_taskgroup(group_id=gid, select=models, **common_kwargs)
        for gid, models in groups_spec.items()
    }

    # 3. manifest 의 depends_on 따라 그룹 간 dep 추출
    manifest = json.load(open(manifest_path))
    inter_deps = set()
    for node in manifest["nodes"].values():
        if node.get("resource_type") != "model":
            continue
        ds = model_to_group.get(node["name"])
        if not ds:
            continue
        for dep_id in node.get("depends_on", {}).get("nodes", []):
            dep = manifest["nodes"].get(dep_id, {})
            us = model_to_group.get(dep.get("name"))
            if us and us != ds:
                inter_deps.add((us, ds))

    # 4. wiring
    for us, ds in inter_deps:
        task_groups[us] >> task_groups[ds]

    # 5. heads / tails 계산 (start/end 연결용)
    has_upstream = {d for _, d in inter_deps}
    has_downstream = {u for u, _ in inter_deps}
    heads = [task_groups[g] for g in groups_spec if g not in has_upstream]
    tails = [task_groups[g] for g in groups_spec if g not in has_downstream]

    return {"groups": task_groups, "heads": heads, "tails": tails}
```

DAG 에서:

```python
with DAG(...) as dag:
    start = EmptyOperator(task_id="start")

    result = grouped_dbt_taskgroups({
        "group_a": ["model_a1", "model_a2"],
        "group_b": ["model_b1"],
        "group_c": ["model_c1"],
        # ... 모델이 늘어도 helper 가 manifest 보고 알아서 wiring
    })

    end = EmptyOperator(task_id="end")

    # 외부 task 와의 연결만 명시. heads/tails 가 자동 계산됨
    start >> result["heads"]
    result["tails"] >> end
```

#### 핵심 의의

- 운영 모델 N 개를 의미 단위로 그룹화 가능 (도메인, 팀, 비용 분리 등)
- 그룹 추가/변경 시 wiring 코드 안 건드림 — manifest 만 보면 됨
- 외부 task (start/end, 알림, 검증) 는 heads/tails 에만 명시 연결

#### `heads` / `tails` 가 필요한 이유

순진하게 모든 그룹을 start/end 에 연결하면 redundant edge 생김:
```python
# ❌ 잘못된 방식
start >> [group_a, group_b]   # group_b 는 group_a 의 downstream인데 start 와 직접 연결
[group_a, group_b] >> end     # group_a 가 group_b 거치지 않고 end 와 직접 연결
```

graph 가 어수선해지고 의존성 의도가 흐려짐. helper 가 자동 계산한 heads/tails 만 쓰면 깔끔.

## 4. 같은 DAG vs 다른 DAG 의존성

dbt model 끼리 의존성은 같은 dbt 프로젝트 안이라면 ref() 로 자유. 그런데 Airflow 측면에서 같은 DAG 인지 다른 DAG 인지 구분되면 처리 방식 다름.

### 4-1. 같은 DAG 의 의존성 — Cosmos 가 자동 처리

production DAG 안에 case2 와 case2_downstream (case2 를 ref) 둘 다 있으면 자동으로 순서 설정됨.

### 4-2. 다른 DAG 간 의존성 — Airflow Asset (Dataset)

dbt 모델이 다른 DAG 에 있는 모델을 참조해야 하는 경우:

**옵션 A**: Cosmos 의 `emit_datasets=True` 활용 (default)
- 각 모델 task 가 자동으로 `bigquery/proj/ds/table` URI 의 Airflow Asset outlet 부착
- 다른 DAG 이 `schedule=[Asset("bigquery/.../table")]` 로 그 Asset 을 구독 → 자동 trigger

```python
# DAG B (consumer)
with DAG(
    schedule=[Asset("bigquery/dev-dp-project/dbt_test/case2_table")],
    ...
):
    ...
```

→ case2 가 완료되면 자동으로 DAG B 의 dag_run 생성됨.

**옵션 B**: ExternalTaskSensor / TriggerDagRunOperator (Airflow 2 식)
- 구식 패턴. Asset 이 더 깔끔.

### 4-3. Neptune 의 같은 메커니즘

Neptune 은 한 DAG 안의 ETL 끼리는 upstream 직접 선언, 다른 DAG 의 ETL 은 보통 같은 DAG 으로 합치거나 별도 트리거. Asset 같은 추상화는 없음.

→ dbt + Cosmos + Airflow 3 의 **Asset 기반 cross-DAG dependency** 가 Neptune 대비 명확한 강점.

## 5. 마이그레이션 매핑

| Neptune 자산 | dbt 대응 | 변환 방법 |
|---|---|---|
| `Etl.upstreamEtlIds: [A, B]` | 모델 SQL 안의 `{{ ref('A') }}`, `{{ ref('B') }}` | upstream 선언 삭제. SQL 의 `FROM datawarehouse.A` 를 `FROM {{ ref('A') }}` 로 변경 |
| Raw Hive 테이블 참조 | `{{ source('raw', 'table') }}` | sources schema.yml 등록 후 ref 형태로 변경 |
| 순환 의존성 체크 | dbt parse 의 자동 감지 | 작업 없음 — 자동 |
| 같은 DAG 의 ETL 순서 | Cosmos 자동 (ref 그래프 → task 의존성) | 작업 없음 |
| 다른 DAG 의 ETL 트리거 | Airflow Asset 기반 schedule | 새 패턴. consumer DAG 에 `schedule=[Asset(...)]` 추가 |

**예상 마이그레이션 흐름**:
1. Neptune ETL 의 SQL 본문에서 `FROM <db>.<table>` 들을 식별
2. 각 table 이 다른 ETL 의 출력이면 `{{ ref('<model_name>') }}` 로 변경
3. raw 데이터면 source 로 등록 + `{{ source(...) }}` 로 변경
4. ETL 의 upstreamEtlIds 선언은 **삭제** (불필요)
5. 다른 DAG 으로 트리거 보내야 하는 케이스만 Asset 으로 설정

## 6. PoC 의 의존성 예시

### 6-1. case3 의 모델 간 의존성 (같은 dbt 프로젝트 안)

```sql
-- tmp_stat_result.sql (ephemeral)
SELECT ...
FROM {{ ref('tmp_open') }} tg
LEFT JOIN {{ ref('tmp_click') }} cl USING (...)
LEFT JOIN {{ ref('tmp_imp') }} ip USING (...)
LEFT JOIN {{ ref('tmp_pv') }} pv USING (...)

UNION ALL

SELECT ...
FROM {{ ref('tmp_open_web') }}
```

```sql
-- stat_first_open_detail_daily.sql (incremental)
SELECT
    DATE('{{ var("run_date") }}') AS create_date,
    *
FROM {{ ref('tmp_stat_result') }}
```

→ 5개 tmp_* + tmp_stat_result + perm = 7개 모델의 의존성이 ref() 만으로 표현. 별도 의존성 선언 없음.

ephemeral 이라 Airflow task 는 perm 1개만. 다 view/table 이면 7개 task + 자동 순서.

### 6-2. case 간 의존성 (없음)

case1, case2, case3, case4, case5 는 서로 ref 없음 → DAG 안에서 병렬 실행.

운영에선 case 간 의존성 생기면 ref() 추가하면 끝.

## 7. dbt 의 추가 기능

### 7-1. 의존성 시각화

```bash
dbt docs generate
dbt docs serve
```

→ ref/source 그래프를 lineage 뷰로 시각화. Neptune 의 UI 대비 강점.

### 7-2. 영향도 분석

```bash
dbt ls --select +<model>   # upstream 모두
dbt ls --select <model>+   # downstream 모두
```

→ 변경 영향 받는 모델 미리 확인. 운영 PR 리뷰에 유용.

### 7-3. groups / access (1.5+)

```yaml
# schema.yml
models:
  - name: dim_user
    access: public
    group: dim_team
```

→ 다른 팀이 함부로 ref 못 하게 막거나, 의도적으로 public 으로 열기. 거버넌스.

## 8. 미해결 / 추가 검토

- Cross-project dbt dependencies (dbt packages, dbt mesh) 의 운영 부담 vs 단일 프로젝트 유지
- Airflow Asset 의 partition 단위 감지 가능 여부 (BQ 의 partition 단위로 consumer 트리거 가능?)
- Neptune 의 dynamic upstream (런타임에 의존성 변경) — dbt 에 등가물 없음. 그런 패턴 운영에 실제 있는지 확인
- dbt 1.6+ 의 model versions 와 의존성 — `ref('orders', v=2)` 패턴 운영 활용도
