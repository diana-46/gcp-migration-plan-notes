# 0. 결론 (Executive Summary)

> **팀 baseline + 월요일 MDL 조사자 aligning 5분 요약**. 상세는 각 문서 참조.

## 한 줄 결론

> **Airflow 3.1 은 asset 이 이벤트 신호 수준**. 3.2 부터 **partition first-class** 로 진짜 데이터-centric orchestration 이 됨. Cosmos 호환과 UI 성숙도가 남은 관건. **Story 팀 케이스는 stamp task bridge → 3.2 이관 시 대부분 native 로 흡수** 예상.

## 지금 (Airflow 3.1) 의 3가지 gap

Cosmos + Airflow 3.1 asset 을 그대로 켜기만 하면:

| Gap | 증상 |
|---|---|
| **Payload 없음** | Downstream 이 producer 의 execution_date/partition 을 못 알아냄. run_id 파싱은 fragile |
| **조건부 emit 없음** | Producer 완료 시 무조건 downstream 을 깨움. Backfill 시 downstream storm |
| **Partition 매칭 없음** | `schedule=[A, B]` 의 AND 는 "둘 다 왔음" 만 봄. "같은 hour 짝" 같은 시간축 매칭은 스케줄러가 안 해줌 |

상세: [[2_문제_정의]]

## 3.2/3.3 에서 대부분 해결됨

| 3.1 Gap | 3.2 해결 | 3.3 추가 |
|---|---|---|
| Payload 없음 | `partition_key` first-class + `dag_run.partition_key` | — |
| 조건부 emit 없음 | — (여전히 stamp 필요) | — |
| Partition 매칭 없음 | `PartitionedAssetTimetable` + 매퍼 | Rollup / FanOut |
| Cadence 다름 (hourly → daily) | 수동 매퍼 조합 | ✅ `RollupMapper + DayWindow + WaitForAll` |

상세: [[3_Airflow_3.1_3.2_비교]]

## 3.1 상태에서의 Bridge Pattern

Composer 가 3.2 로 이관되기까지 (~1개월 예상) 는 다음 패턴으로 우회:

### 1. Stamp task (self-describing event)

Cosmos 뒤에 stamp task 하나 붙여서 **팀이 명시한 payload** 를 asset event 에 실음. `AirflowSkipException` 으로 **조건부 emit** 도 통제 가능.

```python
@task(outlets=[SUMMARY_READY])
def stamp_summary_ready(**ctx):
    if ctx["dag_run"].run_type == "backfill":
        raise AirflowSkipException("backfill 은 downstream 안 깨움")
    ctx["outlet_events"][SUMMARY_READY].extra = {
        "partition_kst": ...,
        "producer_run_id": ctx["dag_run"].run_id,
    }
```

### 2. AssetAlias (partition-specific 구독)

한 stamp task 가 **여러 alias 로 fan-out**. Consumer 는 원하는 조건의 alias 만 subscribe.
- `SUMMARY_HOURLY` — 매 시간
- `SUMMARY_EOD` — KST 23시 파티션만
- `SUMMARY_EOW` — 일요일 KST 23시만

→ **필터 로직이 subscription 자체에 인코딩**됨. 3.3 의 `RollupMapper` 가 이걸 native 로 대체할 예정.

### 3. Consumer 쪽 dynamic task mapping

`triggering_asset_events` 를 unpack 해서 partition 별 병렬 task 로 `.expand()`. Backfill 로 이벤트가 뭉쳐 와도 안전하게 처리.

상세: [[4_해결_패턴]]

## Cosmos 와 stamp 의 계층 분리

두 outlet 은 **의미가 다른 이벤트 스트림**:

| 층위 | Cosmos outlet | Stamp task outlet |
|---|---|---|
| 사실의 종류 | 물리적 (SQL 완료) | 논리적 (파이프라인 readiness) |
| 조건 | 무조건 | 비즈니스 조건 |
| 소유권 | Cosmos 라이브러리 | 팀 |
| 소비자 | Lineage 도구 (DataHub 등) | Downstream DAG |

Cosmos 자동 outlet 을 굳이 끄지 않고, **역할을 분리해서 각자 잘 하는 걸 하게** 두는 게 실무 정답.

상세: [[5_계층_분리_원칙]]

## Provider 확장 방향 (데이터플랫폼팀 내부 로드맵)

`airflow-provider-kakaoent-dataplatform` 에 3개 컴포넌트 추가 검토:

1. **`KakaoAsset`** — URI 컨벤션 빌더 (`KakaoAsset.bigquery(...)`, `KakaoAsset.logical(...)`)
2. **`KakaoAssetStampOperator`** — stamp 패턴 표준 operator (조건부 emit, 표준 payload 필드)
3. **`AssetEventUnpacker`** — consumer 쪽 event 파싱 헬퍼

→ 소비자 팀 (Story 등) 이 stamp task 재발명하지 않도록. **단, 3.2 partition_key 로 migration 가능한 API 설계**.

상세: [[7_Provider_확장_제안]]

## Asset vs Sensor 판단

Asset scheduling 은 **sensor 상위호환이 아니라 부분 대체**. 그리고 정확히 이 조건:

> "DAG 시작점에 있는, 오직 upstream 완료를 기다리기 위한 sensor" 만 자연스럽게 대체

Sensor 유지가 나은 케이스:
- DAG 이 자기 cron 으로 시작 후 **중간에** upstream 대기
- 데이터 조건 검사 (row count, freshness 등)
- 동적 execution_delta

상세: [[6_Asset_vs_Sensor_판단표]]

## MDL 요구와의 커버리지 (정직하게)

MDL 팀 (dataset_test.md) 문제 대비 우리 관점:

- **Airflow 3.2/3.3 이 커버**: DSP 갭 감지, Kafka 이벤트, 파티션 매칭, cadence 변환
- **Airflow 여전히 약함**: Sequenced self-dep, 재수집 자동, 파티션 UI, Freshness SLA
- **Cosmos 개선 필요**: Cross-DAG dbt 의존성

즉 MDL 케이스는 **Dagster 가 유리한 지점이 남음**. 우리가 Airflow 로 다 커버 가능하다고 주장하기는 무리.

상세: [[3_Airflow_3.1_3.2_비교]] Part E, [[10_MDL_aligning_노트]]

## 조직 방향 3가지 옵션

미팅에서 놓고 대화할 프레임:

| 옵션 | 성격 | 비용 | 적합 조건 |
|---|---|---|---|
| A. 전체 Airflow | Gap 을 커스텀 개발 | 지속적 개발 부담 | 인력 여유 |
| B. 전체 Dagster | 조직 이동 | 이미 한 투자 손실 | Data-asset 워크로드 압도적 |
| C. 하이브리드 | 워크로드 성격별 도구 | 두 도구 유지 | 경계 명확할 때 (MDL 이 제안) |

**개인 감**: Option C 가 가장 지속가능. 다만 이중 유지 부담 관리 계획 필요.
