# 실제 스펙 기반 Composer 비용 산정 (GCE / GKE / Composer 3)

> [[7_Composer 비용]] 는 일반론. 본 문서는 **우리 현재 운영 스펙**을 기준으로 GCE / GKE / Composer 3 세 가지로 옮겼을 때의 GCP 청구액을 실측 추정한다.
>
> 서울 리전(asia-northeast3) 기준. on-demand 가격이 기본, 할인 적용 케이스는 별도 표시.

## 0. 사전 지식 — DCU

**DCU (Data Compute Unit)** = Composer 3 의 추상 과금 단위. GCE/GKE 가 vCPU·메모리 단가로 직관적인 반면, Composer 3 는 둘을 묶어서 DCU 로 청구.

**환산식** (공식은 모호, [커뮤니티 리버스 엔지니어링](https://discuss.google.dev/t/cloud-composer-3-pricing-explanation/158381) 기준):

> `DCU/h ≈ vCPU 수 + GB RAM 수`
>
> 예: Composer 3 Small preset = 3 vCPU + 9 GB → 12 DCU/h ✅ 실측 일치

**소비 컴포넌트**: worker, scheduler, DAG processor, triggerer, web server  
→ worker 외엔 항상 떠있으므로 **DAG 0개여도 floor 비용 발생**.

**단가**:
- us-central1: $0.06 / DCU-hour (공식 사례)
- 서울 (asia-northeast3): **~$0.072 / DCU-hour 추정** ⚠️ 공식 확인 필요

**별도 청구** (DCU 에 안 포함): Cloud SQL 디스크, GCS 스토리지, 네트워크 egress.

## 1. 현재 운영 스펙

### 1.1 호스트 구성 (on-prem)

| 호스트                        | 역할                                     | CPU (physical)                                     | RAM                 | 디스크                              | 대수    |
| -------------------------- | -------------------------------------- | -------------------------------------------------- | ------------------- | -------------------------------- | ----- |
| `dp-airflow2-manager03~04` | scheduler / DAG processor / web server | Xeon Silver 4410Y (12c, 2.0GHz) × 2 = **24 cores** | 32G × 2 = **64 GB** | NVMe PM9A3 800GB × 1             | **2** |
| `dp-airflow2-worker01~05`  | worker                                 | Xeon Silver 4210 (10c, 2.2GHz) × 2 = **20 cores**  | 16G × 2 = **32 GB** | (on-board)                       | **5** |
| `dp-airflow2-ext01~02`     | worker (ext, 대용량 디스크)                  | Xeon Silver 4110 (8c, 2.1GHz) × 2 = **16 cores**   | 16G × 2 = **32 GB** | SSD PM883 1.9TB × 4 = **7.6 TB** | **2** |

### 1.2 합계

| 그룹                                    | physical cores | RAM        | 노드 수 | 24/7?   |
| ------------------------------------- | -------------- | ---------- | ---- | ------- |
| Manager (scheduler/DAG processor/web) | **48**         | **128 GB** | 2    | ✅ floor |
| Worker (regular)                      | **100**        | **160 GB** | 5    | 대체로 ✅   |
| Worker (ext, 대용량 디스크)                 | **32**         | **64 GB**  | 2    | 대체로 ✅   |

추가 디스크: ext 노드 **15.2 TB SSD** (대량 데이터 처리용으로 추정).

### 1.3 ⚠️ 물리 코어 → GCP vCPU 매핑

**GCP 공식 정의**: `1 vCPU = 1 hyperthread` (= **물리 코어의 절반**).
→ 따라서 on-prem 의 N physical core (HT 켜진 상태) 를 GCP 로 옮길 때 **동등 capacity 는 2N vCPU** 가 기본.

> Google Cloud 공식: *"On Compute Engine, each virtual CPU (vCPU) is implemented as a single hardware hyper-thread on one of the available CPU platforms."*

| 매핑                              | 총 vCPU       | 의미                                                  | 사용 시점                                |
| ------------------------------- | ------------ | --------------------------------------------------- | ------------------------------------ |
| **B. HT 동등 (기본)** — core × 2    | **360 vCPU** | 현재 thread 수 그대로 보존 → GCP 콘솔/공식 가이드 환산 방식            | **본 비용 산정의 default**                 |
| A. 다운사이징 — core × 1             | 180 vCPU     | "어차피 HT 절반은 안 쓰고 있을 것"이라 가정한 축소판                    | CPU 사용률 측정 후 낮을 때 별도 시나리오로 비교         |

→ 본 문서는 **B 방식 (360 vCPU, 352 GB)** 을 기본 산정 기준으로 잡는다. A 방식은 5. 비교 표에 "downsize" 옵션으로 병기.

**기본 산정치 (B 방식 기준)**:

| 그룹               | vCPU (= core × 2) | RAM        |
| ---------------- | ----------------- | ---------- |
| Manager          | 96                | 128 GB     |
| Worker (regular) | 200               | 160 GB     |
| Worker (ext)     | 64                | 64 GB      |
| **합계**           | **360 vCPU**      | **352 GB** |

### 1.4 30일 실측 사용률

직접 측정한 30일 평균 / 피크 사용량 (출처: `[GCP 이관] airflow 이관 비용 관련 정리.xlsx`):

| 호스트 | 역할 | CPU 평균 | CPU 피크 | Memory 평균 | Memory 피크 | Load 피크 |
|---|---|---|---|---|---|---|
| worker01~05 | 워커 (regular) | **~4.9%** | ~25% | ~17.5 GB | ~30 GB | ~6.5 |
| ext01~02 | 워커 (ext) | **~1.3%** | **75~83%** | ~7 GB | ~30 GB | **~30** |
| manager03~04 | 스케줄러 | **~18%** | ~38% | ~18.7 GB | ~32 GB | ~15 |

**핵심 인사이트**:

1. **메모리 병목 (Memory-bound) 워크로드**: CPU 는 평소 5% 미만인데 RAM 은 노드당 30 GB 까지 꽉 참 → 사이징은 CPU 가 아닌 **메모리 중심**으로 잡아야 함. 기존 `worker_concurrency=8` 설정 + task 당 ~4 GB 점유 패턴.
2. **ext 노드의 CPU 스파이크**: 평소 1.3% 인데 피크 80% + Load 30 → 간헐적으로 32 코어 풀로 끌어다 쓰는 **CPU-bound 외부 작업** 전담. **Spot 노드로 0대 → 띄움 → 반납** 패턴이 적합.
3. **manager 는 평균 18% CPU**: 피크에도 38% 라 현재 24c × 2대 (48c) 는 **확실히 과잉 프로비저닝**. 분산 + 다운사이즈 여지 큼.

### 1.5 부속 인프라 (산정 가정)

엑셀 견적에 잡힌 GCP 매핑 기준:

| 항목 | 가정 사양 | 월 비용 (서울, on-demand) |
|---|---|---|
| Metadata DB | Cloud SQL for MySQL Regional HA, 2 vCPU / 8 GB / 200 GB SSD | **~$570** |
| Celery broker | Memorystore Redis Cluster (Shared Core Nano) | **~$179** |

이 둘은 **세 시나리오 (GCE / GKE / Composer 3) 모두 공통**으로 들어감 (Composer 3 는 내부 흡수돼서 별도 청구는 아니지만, DCU 안에서 동등한 리소스 소비).

## 2. 시나리오 A — GCE (VM 직접)

VM 으로 현재 구조 그대로 옮긴 견적. 두 가지 버전:

### 2.1 상시 가동 (현재 스펙 그대로)

전제: 현재 물리 코어 × 2 = vCPU, RAM 그대로 24/7 가동. 머신은 **N4 custom**.

| 항목 | 사양 | vCPU-hours/월 | RAM-hours/월 | 월 비용 (USD) |
|---|---|---|---|---|
| ext01~02 | N4 custom, 32 vCPU + 64 GB × 2대 | 46,720 | 46,720 | **$2,189.76** |
| worker01~05 | N4 custom, 40 vCPU + 32 GB × 5대 (※) | 146,000 | 116,800 | **$6,702.48** |
| manager03~04 | N4 custom, 48 vCPU + 64 GB × 2대 | 70,080 | 93,440 | **$3,395.24** |
| Cloud SQL (MySQL HA) | 2 vCPU / 8 GB / 200 GB | — | — | $570.38 |
| Memorystore Redis | Shared Core Nano | — | — | $178.70 |
| Hyperdisk | 디스크 합산 | — | — | ~$8.19 |
| **합계** | | | | **$13,036.57 / 월** |

> 약 **₩1,900만/월** (1 USD = ₩1,450 가정)

(※) 워커 합계는 5대 × 40 vCPU = 200 vCPU 가 정상이나, 견적상 146k vCPU-h / 730h = 200 vCPU 로 일치.

### 2.2 사용량 기반 다이어트

전제: 30일 실측에 맞춰 **워커/매니저 다운사이즈**, ext 는 피크 대응 위해 그대로 유지.

| 항목 | 사양 (다운사이즈) | 월 비용 (USD) |
|---|---|---|
| ext01~02 | 그대로 (피크 대응) | $2,189.76 |
| worker01~05 | N4 custom, 16 vCPU + 32 GB × 5대 (※ 메모리 유지, CPU 반감) | **$3,018.24** |
| manager03~04 | N4 custom, 16 vCPU + 32 GB × 2대 (CPU/RAM 모두 반감) | **$1,207.30** |
| Cloud SQL + Redis + 디스크 | 동일 | $753.07 |
| **합계** | | **$7,164.39 / 월** |

> 약 **₩1,040만/월**

→ 상시 가동 대비 **약 45% 절감**. 단, **CUD / Spot 미적용 상태** — 그것까지 적용하면 더 내려갈 여지.

### 2.3 GCE 의 특성

- ✅ HA/패치/autoscale 모두 **직접**: 운영 부담 최대
- ✅ Spot VM, CUD (1년/3년 약정) 자유롭게 적용 가능
- ❌ 노드 단위 관리라 K8s 식 fine-grained 스케일링은 안 됨
- ❌ ext 노드의 "평소 0대 → 띄움" 패턴이 어렵음 (인스턴스 단위 켜고 끄기 수동)

## 3. 시나리오 B — GKE (self-managed Kubernetes)

엑셀 견적 기준. Spot 적극 활용 + 풀 분리로 가장 적극적인 최적화 적용.

### 3.1 노드 풀 구성 (산정 근거)

| 노드 풀 (역할) | 실측 피크 | GKE 산정 스펙 | 산정 근거 |
|---|---|---|---|
| **manager pool** (web/scheduler) | 18 vCPU / 32 GB | **n4-standard-16 × 2대** (32 vCPU / 128 GB) | 단일 서버에서 분산 → HA 확보. 기존 96 vCPU 에서 1/3 로 감축 |
| **celery worker pool** | CPU <5%, RAM 30GB/노드 (총 ~150 GB) | **n4-custom 12 vCPU / 32 GB × 5대** (Regular 1 + Spot 4) | 메모리 병목 대응. CPU 낮추고 RAM 에 집중. OOM 차단 |
| **kubernetes worker pool** (ext 용) | CPU 80% 스파이크 (32c 풀가동) | **n4-highcpu-32 × 최대 2대 (Spot, default 0)** | 평소 0대로 비용 0. 무거운 작업 들어올 때만 띄움 → 반납 |

### 3.2 월 비용

| 컴포넌트 | 월 비용 (USD) |
|---|---|
| celery worker (regular, 1대 24/7) | $480.84 |
| celery worker (spot, 4대) | $803.93 |
| kubernetes worker (spot, 평균 사용분) | $153.62 |
| manager pool (regular, 2대 24/7) | $1,605.14 |
| Cloud SQL (MySQL HA) | $570.38 |
| Memorystore Redis | $178.70 |
| Regional Kubernetes cluster fee | $73.00 (manager pool 항목 안에 포함) |
| **합계** | **$3,792.62 / 월** |

> 약 **₩550만/월**

→ GCE 상시 가동 대비 **약 71% 절감**, 다이어트 버전 대비 **약 47% 절감**.

### 3.3 GKE 의 특성

- ✅ Pod 단위 fine-grained 스케일링 + Spot 적극 활용으로 비용 최저
- ✅ ext 의 "평소 0대" 패턴이 자연스럽게 구현됨
- ✅ HA/롤링 업데이트가 K8s 표준 메커니즘
- ⚠️ Kubernetes 운영 부담 (Pod 설계, autoscaler 튜닝, RBAC, 네트워킹)
- ⚠️ Spot preemption 시 task 재시도 설계 필요

## 4. 시나리오 C — Cloud Composer 3

### 4.1 견적 (엑셀 기준)

| 항목 | 수량 | 월 비용 (USD) |
|---|---|---|
| Composer 3 standard milliDCU-hours | **64,686,760 milliDCU-h** = ~64,687 DCU-h | **$4,967.94** |
| Composer 3 database storage | 40 GB | $8.70 |
| **합계** | | **$4,976.65 / 월** |

> 약 **₩720만/월**
>
> ⚠️ **리전이 `asia-northeast2` (오사카)** — 서울(`asia-northeast3`) 은 **Composer 3 가 현재 미지원**일 가능성. 서울에서 운영하려면 별도 확인 필요.

### 4.2 DCU 환산 의미

64,687 DCU-hour / 730h = **~88.6 DCU/h 평균**

DCU/h ≈ vCPU + GB RAM 공식으로 역산하면, 평균적으로 환경에 **88.6 unit (vCPU+RAM) 정도가 떠있는** 셈. 예: 30 vCPU + 60 GB ≈ 90 DCU/h. 워커 autoscale 로 인해 24/7 풀 가동보다 한참 낮게 책정됨.

### 4.3 Composer 3 의 특성

- ✅ Airflow 운영 부담 거의 없음 (스케줄러/웹/트리거러 관리형)
- ✅ Autoscale 내장
- ❌ **Spot/CUD 적용 거의 불가** → 비용 최적화 여지 제한
- ❌ 서울 리전 미지원 가능성 — 오사카 사용 시 latency / 데이터 주권 이슈
- ❌ Pod 스펙 / 워커 풀 분리 같은 fine-tuning 제한

## 6. 결론 / 함의

1. **순수 비용만 보면 GKE (Spot 적극) 가 압도적**: 월 ₩550만, GCE 상시 대비 **70% 절감**.
2. **Composer 3 는 GKE 보다 약 31% 더 비쌈** (₩170만/월 차이) — 운영 인력 비용을 그 차이로 흡수할 수 있는가가 의사결정 포인트.
3. **메모리 병목 워크로드 + ext 의 CPU 스파이크 패턴**이 명확 → GKE 노드 풀 분리가 자연스럽게 들어맞음. Composer 3 는 이런 fine-tuning 이 제한적이라 손해 봄.
4. **서울 리전 이슈 (Composer 3)** 가 가장 큰 변수. 오사카 운영이 부담스러우면 Composer 3 는 사실상 후보에서 빠짐.
5. **추가 절감 여지**:
   - **Deferrable sensor 전환**: 상위 task 의 절반 이상이 wait sensor (`33239_wait_45_min`, `21541_wait_10_min` 등). 이걸 deferrable 로 바꾸면 worker 점유 시간 대폭 절감 → 워커 수 추가 다운사이즈 가능
   - **CUD 1년 약정**: GCE/GKE 의 regular 부분에 -25% 추가 절감

## 7. 가정 / 미확정

- [ ] **Cloud Composer 3 서울 리전 지원 여부** 공식 확인 (현재 오사카 견적)
- [ ] DCU 환산식이 우리 워크로드에서도 `vCPU + GB_RAM` 으로 정확히 맞는지 (커뮤니티 리버스)
- [ ] Composer 3 에서 CUD 적용 가능한 SKU 범위
- [ ] Spot VM preemption 빈도가 우리 task 재시도율에 미치는 영향
- [ ] sensor → deferrable 전환 시 실제 워커 절감 폭 측정
- [ ] CUD 1년 약정 시 GCE/GKE 견적 재산정
