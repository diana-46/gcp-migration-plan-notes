# 리소스 다이어트 포인트 — Sensor 를 Trigger 로 전면 전환

> [[7_1_실제 스펙 산정]] 의 **다이어트 옵션 B (₩200만/월 추가 절감)** 을 가능하게 만드는 코드 레벨 액션. 단일 변경으로 가장 큰 임팩트를 내는 것이 **모든 Sensor 를 Trigger (deferrable) 로 전환**하는 작업이다.

## 결론 먼저

> **오래 기다리거나 주기적으로 확인만 하는 작업 = 무조건 `deferrable=True`**.
>
> Worker 슬롯 낭비 0, DB 부하 0, 비동기로 수만 개 동시 처리 가능.

## 1. 대기 작업 처리 — 3가지 방식 비교

Airflow 에서 "외부 조건 대기" 를 구현하는 세 가지 방식. 각각의 동작·비용 차이가 결정적이다.

### 1.1 Poke 모드 (기본값 — ❌ 비추천)

**동작**: Worker 슬롯 하나를 점유한 채로 앉아서, 1분에 한 번씩 조건 충족 여부를 찔러봄(poke).

**문제점**:
- 1시간 대기 = Worker 슬롯 하나가 1시간 동안 낭비
- 이런 sensor 100개 켜져 있으면 **Worker 100개가 아무 일도 안 하면서 메모리/슬롯 점유**
- 우리 워크로드의 `33239_wait_45_min` 같은 task 가 정확히 이 패턴 (월 누적 ~2,156 GB·hour 점유)

### 1.2 Reschedule 모드 (기존 대안 — ⚠️ 절반의 성공)

**동작**: 한 번 찔러보고 조건 안 맞으면 Worker 슬롯 반납 → sleep → 지정 시간 후 Scheduler 가 다시 깨움.

**문제점**:
- Worker 낭비는 막았지만, 매번 깨어날 때 **Scheduler 가 재스케줄링 + DB 에 상태 read/write 반복**
- Scheduler 와 metadata DB 에 상당한 부하

### 1.3 Trigger / Deferrable 모드 (현재 표준 — ✅ 강력 추천)

**동작**: 시작하자마자 대기 조건을 **Triggerer** 라는 가벼운 전담 컴포넌트에 던지고, Worker 슬롯은 **즉시 100% 반납**.

**장점**:
- Triggerer 는 **비동기(AsyncIO)** 로 동작 → 단일 프로세스가 **수만 개 센서 동시 처리**
- Worker 낭비 없음
- DB 부하 없음 (Scheduler 재스케줄링 없이 Triggerer 가 자체 처리)
- 가장 최적화된 방식

### 1.4 비교 요약

| 항목 | Poke (기본) | Reschedule | **Trigger / Deferrable** |
|---|---|---|---|
| Worker 슬롯 점유 | 🔴 대기 시간 내내 | 🟡 깨어날 때만 | 🟢 거의 0 |
| Scheduler 부하 | 낮음 | 🔴 주기적 재스케줄링 | 🟢 없음 |
| Metadata DB 부하 | 낮음 | 🔴 주기적 read/write | 🟢 없음 |
| 동시 처리 가능 수 | Worker 수 만큼 | Worker 수 만큼 | 🟢 수만 개 (단일 Triggerer) |
| 우리 코드 적용 비율 | **거의 100%** | 0% | 0% |

→ 우리는 **Poke 100%** 인 상태. Trigger 로 전면 전환 시 sensor 워커 부담이 사실상 0 으로 떨어짐.

## 2. 우리 코드에 적용하는 법

### 2.1 표준 Sensor — `deferrable=True` 한 줄

Airflow 2.x 의 표준 sensor 들은 **파라미터 한 줄 추가로 Triggerer 이관**됨. 새 클래스 만들 필요 없음.

```python
# Before (Poke 모드, Worker 슬롯 점유)
ExternalTaskSensor(
    task_id='wait',
    external_dag_id='other_dag',
)

# After (Triggerer 위임, Worker 슬롯 즉시 반납)
ExternalTaskSensor(
    task_id='wait',
    external_dag_id='other_dag',
    deferrable=True,   # ← 한 줄 추가
)
```

**적용 가능한 표준 sensor** (athlon/airflow.py 에서 사용 중):
- `ExternalTaskSensor`
- `TimeDeltaSensor`
- `S3KeySensor`
- `GCSObjectExistenceSensor`
- `BigQueryTablePartitionExistenceSensor`

→ 모두 `deferrable=True` 추가만 하면 끝.

### 2.2 커스텀 Sensor / Polling 코드 — AsyncIO 마이그레이션

직접 만든 Python 코드에서 `time.sleep()` 을 쓰거나 전통적인 커스텀 Sensor 를 상속하고 있다면, **AsyncIO 기반 Deferrable Operator 로 마이그레이션** 필요.

핵심 원칙:
- HTTP 요청: 동기 라이브러리 `requests` ❌ → 비동기 `aiohttp` ✅
- DB 쿼리: 동기 cursor ❌ → 비동기 driver (예: `asyncmy`, `asyncpg`) ✅
- 대기/주기 확인: `time.sleep()` ❌ → `await asyncio.sleep()` ✅

**우리 코드의 커스텀 sensor**:
- `AthlonQuerySensor` (operators/athlon_query_sensor.py) — sync `BaseSensorOperator` 상속 → trigger 자체 작성 필요 (중간 난이도)
- `BigqueryQuerySensor` — 이미 `BigQueryHook` 사용 → 표준 `BigQueryTablePartitionExistenceSensor` 로 갈음 가능
- `BashSensor` — `mode="reschedule"` 또는 deferrable trigger 작성

### 2.3 사전 조건 — Triggerer 활성화

`airflow.cfg` 또는 환경에 **Triggerer 프로세스가 떠있어야** 한다 (Airflow 2.2+ 기본 지원).

```ini
# airflow.cfg
[triggerer]
default_capacity = 1000   # 단일 triggerer 가 처리할 수 있는 동시 trigger 수

# 또는 systemd / k8s deployment 에서
airflow triggerer
```

GKE 에서는 별도 Pod / Deployment 로 띄움. Composer 3 는 기본 내장.

## 3. 정량적 효과 추정

### 3.1 현재 상태

- 코드 전체 `deferrable=True` **0건**, `mode="reschedule"` **0건**
- 모든 sensor 가 Poke 모드로 동작
- 상위 30일 누적 점유 시간 task 들이 대부분 `*_wait_*_min` / `*_wait_*_hour` 류 sensor

### 3.2 단일 task 예시

`33239_wait_45_min` (월 719회 실행, 평균 43.6분 대기) 기준:

| 항목 | Poke (현재) | Trigger 적용 후 |
|---|---|---|
| Worker 슬롯 점유 시간 | 43.6분 × 719회 = **~522 시간/월** | 거의 0 |
| Worker 메모리 점유 | 4 GB × 522h = **~2,088 GB·hour/월** | 거의 0 |

이런 sensor 가 상위 task 의 절반 이상 → 누적 효과 매우 큼.

### 3.3 인프라 비용 영향 (7_1 견적 연결)

7_1 의 옵션 B (concurrency=4 + deferrable sensor) 가 가능해지는 전제 조건이 본 작업.

| 시나리오 | 옵션 A 비용 | 옵션 B 비용 | 차이 |
|---|---|---|---|
| GKE | ₩550만/월 | ₩344만/월 | **₩206만/월 절감** |
| GCE 다이어트 | ₩952만/월 | ₩689만/월 | ₩263만/월 절감 |

→ Sensor 다이어트 단일 작업으로 **연 ₩2,400만~3,100만 절감**.

## 4. 적용 우선순위 / 작업 계획

### Phase 1: 표준 Sensor 일괄 전환 (1~2일)

`athlon/airflow.py` 의 sensor 빌더 함수들에 `deferrable=True` 추가:

| 빌더 위치 | Sensor | 작업 |
|---|---|---|
| `athlon/airflow.py:203-213` | `TimeDeltaSensor` | kwargs 에 `deferrable=True` |
| `athlon/airflow.py:282-291, 482-491` | `ExternalTaskSensor` | 동일 |
| `athlon/airflow.py:195-198` | `S3KeySensor` | 동일 |
| `athlon/airflow.py:292-297` | `GCSObjectExistenceSensor` | 동일 |

→ 단일 파일 변경으로 **거의 모든 DAG 에 즉시 적용**됨 (athlon-derived 구조 덕분).

### Phase 2: 커스텀 Sensor 마이그레이션 (1~2주)

| Sensor | 작업 |
|---|---|
| `BigqueryQuerySensor` | 표준 `BigQueryTablePartitionExistenceSensor` 로 갈음 (또는 deferrable trigger 작성) |
| `AthlonQuerySensor` | 자체 trigger 작성. `eval()` 기반 condition 은 그대로 두고 polling 만 async 화 |
| `BashSensor` | deferrable trigger 작성 또는 `mode="reschedule"` 우선 적용 (임시) |

### Phase 3: Triggerer 운영 안정화

- Triggerer 프로세스 모니터링 (CPU/메모리 / lag)
- `default_capacity` 튜닝
- HA 구성 (GKE 라면 replicas ≥ 2)

## 5. 검증 방법

### 5.1 적용 전후 메트릭 비교

```sql
-- Airflow metadata DB 에서 sensor task 의 worker 점유 시간 측정
SELECT
    task_id,
    SUM(EXTRACT(EPOCH FROM (end_date - start_date))) / 60 AS total_minutes
FROM task_instance
WHERE task_id LIKE '%_wait_%'
  AND start_date >= NOW() - INTERVAL '7 days'
GROUP BY task_id
ORDER BY total_minutes DESC
LIMIT 20;
```

적용 후 같은 쿼리를 돌려서 `total_minutes` 가 거의 0 으로 떨어졌는지 확인.

### 5.2 워커 노드 메모리 사용량 측정

[[7_1_실제 스펙 산정]] 의 30일 측정 스크립트 재실행 → worker 노드 평균/피크 메모리 비교.

기대치:
- 현재: 평균 15.8 GB / 피크 28-29 GB (94%)
- Trigger 적용 후: 평균 ~8-10 GB / 피크 ~15-20 GB 예상

피크 메모리가 충분히 떨어지면 [[7_1_실제 스펙 산정]] 의 **옵션 B 견적이 안전하게 실현 가능**해짐.
